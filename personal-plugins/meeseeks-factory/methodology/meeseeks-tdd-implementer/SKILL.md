# Meeseeks TDD Implementer — реализация ТЗ в Codex

## Реализация по ТЗ

Скил исполняет ТЗ, а не решает, что делать. Содержание работы — из ТЗ; процесс — из этого
файла. Формат и состав ТЗ — `meeseeks-spec`; здесь ТЗ принимается как есть и не дополняется.

Архитектурные решения принимает человек. Скил их не принимает ни при каких условиях.

## Промпт реализации: чем он отличается от ТЗ

ТЗ отвечает на вопрос, что меняется и как это проверяется. Промпт реализации отвечает на
вопрос, как это исполняется: роль и режим, проверка репозитория и pinning, TDD, ветка и PR,
поведение при CI, критические правила. Одно не заменяет другое.

Разделы промпта, несущие содержание — задача, изменения по слоям, приёмочные критерии,
тесты, инварианты и out of scope, — приходят из ТЗ и не пересочиняются. Разделы, несущие
процесс, — поведение этого скила, шаги ниже.

Процессный каркас приходит готовым из шаблона промпта воркера. Скил его не переписывает: он
подставляет факты этого вызова — репозиторий из ТЗ, режим по Шагу 1, наличие CI по факту
Шага 3 — и дальше исполняет.

## Шаг 0 — Вход

ТЗ поступает одним из способов: текст в сообщении, путь к файлу, приложенный файл. Прочитать
целиком до первого действия с репозиторием.

Остановки на входе:

- **На входе список развилок, а не ТЗ** (заголовок «Задача [ID] не готова к ТЗ» или разделы
  «Развилка N») — не реализовывать. Сообщить: развилки закрываются человеком записью на лист
  «Развилки», ТЗ перевыпускается через `meeseeks-spec`.
- **На входе номер задачи без ТЗ** — не сочинять ТЗ. Сообщить: ТЗ строит `meeseeks-spec`.
- **В ТЗ не назван репозиторий** — не достраивать по шаблону и не выводить из текущего
  каталога. Сообщить: ТЗ неполно, репозиторий обязателен.
- **В ТЗ не названа базовая ветка среза** — не подставлять дефолтную ветку репозитория.
  Базовая ветка есть собственное свойство среза и приходит в ТЗ вместе с репозиторием.
  Сообщить: ТЗ неполно, базовая ветка обязательна.
- **На входе несколько ТЗ (многорепозиторная задача)** — исполнять только то, репозиторий
  которого совпадает с текущим. Остальные назвать в отчёте с порядком запуска из раздела
  «Межрепозиторные зависимости»; репозиторий за сессию не менять.

## Шаг 1 — Режим

По заголовку ТЗ:

- Обычное ТЗ → **режим «новая задача»**: новая ветка от зафиксированного base_sha, новый PR.
- ТЗ с пометкой «Тип: доработка существующего PR, не новая задача» → **режим «доработка»**:
  новая ветка не создаётся, работа идёт в названные ТЗ ветку и PR.

Режим определяется один раз и дальше не пересматривается.

## Шаг 2 — Проверка репозитория и pinning

```bash
git remote -v
git rev-parse --abbrev-ref HEAD
git status --porcelain
```

- Сверить remote с репозиторием из ТЗ. **Несовпадение — остановка**: не анализировать код, не
  предлагать «похожий» репозиторий. По этому же remote определяется хостинг репозитория: от
  него дальше зависят признак CI (Шаг 3) и команды работы с PR или MR (Шаги 7-8).
- Рабочее дерево грязное — остановка, разбирается человеком.

<!-- example:start -->
Признак устаревшего ТЗ: путь из расформированного `meeseeks-gev-fabric`; все репозитории
фабрики — на аккаунте `nikell28`.
<!-- example:end -->

**Режим «новая задача»:**

```bash
git fetch origin
git checkout -b <ветка среза> origin/<base>
git rev-parse HEAD    # base_sha — зафиксировать и назвать в отчёте
```

Имя ветки собирается по конвенции репозитория и несёт идентификаторы среза и задачи. Срез
берётся из ТЗ; если не назван — первый. Базовая ветка — та, что названа в ТЗ; она приходит
вместе с репозиторием среза и на дефолтную ветку репозитория не заменяется. Не названа —
остановка по Шагу 0: сборка против дефолтной ветки ломает цепочку срезов.

<!-- example:start -->
Конвенция фабрики: ветка `feat/s<срез>-<ID>-<slug>`, при неназванном срезе — `s1`;
заголовок PR — `feat: <ID> — <название>`.
<!-- example:end -->

**Режим «доработка»:**

```bash
git fetch origin
git checkout <ветка из ТЗ>
git pull --ff-only
git rev-parse HEAD    # текущий HEAD ветки
```

Если HEAD ушёл дальше коммита, на котором проводилось ревью (коммит назван в ТЗ), — это
факт для отчёта и для тела PR перед началом работы, не повод останавливаться и не повод
молчать.

## Шаг 3 — Разведка репозитория

Читать только то, что названо в плане изменений ТЗ, и прямые зависимости этих модулей.
Не читать репозиторий целиком.

Зафиксировать до написания кода:

- команду прогона тестов и раннер (`pyproject.toml`, `Makefile`, `pytest.ini`, `package.json`);
- конвенции тест-файлов: расположение, именование, фикстуры, маркеры;
- наличие CI: признак — файл или каталог пайплайна того хостинга, который определён по
  `git remote` на Шаге 2. Отсутствие пайплайна этого хостинга — надёжный отрицательный факт:
  CI нет, финальная проверка идёт локальным полным сьютом;
- линтеры и типизацию, которые гоняет CI (ruff, mypy, eslint) — чтобы не узнать о них на
  третьей попытке.

<!-- example:start -->
Признак CI по хостингам: GitHub — каталог `.github/workflows/`; GitLab — `.gitlab-ci.yml`.
<!-- example:end -->

## Шаг 4 — План

Перед первым тестом собрать и показать план: порядок слоёв из ТЗ, тест-кейсы по фазам с
TC-ID, файлы к созданию и изменению, out of scope. Подтверждение не запрашивается —
план показывается, работа продолжается.

Порядок исполнения — порядок зависимостей из раздела «Изменения по слоям» ТЗ. Слой не
начинается, пока предыдущий не зелёный.

Перед первым тестом сойтись должно всё: репозиторий один и сверен с ТЗ, base_sha
зафиксирован, режим определён по Шагу 1, наличие CI установлено по факту Шага 3, план
покрывает все слои ТЗ и все TC-ID реестра. Что-то не сходится — не начинать, назвать явно.

## Шаг 5 — Цикл TDD

Реестр тестов — раздел «Тесты» ТЗ, перенесённый из листа «Тесткейсы». Состав фаз A и B
задан в ТЗ (`meeseeks-spec`). Порядок исполнения: фаза A — по мере прохождения слоёв, фаза
B — после закрытия всех слоёв.

Для каждого TC-ID:

1. **Тест.** Given/When/Then кейса переносится в тест-функцию. TC-ID — в имени функции или в
   докстринге, чтобы ревью сопоставляло кейс и тест без догадок.
2. **Красная фаза, проверенная.** Прогнать тест, прочитать причину падения. Падение из-за
   синтаксиса, опечатки в импорте или неверной фикстуры красной фазой не является — это
   сломанный тест. Красная фаза не подтверждена — код логики не пишется.
3. **Минимальная логика.** Ровно то, что описано в ТЗ среза. Модули вне плана ТЗ не
   меняются, out of scope не трогается.
4. **Зелёная фаза.** Тест правится под логику — никогда. Логика правится под тест — всегда.
5. **Рефакторинг** — по необходимости, при зелёных тестах.

### Границы реестра

За пределы реестра тестов не выходить. Если реализация требует теста, которого в реестре
нет, — завести его по правилу идентификатора из `meeseeks-testcases` и с пометкой «требует внесения в лист
«Тесткейсы»»; пометка идёт в тело PR и в отчёт. Молча дописанных кейсов не бывает. Вывод
кейсов и ведение реестра — `meeseeks-testcases`.

### Тест, который нельзя прогнать здесь

Тесты, зависящие от внешней инфраструктуры — контейнеров, реестра образов, оркестратора,
движка процессов, базы, объектного хранилища, — в среде Codex могут быть недоступны.
Такой тест помечается `skip` с указанием TC-ID и причины пропуска, а не переписывается до
состояния, в котором он проходит без инфраструктуры. Список пропущенных — в теле PR и в
отчёте.

<!-- example:start -->
В контуре фабрики это тесты, зависящие от Docker, реестра образов, Nomad, Temporal,
Postgres или MinIO.
<!-- example:end -->

Безусловный `skip`, `assert True`, тест без assert и тест, где мок закрывает ровно тот
уровень, который проверяется, — тесты, которые ревью классифицирует как нечестные
(`meeseeks-review`). Не писать.

<!-- example:start -->
Замоканный `execute_activity` не ловит отсутствие регистрации activity: мок закрывает ровно
проверяемый уровень.
<!-- example:end -->

### Проверка на форму, а не на свойство

Grep по тексту файла и проверка присутствия строки — слабейший класс проверки. Там, где
кейс формулирует наблюдаемое свойство системы, тест проверяет свойство, а не форму артефакта.

## Шаг 6 — Расхождение, контракт и развилка: три разных правила

**Техническое расхождение** — названного в ТЗ модуля, пути, зависимости или сигнатуры в
репозитории нет, либо они отличаются. Реализуется наиболее консервативный вариант,
сохраняющий инварианты. Расхождение и выбранный вариант идут в раздел «⚠️ Расхождения с ТЗ»
тела PR. Работа продолжается.

**Расхождение с контрактом** — затронута граница, у которой в ТЗ назван ID контракта.
Прогон против снимка контракта обязателен: нарушение рамки ловится на ревью, нарушение
контракта — только прогоном против снимка. Прогон зелёный — работа продолжается. Прогон
красный — **остановка**: изменение контракта одним PR не вносится, второй стороной границы
оно тоже должно быть принято. ID контракта и результат прогона идут в отчёт и в тело PR в
обоих случаях. Правило заведения контракта — `meeseeks-methodology`.

**Неустранимая развилка** — архитектурный выбор, который не выводится ни из фактов кода, ни
из строки листа «ADR», ни из строки листа «Развилки» (Р-N), ни из записи листа «Решения»:
два и более равнозначных варианта, и решение принадлежит человеку. Признаки: план ТЗ
предполагает решение, для которого в коде есть 2+ равноценных места, и ни одно не закрыто
перечисленными основаниями; ТЗ и код расходятся так, что консервативный вариант не определён.
Открытый вопрос листа «Открытые вопросы» (ОВ-N), накрывающий предмет выбора, — самостоятельное
основание остановиться.

При развилке — **остановка**:

- код и тесты, написанные до этого места, коммитятся в ветку как есть;
- в режиме «новая задача» PR не создаётся, ветка остаётся локальной; в режиме «доработка»
  коммиты пушатся в существующую ветку, тело PR дополняется разделом «Остановка: развилка»;
- в чат выдаётся список развилок в формате: суть, контекст (факты кода, которые вопрос не
  разрешают), варианты с плюсами и рисками у каждого; каждая остановка оформляется записью
  на лист «Развилки»;
- ни один вариант не выбирается и не помечается предпочтительным.

Обход развилки пометкой в PR не заменяет остановку. Статусами реестров этот скил не владеет
и их не проставляет.

## Шаг 7 — Коммиты, ветка, PR

Ветка и PR — на срез как единицу поставки (`meeseeks-slice`).

Коммиты — точечно по файлам: `git add <файл>`, никогда `-A` и `.`. Один коммит — одна
логическая единица (тест red, затем логика green — допустимо одним коммитом на TC-ID).

Финальная проверка до PR: полный тест-сьют репозитория, не только написанные тесты. Ни один
существующий тест не сломан. Линтеры и типизация, найденные на Шаге 3, прогнаны локально.

**Режим «новая задача»** — создать PR:

```bash
git push -u origin <ветка среза>
```

Дальше — команда создания PR или MR того хостинга, который определён по `git remote` на
Шаге 2: заголовок по конвенции репозитория, тело из файла, база — базовая ветка среза из ТЗ.

<!-- example:start -->
GitHub: `gh pr create --title "<тип>: <ID> — <название>" --body-file <файл> --base <base>`.
GitLab: `glab mr create --title "<тип>: <ID> — <название>" --description-file <файл> --target-branch <base>`.
<!-- example:end -->

Тело PR:

```markdown
## Что сделано
[2–3 предложения из цели ТЗ]

## Задача
[ID] · base_sha: [sha]

## Тест-кейсы
| TC-ID | Фаза | Тип | Статус |
|-------|------|-----|--------|
| TC-... | A | U | ✅ |
| TC-... | B | E | ⏭ skip: требует инфраструктуры |

## Изменённые файлы
- `путь` — [что]

## Чек-лист
- [ ] Все кейсы реестра покрыты
- [ ] Красная фаза подтверждена по каждому тесту
- [ ] Полный сьют зелёный, регрессий нет
- [ ] Out of scope не затронут, чужие тесты не изменены
- [ ] Инварианты из раздела ТЗ соблюдены

## ⚠️ Расхождения с ТЗ
[если есть: расхождение, выбранный консервативный вариант, основание]

## Контракты
[если граница затронута: ID контракта — прогон против снимка: зелёный / красный (остановка)]

## Новые тест-кейсы вне реестра
[если есть: TC-<ID>-D<N> — требует внесения в лист «Тесткейсы»]
```

**Режим «доработка»** — новый PR не создаётся. Коммиты пушатся в существующую ветку, тело
PR #N дополняется разделом:

```markdown
## Доработка по ревью, цикл [k]
Исправлено по находкам: [номера и формулировки находок]
Изменённые файлы: [список]
HEAD на старте цикла: [sha] [+ «ушёл дальше коммита ревью [sha]», если применимо]
```

Если CLI хостинга недоступен — запушить ветку и выдать ссылку для создания PR или MR вручную.
Ошибка создания PR отчёт не блокирует: статус PR указывается в отчёте явно.

## Шаг 8 — CI

Выполняется только если CI найден на Шаге 3. Иначе: полный локальный сьют до зелёного,
и это названо в отчёте.

Прогресс проверок и лог упавшего джоба смотрятся командами того хостинга, который определён
по `git remote` на Шаге 2.

<!-- example:start -->
GitHub: `gh pr checks <N> --watch`, `gh run view --log-failed`.
GitLab: `glab ci status`, `glab ci trace <job>`.
<!-- example:end -->

Максимум **5 попыток**, счётчик не сбрасывается.

| Причина падения | Действие |
|---|---|
| Assertion в тесте задачи | Править логику, не тест |
| Линтер, форматирование | Применить правило репозитория |
| Типы, сборка, импорты | Править код |
| Инфраструктура CI (timeout, сеть, flaky) | Перезапустить job, код не трогать |
| Падает чужой тест вне scope | Остановка, не править — это либо регрессия от изменения (тогда править своё), либо чужая проблема (тогда в отчёт) |

Правила исправления: минимальное изменение, только то, что вызвало падение; тесты реестра не
переписываются; out of scope не затрагивается.

После 5 попыток — остановка со статусом «CI не прошёл»: последняя ошибка дословно, перечень
попыток с результатами, гипотеза причины.

## Шаг 9 — Отчёт

```
[ID] — [название] · [репозиторий]

Режим: новая задача / доработка, цикл k
Ветка: [ветка] · базовая ветка: [base] · base_sha: [sha]
PR: [ссылка] / не создан ([причина])
CI: зелёный / не найден, локальный сьют зелёный / не прошёл после 5 попыток

Тест-кейсы: N покрыто, M пропущено (инфраструктура), K заведено вне реестра
Файлов изменено: X, создано: Y
Регрессии: нет / [описание]

Расхождения с ТЗ: [список] / нет
Контракты: [ID контракта — прогон против снимка зелёный / красный] / границы не затронуты
```

## Критические правила

- ТЗ — источник содержания; этот файл — источник процесса. Содержание ТЗ не
  переписывается и не дополняется по своему усмотрению.
- Один вызов = один репозиторий. Многорепозиторная задача исполняется по одному ТЗ за
  сессию, в порядке из раздела «Межрепозиторные зависимости».
- Тесты не правятся под логику. Логика правится под тесты.
- Реестр «Тесткейсы» — граница. Кейс вне реестра существует только с ID и пометкой.
- Красная фаза проверяется, а не предполагается.
- Техническое расхождение — консервативный вариант плюс раздел в PR. Расхождение с
  контрактом — прогон против снимка, красный прогон означает остановку. Неустранимая
  развилка — остановка со списком вариантов, без выбора.
- Архитектурное решение за человека не принимается ни при каких условиях, включая случай,
  когда вариант выглядит единственным разумным.
- Out of scope не трогается, чужие тесты не изменяются.
- Коммиты точечно по файлам.
- Молчание не заменяет отчёт: расхождения, пропуски и остановки называются явно.
