# Meeseeks Delivery Cycle - сквозной прогон задачи

## Единица прогона

Единица прогона - задача. **Один прогон - одна задача - одно состояние.** Единица приёмки
внутри прогона - срез: вердикт выносится по срезу, счётчик циклов доработки ведётся по срезу,
терминальное состояние наступает у среза. У задачи вердикта нет, задача закрыта, когда закрыт
каждый её срез.

Цепочка прогона:

```
spec-cycle -> tdd-implementer -> review-cycle -> ( tdd-implementer -> review-cycle ) * N
```

Скобки исполняются, только если вердикт по срезу отличен от PASS, и повторяются, пока вердикт
не станет PASS. **N не больше пяти на срез.** Счётчик считается по срезу, не по задаче: срезы
идут разными PR и сходятся независимо, и срез, исчерпавший потолок, не закрывает прогон по
остальным.

Первое ревью в потолок не входит: пять - это число циклов доработки, то есть пар
(реализация, приёмка) после первого вердикта. Ревью по срезу за прогон не больше шести.

## Место в методологии

Обёртка над `meeseeks-spec-cycle`, `meeseeks-tdd-implementer` и `meeseeks-review-cycle`.
Правила нарезки, триажа, сборки ТЗ, TDD, порога находки и таксономии вердиктов живут в них и
в скилах, которые они сами оборачивают. Здесь они не дублируются и не смягчаются.

Этот скил отвечает за пять вещей: порядок вызовов, состояние прогона между вызовами,
изоляцию контекста каждого сабагента, счётчик циклов доработки и его потолок, сводный отчёт.

Вход - ID задачи. Выход - открытые PR по срезам задачи, отчёты ревью, файлы ТЗ каждого цикла
и сводка по каждому срезу: PASS, выпал, исчерпал потолок.

**Граница скила:** ТЗ не пишет, код не правит, диффы не читает, вердикт не выносит и не
пересматривает, PR не мержит и не аппрувит, в файл проекта и в Google Drive не пишет, статусы
срезов не проставляет.

## Изоляция вложенных скилов

Каждый вложенный скил исполняется отдельным сабагентом. Сабагент получает пути, идентификаторы
и параметры своего шага - не переписку прогона, не отчёты соседних сабагентов, не результаты
предыдущих циклов сверх названных ниже.

| Сабагент | Промпт | Что получает | Что возвращает |
|---|---|---|---|
| spec-cycle | `agents/specer.md` | ID задачи, `run_dir`, запрет коммита в inbox | `spec-result.json`, файлы ТЗ в `run/` |
| tdd-implementer | `agents/implementer.md` | один файл ТЗ, `repo`, `base_branch`, `contract`, `workdir`, режим, ветка и PR при доработке | `impl.json` |
| review-cycle | `agents/reviewer.md` | ID задачи, перечень срезов на приёмку, `run_dir`, `tz-index.txt`, пометки циклов, запрет коммита в inbox | `review-result.json`, отчёты ревью |

Оркестратор передаёт между шагами только машиночитаемые поля: имена и пути файлов ТЗ,
`repo`, `base_branch`, `contract`, `branch`, `pr`, `verdict`. Текст ТЗ и текст отчёта ревью
через оркестратора не проходят: их читает следующий сабагент по пути.

Сабагент реализации получает **одно ТЗ**. Соседние ТЗ того же среза, ТЗ соседних срезов и
отчёты ревью прошлых циклов ему не передаются: скоуп доработки уже сведён в его ТЗ скилом
`meeseeks-fix-spec`.

## Режим запуска

Cowork. Оркестратор и все сабагенты - Opus 5; модель задаётся параметром `model` инструмента
Agent при каждом диспатче. У человека модель не спрашивается. Ревью на слабой модели даёт
ложный PASS, а по ложному PASS код уходит в мерж.

Рабочая папка прогона - `run/<задача>/`:

```
run/<задача>/spec/                 рабочая папка сабагента spec-cycle
run/<задача>/spec-result.json      состав срезов, файлы ТЗ, outcome по каждому срезу
run/<задача>/cycle.json            состояние прогона
run/<задача>/tz-index.txt          перечень файлов ТЗ прогона
run/<задача>/repos/<repo>/         клон репозитория среза
run/<задача>/<срез>/c<N>/tz-*.md   файлы ТЗ цикла N
run/<задача>/<срез>/c<N>/impl-*.json   результаты сабагентов реализации
run/<задача>/review-c<N>/          рабочая папка сабагента review-cycle волны N
run/<задача>/review-result-<N>.json
```

Папка даёт возобновляемость: прерванный прогон продолжается по `cycle.json` с того среза и
той части, на которых встал. Уже собранные ТЗ не пересобираются, уже реализованные части не
переисполняются, уже полученные вердикты не перезапрашиваются.

## Два изменения в поведении вложенных скилов

Оба заданы явно в промптах сабагентов и вне этого прогона не действуют.

1. **Коммит в inbox не выполняется.** Шаг 7 `meeseeks-spec-cycle` и Шаг 8
   `meeseeks-review-cycle` в этом прогоне пропускаются. ТЗ исполняет сабагент этого же
   прогона; попав в inbox, то же ТЗ разобрал бы ещё и внешний воркер, и на срез вышло бы два
   PR. Планы (`Шаг 6а` и `Шаг 7а` вложенных скилов) собираются как обычно и остаются в `run/`:
   порядок публикации нужен оркестратору как порядок реализации.

2. **Номер цикла доработки считается по прогону.** `new_tz.py --rework-auto --existing`
   получает `run/<задача>/tz-index.txt` вместо листинга корня inbox. В inbox файлов этого
   прогона нет, и счёт по нему дал бы `rework-1` на каждом цикле, то есть перезапись ТЗ.
   Индекс ведёт `cycle_state.py tz-index` перед каждым диспатчем review-cycle.

Всё остальное во вложенных скилах исполняется по их инструкциям без изменений.

## Шаг 0 - Предусловия среды

Проверяются до первого сабагента. Прогон, который встанет на середине из-за отсутствующего
доступа, уже потратил сборку ТЗ.

- `git` есть, токен с правом пуша в репозитории проекта доступен процессу.
- Хостинг каждого репозитория прогона берётся из колонки «Путь» листа «Репозитории» файла
  проекта. У каждого хостинга свой способ создать PR или MR и прочитать прогон CI; доступ к
  этому способу проверяется до первого сабагента. CLI конкретного хостинга предпосылкой не
  является: в контейнере его может не быть.
  <!-- example:start -->
  Репозиторий на GitHub - GitHub MCP (`create_pull_request`, `pull_request_read`); репозиторий
  на GitLab - MCP или REST GitLab: merge request и pipelines.
  <!-- example:end -->
- Место под клоны репозиториев срезов задачи.

Чего-то нет - стоп на входе с называнием недостающего. Прогон без пуша не автономен: PR не
появится, а без PR приёмке нечего принимать.

## Шаг 1 - ТЗ по задаче

Один сабагент по `agents/specer.md` на весь шаг. В промпт подставляются: ID задачи,
`run_dir` = `run/<задача>/spec`, путь `run/<задача>/spec-result.json`.

Сабагент исполняет `meeseeks-spec-cycle` целиком, включая снимок файла проекта, состав задачи,
нарезку, диспатч своих сабагентов по срезам и сборку плана. Коммит в inbox не делает.

Оркестратор в сборку ТЗ не вмешивается: код не читает, оценку и разрез на части не
пересматривает, потолок бюджета не поднимает.

Остановки шага:

- **Задача не нарезана** (`sliced: false`): сабагент возвращает патч листов «Срезы» и
  «Тесткейсы». Строки вносит человек - прогон останавливается и ждёт. Строки внесены - Шаг 1
  повторяется.
- **Развилки вместо ТЗ**: Шаг 7.
- **Ни одного собранного ТЗ**: стоп, дальше идти не с чем.

## Шаг 2 - Состояние прогона

```
python3 scripts/cycle_state.py init \
  --spec-result run/<задача>/spec-result.json \
  --out run/<задача>/cycle.json
```

Состояние держит по каждому срезу: репозиторий, базовую ветку, ID контракта,
`depends_in_task`, номер цикла, файлы ТЗ каждого цикла, ветку, PR, число реализованных частей,
вердикты, терминальное состояние.

Репозиторий и базовая ветка приходят из колонки «Репозиторий» строки среза на листе «Срезы» -
она несёт и то, и другое: срез есть единица поставки, и куда он мержится, его собственное
свойство. Сабагент spec-cycle отдаёт их полями `repo` и `base_branch` в `spec-result.json`,
`init` переносит их в `cycle.json`, оркестратор передаёт параметром сабагенту реализации. ID
контракта из колонки «Контракт» строки среза едет тем же путём полем `contract`: правила
контракта здесь не пересказываются, их держит `meeseeks-methodology`.

Молчаливый откат на дефолтную ветку репозитория - дефект, а не запасной путь: ТЗ, ветка, PR и
ревью построятся против чужой базы.

Код возврата 2 - вход отвергнут: цикл в зависимостях срезов, зависимость на срез вне состава,
срез с `outcome: spec` без файлов ТЗ, без репозитория или без базовой ветки. Стоп, вход
правится; состояние руками не пишется.

Дальше прогон идёт циклом: `next` - диспатч - `record`. Что делать дальше, считает скрипт:

```
python3 scripts/cycle_state.py next --state run/<задача>/cycle.json
```

| `action` | Что означает | Куда идти |
|---|---|---|
| `implement` | есть части ТЗ, готовые к реализации | Шаг 3 |
| `review` | есть срезы, у которых реализованы все части цикла | Шаг 4 |
| `cascade` | предшественник среза закрылся неуспешно | Шаг 7 |
| `waiting` | ждёт ТЗ на доработку или предшественника | Шаг 6 |
| `done` | все срезы терминальны | Шаг 8 |

Порядок между срезами - `depends_in_task`: срез не начинает реализацию, пока каждый его
предшественник внутри задачи не получил PASS. Порядок внутри среза - порядок частей ТЗ:
часть N не начинается, пока не реализована часть N−1.

## Шаг 3 - Реализация

На каждую позицию `implement` - отдельный сабагент по `agents/implementer.md` с `model` =
Opus 5. Позиции разных срезов идут параллельно, не больше трёх сразу; позиции одного среза -
строго последовательно.

В промпт подставляются: `slice_id`, `repo`, `base_branch`, `contract`, путь файла ТЗ,
`workdir` = `run/<задача>/repos/<repo>`, `mode`, `branch` и `pr` (при `mode: rework`),
`output_dir`.

Клон репозитория делает оркестратор до первого диспатча по этому репозиторию. Клонируется путь
репозитория из колонки «Путь» листа «Репозитории» и базовая ветка среза:

```
git clone --branch <base_branch> <путь репозитория из реестра> run/<задача>/repos/<repo>
```

<!-- example:start -->
```
git clone --branch zn-translate https://gitlab.mpstats.io/frontend/mpstatsPlugin.git \
  run/Z-14/repos/mpstatsPlugin
```
<!-- example:end -->

Клон один на репозиторий на прогон. Два среза одной репы в задаче допустимы, и их сабагенты
работают в одном клоне последовательно: параллельная работа двух агентов в одном рабочем
дереве даёт перемешанные коммиты.

**Режим не выводится сабагентом из заголовка ТЗ.** Он приходит параметром:

- `mode: new` - только часть 1 первичного цикла: новая ветка от `base_branch` среза по
  зафиксированному на ней `base_sha`, новый PR в ту же `base_branch`.
- `mode: rework` - все остальные позиции: работа идёт в названную ветку, PR дополняется.
  Части одного среза идут одной веткой и одним PR (`meeseeks-slice`), и части 2..M
  первичного цикла в этом смысле ничем не отличаются от доработки.

Сабагент возвращает `impl.json`. Оркестратор записывает факт:

```
python3 scripts/cycle_state.py record --state run/<задача>/cycle.json \
  --slice <срез> --implemented --branch <ветка> --pr <ссылка>
```

Скрипт отказывает, если все части цикла реализованы, а PR не назван: приёмка сопоставляет PR
со срезом по имени файла ТЗ в теле PR, и без PR ревью нечего принимать.

Исходы сабагента, отличные от реализации:

| Исход `impl.json` | Действие |
|---|---|
| `implemented` | `record --implemented`, следующая часть или приёмка |
| `fork` | Шаг 7: сабагент остановился на неустранимой развилке |
| `mismatch` | `record --drop`: remote не совпал с репозиторием ТЗ, ТЗ неполно |
| `ci_failed` | `record --implemented` всё равно: CI красный после пяти попыток - предмет ревью, не остановка прогона |
| `failed` | один повторный диспатч той же позиции; второй сбой - `record --failed` |

CI, не сошедшийся за пять попыток внутри `meeseeks-tdd-implementer`, прогон не останавливает:
красный CI виден ревьюеру и становится находкой. Потолок попыток CI и потолок циклов
доработки - разные счётчики, друг друга не сбрасывают.

## Шаг 4 - Приёмка

Перед диспатчем обновить индекс ТЗ:

```
python3 scripts/cycle_state.py tz-index --state run/<задача>/cycle.json \
  --out run/<задача>/tz-index.txt
```

Один сабагент по `agents/reviewer.md` с `model` = Opus 5 на всю волну приёмки. В промпт
подставляются: ID задачи, перечень срезов из `review`, `run_dir` = `run/<задача>/review-c<N>`,
путь `tz-index.txt`, пометки циклов из `next_notes`, путь результата
`run/<задача>/review-result-<N>.json`, запрет коммита в inbox.

Сабагент исполняет `meeseeks-review-cycle` целиком: поиск открытых PR по каждому срезу,
диспатч своих ревьюеров, закрытие развилок основанием, сборка ТЗ на доработку по срезам с
вердиктом REWORK или FAIL, сборка плана цикла доработки. Коммит в inbox не делает.

Приёмка идёт волной на все готовые срезы разом: единица прогона `meeseeks-review-cycle` -
задача, и разбивать её на срезы значило бы перевыгружать снимок файла проекта на каждый срез.

Срез, у которого волна не нашла открытого PR, - не ошибка приёмки, а факт: реализация не
доехала. Он приходит из волны вердиктом `NO_PR` и записывается тем же `record --verdict`, что
и любой другой вердикт волны (Шаг 5), с причиной ключом `--reason`. Скрипт делает срез
терминальным `dropped`; это строка отчёта. Отдельного `--drop` для этого исхода нет: `--drop`
остаётся за исходами, у которых вердикта волны не было вовсе - `mismatch` реализации и
каскадом закрытый предшественник.

Оркестратор в ревью не вмешивается: диффы не читает, находки не добавляет и не снимает,
вердикт не пересматривает ни в одну сторону.

## Шаг 5 - Маршрутизация по вердиктам

Маршрут считается по полю `verdict` из `review-result-<N>.json`, не по впечатлению от текста
отчёта. По каждому срезу волны:

```
python3 scripts/cycle_state.py record --state run/<задача>/cycle.json \
  --slice <срез> --verdict <PASS|REWORK|FAIL|ESCALATE|NO_PR|FAILED> [--reason <текст>]
```

| `verdict` | Что делает скрипт | Что дальше |
|---|---|---|
| `PASS` | срез терминален | мерж - решение человека, прогон его не делает |
| `REWORK` / `FAIL` | цикл не исчерпан: срез уходит в `reworking` | Шаг 6 |
| `REWORK` / `FAIL` на пятом цикле | срез терминален, `exhausted` | отчёт |
| `ESCALATE` | срез терминален, `dropped` | Шаг 7 |
| `NO_PR` | срез терминален, `dropped` | отчёт |
| `FAILED` | срез терминален, `dropped` | отчёт |

Вердикт сабагента - данность. PASS не превращается в REWORK, REWORK не смягчается до PASS.

## Шаг 6 - Цикл доработки

ТЗ на доработку собирает сабагент review-cycle на своём Шаге 7 - оркестратор его не пишет и
не переименовывает. Файлы ТЗ этого цикла записываются в состояние:

```
python3 scripts/cycle_state.py record --state run/<задача>/cycle.json \
  --slice <срез> --tz <имя файла> [--tz <имя файла> …] \
  --tz-path <путь> [--tz-path <путь> …]
```

Скрипт поднимает номер цикла среза, обнуляет счётчик реализованных частей и возвращает срез в
очередь на реализацию. Порядок `--tz` - порядок частей; он же порядок реализации.

Дальше срез идёт тем же Шагом 3 в режиме `rework`: ветка и PR у него уже есть.

**Потолок - пять циклов доработки на срез.** Срез, получивший REWORK или FAIL на пятом цикле,
переходит в `exhausted` и выпадает из прогона. Остальные срезы задачи продолжают цикл: срез,
не сошедшийся за пять доработок, - сигнал о нарезке или о ТЗ, и разбирается человеком
отдельно, а не остановкой всей задачи.

Разрез ТЗ на части номер цикла не увеличивает: `rework-3.part-01-of-02` и
`rework-3.part-02-of-02` - один цикл.

## Шаг 7 - Остановки

**Незакрытая основанием развилка останавливает прогон целиком.** Правило снятия развилки
основанием живёт во вложенных скилах и здесь не пересказывается: закрыть - значит найти уже
существующее основание, а не выбрать более удачный вариант. Не закрылось - вопрос человеку, и
до ответа вперёд не едет ни один срез задачи.

Останавливают прогон три исхода:

1. Сабагент spec-cycle вернул развилки или блокеры, которые не снялись основанием (Шаг 1).
2. Сабагент review-cycle вернул `ESCALATE`, не закрытый основанием (Шаг 5).
3. Сабагент реализации остановился на неустранимой развилке (Шаг 3, исход `fork`).

Причина одна на все три: развилка меняет скоуп не только своего среза. Срез, чьё ТЗ собрано
против состояния кода, которое зависит от невыбранного варианта, реализуется впустую, и это
видно только на ревью.

Формат выдачи человеку - тот же, что у вложенных скилов, по одному срезу за раз:

```
[ID среза] · [repo] — [источник развилки: ТЗ / реализация / приёмка]

## Развилка 1: [суть]
Контекст: [факты кода и реестра]
Что уже проверено: [что смотрели и почему не закрылось - строки листа «Развилки» (Р-N),
                   строки листа «Открытые вопросы» (ОВ-N), строки листа «ADR» (ADR-N),
                   строки листа «Контракты» (K-N), лист «Решения», статусы и файлы кода]

Вариант А: [описание]
  + [плюсы]
  − [риски]
Вариант Б: [...]
```

«Что уже проверено» - обязательная строка: она отделяет развилку, у которой основания нет, от
развилки, основание которой не нашли. Открытый ОВ - легальное основание остановиться и дальше
не ехать: это штатный исход, а не ненайденное основание.

Человек ответил в этом же диалоге - ответ записывается строкой листа «Развилки» в
`run/<задача>/forks.md` тем же форматом, что во вложенных скилах: двенадцать колонок
`ID | Дата | Уровень | Развилка | Контекст | Варианты | Принято | Обоснование | Последствия |
Что отвергнуто и почему | Основание | Статус`. Развилка, фиксирующая архитектурный выбор класса
решения, дополнительно поднимается строкой листа «ADR»: журнал реализацию не ограничивает, и
исполнителю извне ничто не запрещает сделать иначе. Строки вносит в файл проекта человек -
прогон в файл проекта не пишет. После ответа прогон продолжается с того же места по
`cycle.json`; перезапуск не нужен, `run/` сохранён.

`action: cascade` остановкой не является: срез, чей предшественник закрылся неуспешно,
записывается `--drop` с причиной «предшественник [ID] не закрыт», прогон идёт по остальным.

## Шаг 8 - Отчёт

`present_files` со всеми файлами ТЗ, отчётами ревью и планами прогона. Имена файлов ASCII -
карточка не отрисовывается для кириллицы в имени.

Сводка собирается из состояния, не из памяти о прогоне:

```
python3 scripts/cycle_state.py report --state run/<задача>/cycle.json
```

Формат в чат:

```
Задача [ID] — [название] · срезов [N]

[ID среза] · [org/repo] · [состояние] · циклов доработки [k] · [PASS/REWORK/FAIL по циклам] → [PR]
...

Закрыто PASS: n из N
Исчерпали потолок: [ID — на каком вердикте]
Выпали: [ID — причина]
Развилки человеку: [по каким срезам, сколько]
Ошибки нарезки: [находки вне репозитория среза; какой задаче нужен meeseeks-slice]
Новые тест-кейсы вне реестра: [сколько, по каким срезам — требуют внесения в лист «Тесткейсы»]
CI: [срезы, где CI красный после пяти попыток]

Проставить в файле проекта вручную:
  [ID среза] → [значение колонки «Статус» листа «Срезы»] ([PASS и смержен / PR открыт, цикл
               не сошёлся / выпал])
Долг человеку: [исходы прогона, под которые значения статуса на листе «Срезы» нет]
Дальше: [мерж / ответ на развилки / meeseeks-slice по задаче X]
```

Блок «Проставить вручную» обязателен: статусы срезов ведёт человек, и следующий прогон задачи
считает готовность по ним. Скил их не проставляет и за мерж не отчитывается: мержит человек.

Называются только фактические значения колонки «Статус» листа «Срезы»; сейчас на листе заведено
одно - `NeedSpec`. Значений под исходы прогона - смержен, PR открыт и цикл не сошёлся, выпал -
на листе нет. Скил их не выдумывает: недостающее значение идёт строкой «Долг человеку», и
статус по такому срезу человек заводит сам.

Строка про тест-кейсы обязательна, если ТЗ или отчёты ревью их содержат.

## Критические правила

- Единица прогона - задача, единица приёмки и счётчика - срез. Вердикта у задачи нет.
- Каждый вложенный скил исполняется отдельным сабагентом; ему передаются пути, идентификаторы
  и параметры шага, а не переписка прогона и не отчёты соседних сабагентов.
- Сабагент реализации получает одно ТЗ. Скоуп доработки уже сведён в нём.
- Оркестратор не пишет ТЗ, не правит код, не читает диффы и не выносит вердикт. Он считает
  порядок, ведёт состояние и передаёт пути.
- Порядок между срезами - `depends_in_task`: срез не начинает реализацию, пока каждый его
  предшественник внутри задачи не получил PASS. Порядок внутри среза - порядок частей ТЗ.
- Части одного среза идут одной веткой и одним PR; режим реализации приходит параметром, а не
  выводится сабагентом из заголовка ТЗ.
- Базовая ветка среза и ID его контракта приходят строкой листа «Срезы» и едут полями
  `base_branch` и `contract` через `spec-result.json` и `cycle.json` до сабагента. Клон, ветка
  `mode: new` и цель PR - от `base_branch`; молчаливый откат на дефолтную ветку - дефект.
- Хостинг репозитория берётся из колонки «Путь» листа «Репозитории»; способ создать PR или MR
  и прочитать прогон CI - тот, который есть у этого хостинга. В теле правил он не зашит.
- Один клон репозитория на прогон; два сабагента в одном рабочем дереве одновременно не
  работают.
- Потолок - пять циклов доработки на срез, счётчик по срезу. Первое ревью в потолок не входит.
  Исчерпавший срез выпадает, остальные продолжают.
- Потолок попыток CI внутри реализации и потолок циклов доработки - разные счётчики.
- Незакрытая основанием развилка останавливает прогон целиком, из любого шага.
- Вердикт сабагента - данность: не смягчается, не ужесточается, находки не дописываются.
- ТЗ прогона в inbox не коммитятся; планы собираются и остаются в `run/`.
- Номер цикла доработки считается по `tz-index.txt` прогона, а не по корню inbox.
- Состояние прогона ведёт `scripts/cycle_state.py`, руками не правится; `next` считает, что
  диспатчить, `record` записывает факт.
- Не мержит, не аппрувит, в файл проекта и в Google Drive не пишет, статусы срезов не
  проставляет.
