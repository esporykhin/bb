# Meeseeks Batch Testcases — пакетное заполнение реестра кейсов

## Место в методологии

Обёртка над `meeseeks-testcases`, не замена ему. Методология вывода кейсов, правила
свёртки, различимости и честности, словари уровня и типа, форма приёмочного кейса стори
и стоп-правила живут в `meeseeks-testcases` и здесь не дублируются. Этот скил отвечает
за три вещи: выборку и группировку задач, диспатч сабагентов, сведение результатов в
один патч.

Предыдущий шаг конвейера: `meeseeks-batch-decompose`. Следующий: `meeseeks-slice`,
а после нарезки на срезы - `meeseeks-spec`.

**Граница скила:** в файл проекта не пишет, в Google Drive не пишет, код не читает.
Патч применяет человек.

## Режим запуска

Cowork. Оркестратор — Fable 5, сабагенты — Opus 5.

Сабагент запускается инструментом Agent с параметром модели; промпт — содержимое
`agents/testcaser.md` с подставленными параметрами. Если параметр модели у инструмента
недоступен и сабагент унаследует модель оркестратора — **стоп**: сообщить человеку и не
запускать прогон.

Рабочая папка прогона — `run/` в папке проекта: `run/plan.json`, `run/state.json`,
`run/chains/<group_id>.json`. Она же даёт возобновляемость: прогон, прерванный на
середине, продолжается с непройденных цепочек, уже полученные результаты сабагентов не
перезапрашиваются.

## Единица диспатча — цепочка одной рамки поведения, не задача

Корень задачи — инициатива, ровно одна; стори лежит в колонке «Рамка поведения» листа
«Задачи». Цепочка прогона — все задачи с одной и той же рамкой поведения.

`meeseeks-testcases` работает по цепочке рамка→задачи→подзадачи: аудит покрытия и
приёмочный кейс стори — на всю цепочку (`аудит-покрытия`, `приёмочный-кейс-стори`). Две
задачи одной рамки поведения, отданные разным сабагентам, дают два аудита одной цепочки
и два приёмочных кейса.

Поэтому цепочка идёт одному сабагенту целиком, включая задачи рамки, не попавшие в
выборку по статусу: они дают контекст покрытия и определяют замыкающую задачу. В патч
статуса входят только выбранные.

Задача с пустой рамкой поведения — техническая: класс вычисляется по заполненности
рамки, правило уровня задачи принадлежит `meeseeks-backlog`. Такая задача обрабатывается
в одиночку, и приёмочного кейса стори у неё не бывает — это норма, а не деградация. В
отчёте такие задачи перечисляются отдельной строкой.

## Шаг 0 — Сверка файла проекта (блокирующий)

Сабагенты читают локальную копию файла проекта из папки проекта. Значит локальная копия
обязана совпадать с оригиналом до начала работы.

1. `get_file_metadata` по `fileId` файла проекта — зафиксировать `modifiedTime`.
   <!-- example:start -->
   `fileId = "1mgoml4Kv3NPSoZYbbjTht0Fsw1Q_4xB1I9qDZ4N6zQg"`
   <!-- example:end -->
2. `download_file_content` с `exportMimeType` = xlsx. Распаковка двухуровневая:

```python
inner = json.loads(result[0]["text"])
data = base64.b64decode(inner["content"])
```

3. Сверка по листам, которые читает генерация кейсов:

```
python scripts/check_sync.py --local <копия в папке проекта> --drive <выгрузка> \
    --sheets "Задачи,Подзадачи,Тесткейсы,Решения,Развилки,ADR,Контракты,Открытые вопросы,User Flow"
```

Лист, названный в `--sheets` и отсутствующий в книге, — код возврата 2 и **стоп**:
опечатка в имени листа иначе сводит сверку к пустому множеству и пропускает расхождение
молча.

Код возврата 1 — **стоп**. Показать человеку список расхождений, назвать `modifiedTime`
оригинала и спросить, обновить ли локальную копию. Ни одного сабагента до совпадения не
запускать: расхождение по листу «Тесткейсы» означает, что нумерация TC-ID пойдёт по
устаревшему реестру и кейсы столкнутся с уже существующими.

Байтовое сравнение здесь не работает — экспорт Google Sheets в xlsx не байт-стабилен.
Скрипт сравнивает нормализованный дамп ячеек.

**Локальная копия обязана быть выгрузкой из Drive как есть.** Колонка «Фаза» листа
«Задачи» — формула; openpyxl при сохранении кэшированные значения формул не переносит.
Локальную копию обновлять записью байтов выгрузки, не пересохранением.

## Шаг 1 — Выборка и группировка

```
python scripts/select_chains.py <project.xlsx> --out run/plan.json
```

Статус матчится литералом файла проекта: `ToDo` — декомпозированная задача. Литерал
совпадает с тем, который проставляет `meeseeks-batch-decompose` в колонку «Статус» при
выпуске патча.
Задач с таким статусом не найдено — скрипт печатает фактические значения колонки
«Статус» с частотами; сверить литерал с ними и передать нужный через `--status`,
не подставлять похожий молча.

Скрипт собирает цепочки по колонке «Рамка поведения», упорядочивает задачи внутри цепочки по
«Зависит от», определяет замыкающую задачу и считает для каждой задачи число подзадач и
уже существующих кейсов. Цепочки независимы, поэтому DAG между ними не строится: они
идут волнами по три сабагента.

Предупреждения плана обрабатываются до диспатча:

| Предупреждение | Действие |
|---|---|
| задача в выборке, подзадач нет | цепочка не диспатчится, парковка: статус противоречит реестру |
| замыкающая задача не определяется однозначно | диспатчится, `closing` = `null`, сабагент поднимет развилку |
| цикл в «Зависит от» внутри цепочки | назвать человеку, диспатчить |
| рамка поведения пуста | не предупреждение, а `note` плана: техническая задача, диспатчится в одиночку, приёмочного кейса стори не будет |

Показать человеку план до запуска: сколько задач, сколько цепочек, какие задачи идут в
одиночку.
Подтверждение не требуется, но план виден.

## Шаг 2 — Литерал следующего статуса

Задача, покрытая кейсами, меняет статус. Литерал берётся из файла проекта: значения
колонки «Статус» печатает `select_chains.py`. Если среди них однозначно опознаётся
статус следующего шага конвейера — использовать его. Если нет — спросить человека один
раз, до диспатча, и не изобретать значение.

Человек может ответить «статус не менять» — тогда `build_patch.py` запускается без
`--new-status`, лист «Задачи» не выпускается, патч состоит из кейсов и решений.

## Шаг 3 — Диспатч

На каждую цепочку волны — отдельный сабагент. В промпт подставляются: `group_id`,
`story`, `tasks_selected`, `chain`, `closing`, `project_file`, `output_path` =
`run/chains/<group_id>.json`, `resolutions` (пусто на первом заходе).

Оркестратор кейсы за сабагента не пишет, критерии готовности за него не разбирает. Его
дело — вход, выход и развилки.

## Шаг 4 — Разбор возврата

По `verdict` из `run/chains/<group_id>.json`:

| `verdict` | Действие |
|---|---|
| `covered` | Кейсы и аудит в `run/state.json`, задачи цепочки закрыты |
| `no_gaps` | Кейсов нет, задачи цепочки закрыты: покрытие полное — результат, не отказ |
| `forks` | Шаг 5 |
| `blocked` | Парковка: подзадачи из `return_to_decompose` идут в отчёт для возврата в `meeseeks-decompose` |
| `conflict` | Парковка: противоречие реестра отдаётся человеку |

Схема невалидна или файла нет — один повторный диспатч той же цепочки. Второй сбой —
парковка с пометкой «сабагент не вернул результат».

Кейсы к задачам цепочки, не попавшим в выборку, оркестратор оставляет в патче только
когда без них не закрывается приёмка стори. Остальные отбрасывает: прогон отвечает за
выбранные задачи.

## Шаг 5 — Закрытие развилок оркестратором

Оркестратор пробует закрыть развилку сам. **Закрыть — значит найти уже существующее
основание, а не выбрать более удачный вариант.** Допустимые основания, в порядке
проверки:

1. Строка листа «Решения» либо листа «Развилки», прямо закрывающая этот выбор.
2. Строка листа «ADR». Рамка связана с цепочкой, если существует правдоподобная
   реализация её задачи, нарушающая хотя бы один пункт колонки «Что этим запрещено».
   Совпадение термина, репозитория или задачи связыванием не считается.
3. Однозначный факт реестра файла проекта: критерий готовности соседней подзадачи,
   существующий кейс того же источника, «Рамка поведения» и «Рамка устройства» задачи,
   строка листа «Контракты», названная в колонке «Контракт».
4. Решение, принятое человеком внутри этого же прогона по другой цепочке.

Открытый вопрос листа «Открытые вопросы» (ОВ-N), накрывающий этот выбор, — легальное
основание остановиться: цепочка паркуется со ссылкой на ОВ-N, человеку развилка не
задаётся.

Код основанием не является и не читается — ни оркестратором, ни сабагентом: правило
`meeseeks-testcases` действует и на уровне прогона.

Ни одно основание не найдено — развилка идёт человеку. Правдоподобие, симметрия с
соседней цепочкой и предпочтение оркестратора основаниями не являются.

Каждая закрытая развилка записывается в `state.decisions` строкой листа «Развилки»:
дата прогона, уровень, формулировка развилки, контекст, варианты, принятый вариант,
обоснование, последствия, что отвергнуто и почему, основание со ссылкой (номер строки
«Решения», ID ADR, ОВ-N, ID подзадачи или кейса). Статус — `принято моделью` для
закрытой оркестратором, `принято` для решённой человеком. Основание, которое нельзя
назвать ссылкой, — не основание.

Короткая фиксация прогона без вариантов и без отвергнутого пишется строкой листа
«Решения» (`Дата | Решение | Обоснование | Статус`). Развилка с вариантами на лист
«Решения» не кладётся.

Все развилки цепочки закрыты — повторный диспатч (Шаг 6). Осталась хоть одна — парковка
цепочки целиком: частичное покрытие не выпускается.

## Шаг 6 — Повторный диспатч

Тот же сабагент-промпт, `resolutions` заполнен: формулировка развилки, принятый вариант,
источник. На цепочку приходится не больше двух диспатчей на раунд закрытия развилок.
Если после подстановки решений сабагент возвращает `forks` снова — парковка, новые
развилки идут человеку вместе со старыми.

## Шаг 7 — Вопрос человеку

Задаётся после того, как отработала текущая волна, не в момент возникновения. Волна
доходит до конца, дальше припаркованные цепочки волны предъявляются **по одной**: одна
цепочка — все её незакрытые развилки — ответ — следующая цепочка.

Формат по цепочке:

```
[group_id] — стори [ID] · задачи [ID через запятую]

## Развилка 1: [суть]
Контекст: [факты реестров]
Что уже проверено: [почему не закрылось само — какие решения, ADR и подзадачи смотрели]

Вариант А: [описание]
  + [плюсы]
  − [риски]
Вариант Б: […]
```

«Что уже проверено» — обязательная строка: она отделяет развилку, у которой основания
нет, от развилки, основание которой оркестратор не нашёл.

Ответ человека попадает в `state.decisions` тем же форматом, что и самостоятельно
закрытая развилка. Дальше — Шаг 6.

Человек может ответить «пропустить» — цепочка остаётся припаркованной и в патч не
входит.

Следующая волна начинается после того, как припаркованные цепочки текущей разобраны.

## Шаг 8 — Сводный патч

```
python scripts/build_patch.py --state run/state.json --source <project.xlsx> \
    --new-status <литерал из Шага 2> \
    --out /mnt/user-data/outputs/batch-testcases-patch.xlsx
```

Листы:

- **«Решения»** — короткие фиксации прогона без вариантов и отвергнутого. Строки новые,
  заливка зелёная `C6EFCE`.
- **«Развилки»** — все развилки прогона: закрытые оркестратором по основанию (статус
  `принято моделью`) и решённые человеком (статус `принято`). Двенадцать колонок листа,
  строки новые, заливка зелёная.
- **«Задачи»** — только покрытые задачи (`covered` и `no_gaps`), все двенадцать колонок
  листа, колонка «Статус» = литерал Шага 2. Строки изменённые, заливка жёлтая `FFEB9C`.
  Лист не выпускается, если `--new-status` не задан.
- **«Тесткейсы»** — строки прогона в порядке единицы бэклога и источника. Добавленные —
  зелёные, изменённые — жёлтые. Патчится по TC-ID, не по номеру строки. Колонка
  «Контракт» несёт ID контракта родительской подзадачи или задачи, иначе прочерк.

Припаркованные задачи ни в один лист не попадают: их статус остаётся `ToDo`, и следующий
прогон возьмёт их снова.

Имя файла ASCII — карточка `present_files` не отрисовывается для кириллицы в имени.

## Шаг 9 — Отчёт

```
Прогон: N задач, цепочек M, волн K
Покрыто: N₁ — [group_id: задачи], кейсов добавлено A, изменено B
Без пробелов: [group_id] — реестр уже полон
Развилок закрыто: N₂ (сам: n, человек: m)
Припарковано: [group_id — причина одной строкой]
Вернуть в декомпозицию: [подзадача — чего не хватает]
Технические задачи в одиночку: [ID — рамка поведения пуста]
Дальше: применить патч → meeseeks-slice по покрытым задачам
```

## Критические правила

- Расхождение локальной копии с Drive — стоп до запуска сабагентов, всегда.
- Литерал статуса матчится как есть. Не найден — показать фактические значения колонки
  и спросить, а не подставлять похожий.
- Цепочка одной рамки поведения не разрывается между сабагентами.
- Код не читается ни сабагентом, ни оркестратором.
- Сабагент — Opus, оркестратор — Fable. Не подтверждается модель сабагента — прогон не
  запускается.
- Оркестратор закрывает развилку только ссылкой на существующее основание.
- Частичное покрытие не выпускается: осталась незакрытая развилка — цепочка припаркована
  целиком.
- Оркестратор не пишет кейсы сам, даже последней оставшейся задаче, даже если она
  выглядит простой.
- Существующие строки реестра не переписываются молча (`meeseeks-testcases`): в этом
  прогоне `изменено` выпускается только по закрытой развилке о противоречии кейса и
  критерия.
- Патч один на прогон. Отдельные файлы по задачам не выпускаются.
- В файл проекта и в Google Drive скил не пишет.
