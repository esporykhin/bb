# Meeseeks Diagnose Cycle - от дампа до правки системы

## Место в методологии

Обёртка над `meeseeks-diagnose` и `meeseeks-harden`. Разбор дампа, спасение работы, три
взгляда и адресат правки - `meeseeks-diagnose`. Изменение системы, иерархия средств и цена
изменения - `meeseeks-harden`. Здесь эти правила не дублируются и не смягчаются.

Вход - один или несколько дампов `mrctl dump`. Выход - команды спасения, отчёты разбора,
предложения по системе, патчи по принятым предложениям, список развилок.

Порядок прогона: спасение считается первым и выдаётся человеку до диспатча сабагентов; каждый
дамп разбирается отдельным сабагентом; находки всех разборов сводятся в предложения одним
вызовом; предложения принимает человек, и только принятые идут в патчи.

Единица разбора - прогон. Единица предложения - класс отказов (правило `meeseeks-harden`). Из
десяти дампов может выйти два предложения, из одного - ни одного: количество предложений не
выводится из количества падений.

**Граница скила:** не применяет патчи, не коммитит, не пушит, не создаёт PR, в файл проекта и
в Google Drive не пишет, `mrctl salvage` не запускает. Команды спасения выдаёт - выполняет их
человек.

## Режим запуска

Cowork. **Оркестратор и все сабагенты - Opus 5.** Модель задаётся параметром `model`
инструмента Agent при каждом диспатче; поле `model` в шапке промпта сабагента дублирует то же
значение. У человека модель прогона не спрашивается и на слабую не понижается ни для одного
шага, включая разбор одного дампа.

Причина жёсткости: разбор на слабой модели даёт правдоподобный ответ вместо верного, а по
правдоподобному ответу правится не тот слой. Ошибка адресата дороже отказа: она тратит
цикл и оставляет механизм на месте.

Промпты сабагентов в `agents/`, скрипт в `scripts/`.

Рабочая папка прогона - `run/<ключ>/`, где ключ - дата прогона или имя задачи:

```
run/<ключ>/dumps/<id>.dump.md          входные дампы
run/<ключ>/<id>/facts.json             результат dump_facts.py
run/<ключ>/<id>/diagnose.md            отчёт разбора
run/<ключ>/<id>/findings.json          находки
run/<ключ>/salvage.md                  команды спасения по всем дампам
run/<ключ>/project.xlsx                снимок файла проекта
run/<ключ>/harden.md, proposals.json   предложения по системе
run/<ключ>/decisions.md                развилки, закрытые в прогоне
run/<ключ>/accepted.json               что человек принял
run/<ключ>/patches/<repo>-<ключ>.patch патчи
run/<ключ>/report.md                   сводка
```

Папка даёт возобновляемость: прогон, прерванный на середине, продолжается с дампов, у которых
нет `findings.json`. Уже полученные разборы не перезапрашиваются.

## Шаг 0 - Спасение, до всего остального

Считается оркестратором, без сабагентов, и выдаётся человеку сразу.

```
python3 scripts/dump_facts.py run/<ключ>/dumps/<id>.dump.md --out run/<ключ>/<id>/facts.json
```

Код возврата 2 - на входе не дамп: файл в прогон не идёт, остальные продолжаются.

Из `facts.json` берётся `salvage` с четырьмя исходами: `нечего спасать`, `спасено воркером`,
`спасать нечем`, `есть что спасать`. Только последний даёт команды.

Собрать `run/<ключ>/salvage.md` по всем дампам и **выдать его человеку до диспатча
сабагентов.** Срок жизни дерева упавшей задачи назван в `meeseeks-diagnose`; разбор, после
которого спасать уже нечего, бесполезен.

Оркестратор команды не выполняет. Состав команд спасения и правило «спасать нечего - одна
строка с причиной» - `meeseeks-diagnose`.

## Шаг 1 - Снимок файла проекта

Выгрузить файл проекта из Google Drive (`exportMimeType` = xlsx) в
`run/<ключ>/project.xlsx`. Снимок один на прогон: сводке предложений и закрытию развилок нужны
листы «Решения», «Развилки», «ADR», «Открытые вопросы», и они обязаны быть одними на прогон.

## Шаг 2 - Разбор дампов

На каждый дамп - отдельный сабагент по `agents/diagnoser.md` с `model` = Opus 5, не больше
трёх сразу. В промпт: `dump_path`, `facts_json`, `output_dir`.

Оркестратор в разбор не вмешивается: причину не переформулирует, находки не добавляет и не
снимает, адресата не меняет.

`findings.json` не появился или невалиден - один повторный диспатч того же дампа. Второй сбой
- дамп идёт в отчёт с пометкой «сабагент не вернул результат», в сводку предложений его
находки не идут.

## Шаг 3 - Свод в предложения

Один сабагент по `agents/hardener.md` с `model` = Opus 5, на всю пачку сразу. В промпт:
перечень `findings.json`, перечень `diagnose.md`, `project_file`, `output_dir`.

Один вызов, а не по вызову на разбор: группировка находок по механизму (`meeseeks-harden`)
возможна, только когда все находки перед глазами.

Предложение без заполненного `where` (репозиторий и файлы) в патч не идёт - сабагент обязан
отправить такое в `observations`. Оркестратор пустое `where` не достраивает.

## Шаг 4 - Развилки

Развилки из `proposals.json`, поле `forks`, оркестратор пробует закрыть сам. **Закрыть -
значит найти уже существующее основание, а не выбрать более удачный вариант.** Допустимые
основания, в порядке проверки:

1. Строка листа «Решения» снимка, прямо закрывающая этот выбор.
2. Строка листа «Развилки» снимка (Р-N), закрывающая этот же выбор. Статус `принято моделью`
   основанием считается и прогон не блокирует.
3. ADR - строка листа «ADR» снимка `project.xlsx`; рамка закрывает развилку, если предложение
   нарушает её «Что этим запрещено».
4. Однозначный факт кода: вариант описывает механизм, которого в коде нет, либо противоречит
   существующему контракту. Читается через MCP того хостинга, который назван для этого
   репозитория на листе «Репозитории» снимка.
5. Решение, принятое человеком внутри этого же прогона.

Хостинги прогона cnplug: предмет разработки - GitLab MCP, репозитории воркера и инбокса -
GitHub MCP, снимок master - Forgejo MCP.

Правдоподобие и предпочтение оркестратора основаниями не являются.

Предмет предложения висит открытым вопросом на листе «Открытые вопросы» - предложение выпадает
из прогона с указанием ОВ-N. Это штатный исход, а не ненайденное основание: открытый ОВ есть
законный повод остановиться.

Каждая закрытая развилка пишется в `run/<ключ>/decisions.md` строкой листа «Развилки»:
`ID | Дата | Уровень | Развилка | Контекст | Варианты | Принято | Обоснование | Последствия |
Что отвергнуто и почему | Основание | Статус`; в «Основание» - ссылка на источник закрытия,
статус - `принято моделью`. Лист «Решения» остаётся для коротких фиксаций и строкой развилки
не заполняется.

**Развилка класса «предложение отменяет принятое решение» оркестратором не закрывается
никогда** - она идёт человеку. Отмена принятого решения делается человеком, а не выводится
из падения.

Незакрытая развилка - соответствующее предложение выпадает из прогона, остальные
продолжаются. Формат выдачи - по одной развилке за раз:

```
Предложение [id] — развилка

## Суть: [формулировка]
Контекст: [факты кода и реестра]
Что уже проверено: [какие решения, ADR и файлы смотрели и почему не закрылось]

Вариант А: [описание]
  + [плюсы]
  − [риски]
Вариант Б: […]
```

«Что уже проверено» обязательно: оно отделяет развилку без основания от развилки, основание
которой оркестратор не нашёл.

## Шаг 5 - Приём предложений человеком

**Обязательная остановка прогона.** Патчи собираются только по предложениям, которые человек
принял явно.

Изменение системы меняет поведение всех будущих прогонов очереди. Автоматически принятое
предложение означает, что контур правит сам себя по итогам собственного падения, без внешней
проверки - в этом контуре человек и есть внешняя проверка.

Выдать список: `id`, класс, уровень, слой, суть, цена, наблюдений. Ответ человека записать в
`run/<ключ>/accepted.json`. Принятых нет - прогон завершается на Шаге 7 со сводкой без
патчей; это штатный исход, а не сбой.

## Шаг 6 - Патчи

Принятые предложения сгруппировать по `where.repo`. На каждый репозиторий - отдельный
сабагент по `agents/patcher.md` с `model` = Opus 5, не больше двух сразу. В промпт: `repo`,
предложения этого репозитория, `proposals_json`, `output_dir`.

Один репозиторий - один патч. Смешивать репозитории в один файл нельзя: патчи применяются в
разные деревья.

`status: halted` - развилка реализации: идёт человеку тем же форматом, что Шаг 4, патч по
этому репозиторию не собирается. `status: failed` - патч не прошёл проверки: в отчёт с
причиной, оркестратор его не чинит и не отдаёт.

Оркестратор патчи не применяет и не сводит. Порядок применения называет: сначала репозиторий
воркера, потом остальные - правка контура должна встать раньше правок, которые на неё
опираются.

## Шаг 7 - Сводка

`run/<ключ>/report.md`:

```markdown
# Разбор падений [ключ]

## Спасение
[таблица: прогон — состояние — команды или причина]

## Разобрано
[таблица: прогон — rc — пометка — причина одной фразой — адресат]

## Предложения
[таблица: id — класс — уровень — слой — наблюдений — принято/отклонено/развилка]

## Патчи
[таблица: репозиторий — база sha — файлы — что проверено — что нет]
Порядок применения: [перечень]

## Развилки для человека
[по одной, полным форматом]

## Не разобрано
[дампы, по которым сабагент не вернул результат, и почему]
```

Файлы отдать через `present_files`: первым `salvage.md`, затем патчи, затем `report.md`.
В чат коротко: состояние спасения, число предложений, число патчей, число развилок.

## Критические правила

- **Оркестратор и все сабагенты - Opus 5.** Модель не понижается ни на одном шаге и у
  человека не спрашивается.
- Спасение считается до диспатча сабагентов и выдаётся первым: позже спасать бывает уже
  нечего.
- Что выдаётся в командах спасения и когда - правило `meeseeks-diagnose`.
- Оркестратор `mrctl` не запускает, патчи не применяет, в файл проекта не пишет.
- Свод предложений - один вызов на всю пачку разборов, не по вызову на дамп.
- Предложение без `where` в патч не идёт и оркестратором не достраивается.
- Развилка закрывается только ссылкой на существующее основание; отмена принятого решения не
  закрывается оркестратором никогда.
- Приём предложений человеком обязателен. Без него патчи не собираются.
- Один репозиторий - один патч. Порядок применения называется.
- Прогон возобновляем по `run/<ключ>/`: дампы с `findings.json` не переразбираются.
