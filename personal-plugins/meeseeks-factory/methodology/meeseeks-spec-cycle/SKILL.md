# Meeseeks Spec Cycle - от задачи до задания очереди

## Единица прогона

Единица прогона - задача. **Один прогон - одна задача - одно задание.** Класс и основание
задачи - см. `meeseeks-backlog`; граница среза и правило поставки - см. `meeseeks-slice`.
Срезы задачи лежат на листе «Срезы» и связаны с ней колонкой «Родитель».

Модель прогона:

1. **Срезы задачи могут зависеть друг от друга.** Порядок между ними выражают рёбра
   `depends_on` задания: вершина берётся в работу, только когда предшественник прошёл успешно.
2. **Два среза одного репозитория в одной задаче допустимы.** Очередь воркера на репозиторий
   одна, рёбра её сериализуют.
3. **Внешние зависимости - на операторе.** Зависимость от срезов других задач прогон не
   останавливает и в задание не попадает.

Порядок прогона: состав задачи (Шаг 1) - диспатч сабагента на каждый срез (Шаг 3) -
маршрутизация по `outcome` (Шаг 4) - снятие блокера основанием (Шаг 5) - файлы ТЗ (Шаг 6) -
граф публикации (Шаг 6а) - сборка задания (Шаг 7) - отчёт (Шаг 8).

Разрез ТЗ на части этому не противоречит: части одного среза идут последовательно по одной
ветке и в один PR; правило разреза - `meeseeks-spec`.

## Место в методологии

Обёртка над `meeseeks-triage` и `meeseeks-spec`. Правила триажа, источники ТЗ, порог
развилки, потолок бюджета, правила разреза на части и формат выдачи живут в них. Здесь они
не дублируются и не смягчаются.

Этот скил отвечает за: один снимок реестра на прогон, состав задачи, нарезку задачи на срезы
вызовом `meeseeks-slice`, диспатч сабагента на каждый срез, снятие блокера по уже
существующему основанию, сборку графа публикации, сборку одного JSON-задания для очереди,
передачу результата.

Вход - ID задачи либо перечень ID срезов. Выход - один файл задания
`<задача>.task.json` в `/mnt/user-data/outputs/`, маленькие ТЗ отдельными файлами там же,
большое ТЗ по каждому срезу человеку файлом, плюс список того, что закрыть по срезам,
которые из прогона выпали.

**Граница скила:** промпт реализации не собирает, код не правит, в файл проекта и в Google
Drive не пишет, статусы срезов не проставляет, задание в очередь **не подаёт** - подаёт
человек командой `tfc submit`. В git ничего не пушит.

## Режим запуска

Cowork. Сабагенты - Opus, промпт в `agents/slice-specer.md`, по одному на срез.

Модель сабагента не пиннится инструментом Agent - сказать это человеку и спросить, запускать
ли на модели оркестратора. ТЗ, собранное на слабой модели, проходит дальше молча и всплывает
только на ревью реализации.

Рабочая папка прогона - `run/<задача>/`:

```
run/<задача>/project.xlsx           снимок файла проекта
run/<задача>/task.json              состав задачи и её срезов
run/<задача>/<срез>/context.json    контекст среза
run/<задача>/<срез>/triage.md       отчёт триажа
run/<задача>/<срез>/tz-big.md       большое ТЗ среза, в задание не едет
run/<задача>/<срез>/spec.json       результат сабагента
run/<задача>/<срез>/resolutions.md  блокеры, закрытые оркестратором
run/<задача>/decisions.md           решения прогона строками листа «Решения»
run/<задача>/<задача>.plan.yml      граф публикации
run/<задача>/<задача>.task.json     задание очереди - выход прогона
```

Папка даёт возобновляемость: прогон, прерванный на середине, продолжается со срезов, у
которых нет `spec.json`. Уже собранные ТЗ не пересобираются.

## Шаг 0 - Снимок файла проекта

Выгрузить файл проекта из Google Drive (`fileId` файла проекта, `exportMimeType` = xlsx) и
распаковать:

<!-- example:start -->
`fileId = 1mgoml4Kv3NPSoZYbbjTht0Fsw1Q_4xB1I9qDZ4N6zQg`
<!-- example:end -->

```
python scripts/save_project.py <результат MCP> run/<задача>/project.xlsx
```

Снимок один на прогон, и сабагентам передаётся его путь. Если каждый выгружает файл сам,
триаж и ТЗ разных срезов могут увидеть разные состояния реестра, и расхождение всплывёт уже
в готовом ТЗ.

## Шаг 1 - Состав задачи

```
python scripts/task.py run/<задача>/project.xlsx --task <ID задачи> \
  --out run/<задача>/task.json
```

Перечень срезов вместо ID задачи - `--slices <ID среза>[,<ID среза>…]`; ID задачи скрипт
выводит по колонке «Родитель». Срезы разных задач одним прогоном не идут: задание собирается
на одну задачу.

<!-- example:start -->
`--slices CI-9-S1,AS-4-S1`
<!-- example:end -->

Коды возврата: `0` - состав собран, `2` - задачи или среза с таким ID нет.

Оркестратору из состава нужны три вещи: `sliced` (нарезана ли задача, Шаг 1а), `composition`
(по каким срезам идёт диспатч) и `depends_in_task` каждого среза (из него строятся рёбра
графа на Шаге 6а).

## Шаг 1а - Нарезка задачи на срезы

`sliced: false` - задача в реестре есть, срезов у неё нет. Нарезка делается сабагентом со
скилом `meeseeks-slice` (`/mnt/skills/user/meeseeks-slice/SKILL.md`) на ID задачи, до
диспатча по срезам. Сабагент возвращает патч листов «Срезы» и «Тесткейсы».

Строки листов вносит человек: скил в файл проекта не пишет. Патч отдаётся человеку, прогон
ждёт. Строки внесены - снимок пересобирается Шагом 0, `task.py` вызывается заново, и
`sliced: true` открывает Шаг 2.

Сабагент вернул развилки вместо срезов - нарезки нет, прогон останавливается: развилки идут
человеку форматом Шага 5.

`sliced: true` - шаг пропускается, срезы задачи уже нарезаны.

## Шаг 2 - Контекст срезов

По каждому срезу задачи:

```
python scripts/slice_context.py run/<задача>/project.xlsx <срез> \
  --out run/<задача>/<срез>/context.json
```

Код возврата 2 - среза нет на листе; это уже отловлено Шагом 1, здесь - страховка.

Оркестратор смотрит три поля и дальше не вмешивается: `repo_in_registry` (репозитория нет в
реестре - сабагент разберёт это по правилу Шага 3 `meeseeks-spec`), `status` (срез уже не в
`NeedSpec` - ТЗ по нему существует; спросить человека, пересобирать ли, до
диспатча) и `base_branch` (базовая ветка среза; идёт сабагенту и полем `base` вершины
задания на Шаге 7).

`base_branch` равен `null` - базовая ветка из ячейки «Репозиторий» не распозналась. Это стоп
по срезу и вопрос человеку с сырым значением ячейки (поле `repo_raw`): молчаливого отката на
ветку по умолчанию репозитория нет.

Скрипт кладёт в контекст ещё два перечня, которые читает сабагент: `contracts` - записи листа
«Контракты» по идентификаторам из колонки «Контракт» среза и его задачи, и
`forks_mentioning_id` / `open_questions_mentioning_id` - строки листов «Развилки» и «Открытые
вопросы» с упоминанием ID среза или задачи.

## Шаг 3 - Диспатч сабагентов

На каждый срез - отдельный сабагент по `agents/slice-specer.md`, не больше трёх сразу.
В промпт подставляются: `slice_id`, путь снимка, путь `context.json`, `base_branch` из
`context.json`, `output_dir`.

К промпту сабагента добавляются три требования - без них задание собрать нельзя:

1. В `spec.json` по каждой части вернуть `tc_ids` - идентификаторы тест-кейсов **этой**
   части, те же, что стоят в разделе «Скоуп части» её текста.
2. В `spec.json` по каждой части вернуть `gate_removes` - перечень идентификаторов тестов,
   которые часть удаляет, переименовывает или переписывает, по каждому гейту направления
   `grew` (обычно `tests` и `inventory`). Идентификаторы снимаются с текущего HEAD ветки
   командой `pytest --collect-only -q` по затронутым файлам, а не выдумываются. Ничего не
   удаляется - пустой перечень. Почему это обязательно - см. Шаг 7.
3. Разделы «Изменения по слоям» и «Антискоуп» писать **плоским перечнем** по правилу
   `meeseeks-spec`, без подзаголовков внутри раздела.

Сабагент выполняет `meeseeks-triage` и `meeseeks-spec` по их инструкциям и возвращает
`triage.md`, `tz-big.md` и `spec.json`. Оркестратор в сборку ТЗ не вмешивается: код не
читает, план изменений не правит, оценку и разрез на части не пересматривает.

`spec.json` не появился или невалиден - один повторный диспатч того же среза. Второй сбой -
срез идёт в отчёт с пометкой «сабагент не вернул результат», ТЗ по нему не собирается.

## Шаг 4 - Маршрутизация по результату среза

Маршрут считается по полю `outcome`, не по впечатлению от текста.

| `outcome` | Что означает | Действие |
|---|---|---|
| `spec` | ТЗ собрано: один файл либо упорядоченные части | Шаг 6 |
| `not_ready` | триаж дал НЕ ГОТОВ: блокеры | Шаг 5 |
| `forks` | развилки на шаге ТЗ | Шаг 5 |
| `failed` | сабагент не вернул результат | отчёт, ТЗ нет |

Исхода `over_budget` больше нет: объём сверх потолка закрывается разрезом на части внутри
`meeseeks-spec`, а не возвратом в `meeseeks-slice`. Сабагент, вернувший `over_budget`,
работает по устаревшей инструкции - это строка в отчёт и повторный диспатч.

**Срез, вставший на блокере, развилке или сбое сабагента, выпадает из прогона; остальные
срезы прогона продолжаются.** Вершин в задании у него нет. Срезы, у которых выпавший стоит в
`depends_in_task`, называются в отчёте отдельной строкой: их ТЗ собрано против состояния
кода, которого в этом задании не будет.

## Шаг 5 - Снятие блокера и развилки основанием

Оркестратор пробует закрыть сам. **Закрыть - значит найти уже существующее основание, а не
выбрать более удачный вариант.** Допустимые основания, в порядке проверки:

1. Строка листа «Решения» снимка со статусом «принято», прямо закрывающая этот вопрос.
2. Строка листа «ADR» снимка, состояние `действует`.
3. Строка листа «Развилки» снимка, прямо закрывающая этот вопрос. Статус `принято моделью`
   основанием является: он не блокирует.
4. Строка листа «Открытые вопросы» снимка со статусом «закрыт» и заполненной колонкой
   «Чем закрыт».
5. Статус блокирующего среза в снимке - `Done`.
6. Однозначный факт кода через MCP того хостинга, который назван в реестре «Репозитории»:
   механизм уже реализован либо описанный вариант противоречит действующему контракту.
7. Решение, принятое человеком внутри этого же прогона по другому срезу.

Правдоподобие, симметрия с соседним срезом и предпочтение оркестратора основаниями не
являются.

Открытый вопрос по существу блокера - строка листа «Открытые вопросы» со статусом `открыт`
или `частично закрыт` - основанием не является и снимает вопрос в обратную сторону: блокер
не закрывается, срез выпадает из прогона, в отчёте называется ОВ-N и адресат из колонки
«Кому адресован». Это штатный исход, а не ненайденное основание.

Каждый снятый блокер пишется в `run/<задача>/decisions.md` строкой листа «Решения»: дата
прогона, формулировка, обоснование со ссылкой на источник (номер строки «Решения», ID записи
листа «ADR», «Развилки» или «Открытые вопросы», путь к файлу кода), статус `принято`. Основание, которое нельзя назвать ссылкой, - не
основание. Копия относящихся к срезу строк кладётся в `run/<задача>/<срез>/resolutions.md`.

Все блокеры среза сняты - повторный диспатч **этого среза** с путём `resolutions.md` в
промпте. Прогон целиком не перезапускается.

Остался хотя бы один - срез выпадает из прогона. Формат выдачи человеку, по одному срезу:

```
[ID среза] — [org/repo] — [outcome]

## Развилка 1: [суть]
Контекст: [факты кода и реестра]
Что уже проверено: [какие решения, ADR, статусы и файлы смотрели и почему не закрылось]

Вариант А: [описание]
  + [плюсы]
  − [риски]
Вариант Б: [...]
```

«Что уже проверено» - обязательная строка: она отделяет развилку, у которой основания нет,
от развилки, основание которой не нашли.

Человек ответил в этом же диалоге - ответ пишется в `decisions.md` тем же форматом, срез
переводится в повторный диспатч, прогон продолжается. Перезапуск не нужен, `run/` сохранён.

## Шаг 6 - Файлы ТЗ и их порядок

Сабагент возвращает по срезу большое ТЗ и набор маленьких. Большое ТЗ - рабочий документ
прогона: остаётся в `run/<задача>/<срез>/tz-big.md`, в задание не идёт, отдаётся человеку
через `present_files` на Шаге 8. Телами вершин задания идут только маленькие ТЗ.

Текст маленького ТЗ сабагент пишет черновиком в `output_dir`, файлы создаёт скриптом
`new_tz.py` - по вызову на часть. Имя и идентификатор части скрипт считает до написания тела:
`part_id` идёт внутрь текста ТЗ трейлером коммита, `prev_part_id` - в предусловие.

```
python3 /mnt/skills/user/meeseeks-spec-cycle/scripts/new_tz.py \
  --env <окружение или org/repo> \
  --task <ID среза> \
  [--part <N> --parts <M>] \
  [--note <пометка>] \
  --body run/<задача>/<срез>/tz-part-N.md \
  --json
```

Поля:

- `--env` - окружение из списка скрипта. Принимает и `org/repo`, приводя его к имени
  окружения. Окружения нет в списке - стоп, вопрос человеку; новое окружение заводится
  человеком, скрипт и скил его не придумывают. **Список живёт в `scripts/envs.txt` и
  заполняется человеком до прогона**: окружение предмета разработки обязано стоять там
  раньше, чем прогон дошёл до этого шага, иначе прогон встанет здесь по каждому срезу. **Это же имя идёт полем `repo` вершины
  задания на Шаге 7 и обязано совпадать с именем записи репозитория в контуре**: не
  совпало - очередь отвергнет весь вызов кодом `intake-unknown-repo`.
- `--task` - **ID среза**, не задачи. Точка в ID недопустима (разделитель сегментов имени),
  дефис допустим; ID переводится в нижний регистр.
- `--part`/`--parts` - задаются вместе и только при разрезе по бюджету. Имя выходит вида
  `<окружение>.<id среза>.part-NN-of-MM.tz.md`; номер дополнен нулём слева.

<!-- example:start -->
`nikell28/artifacts-service` приводится к `artifacts_service`; `CI-9-S1` передаётся как
`ci-9-s1`; имя части выходит `mr_meeseeks.ci-9-s1.part-02-of-03.tz.md`.
<!-- example:end -->
- `--note` - свободная пометка. Для первичного ТЗ не задаётся. Имя уже занято - `--note v2`;
  молчаливой перезаписи нет. Пометка `rework-N` принадлежит `meeseeks-fix-spec`.
- `--body` - файл с телом части или `-` для stdin.

Скрипт отказывается создать часть N, пока в outputs нет файла части N−1: пропуск ломает
цепочку предусловий и обнаруживается только сгоревшим слотом воркера.

**Порядок исполнения задают рёбра задания.** Очередь берёт вершину в работу, только когда
предшественник прошёл успешно.

Трейлер `Meeseeks-Part` и секция «Предусловие» остаются второй линией: часть, чьё предусловие
не выполнено, останавливается сама и не коммитит ничего - механика проверки живёт в шаблоне
промпта воркера.

## Шаг 6а - Граф публикации

Вершины графа - маленькие ТЗ, рёбра - порядок между ними. Граф собирает скрипт:

```
python scripts/new_plan.py --task <ID задачи> --title "<единица бэклога>" \
  --tz <имя файла ТЗ> \
  --tz <имя файла ТЗ>[:needs=<id или имя файла>[,...]] \
  --out run/<задача>/<задача в нижнем регистре>.plan.yml
```

- `--tz` - по вызову на маленькое ТЗ, в порядке публикации. Имена берутся из `inbox_paths`
  каждого `spec.json`, порядок частей внутри среза - порядок массива.
- Части одного среза скрипт связывает линейно сам. `needs` задаётся только между срезами.
- Рёбра между срезами - `depends_in_task` из `task.json`: это колонка «Зависит от» листа
  «Срезы», отфильтрованная по составу задачи. Зависимость от срезов других задач в граф не
  идёт. Ссылка ставится на последнюю часть среза-предшественника.
- Идентификатор вершины считает скрипт, руками не собирается. Он же идёт полем `local_ref`
  вершины задания на Шаге 7.
- `--title` - «Единица бэклога» задачи из `task.json`; не задан - в граф идёт ID задачи.
- Имя файла - `<задача в нижнем регистре>.plan.yml`. Скрипт сверяет его с ID задачи и
  отказывает на чужом: иначе второй прогон затрёт первый.

Коды возврата: `0` - граф собран, `2` - вход отвергнут: цикл в зависимостях, ссылка на
несуществующий `id`, имя без суффикса `.tz.md`, повтор файла, части не по порядку. Код 2 -
стоп, вход правится; граф руками не пишется.

`plan.yml` - рабочий файл прогона: он даёт вершины, рёбра и их порядок. В очередь едет не он,
а задание Шага 7.

Один прогон - один граф. Срез, выпавший на Шаге 5, вершин в нём не имеет.

## Шаг 7 - Сборка задания очереди

Выход прогона - **один файл** `run/<задача>/<задача в нижнем регистре>.task.json`, копия в
`/mnt/user-data/outputs/`. Формат - `schemas/intake/task.schema.json` контура: тело
`POST /intake`, оно же вход `tfc submit`. Все вершины и рёбра принимаются одной транзакцией:
либо всё, либо ничего.

Каркас:

```json
{
  "version": 1,
  "nodes": [ { … }, { … } ]
}
```

Одна вершина - один файл маленького ТЗ, то есть одна вершина графа Шага 6а. Поля вершины:

| Поле | Откуда | Правило |
|---|---|---|
| `local_ref` | идентификатор вершины графа (`s1-p1`) | уникален в вызове; только `A-Za-z0-9_.-` |
| `repo` | первый сегмент имени файла ТЗ, он же `--env` Шага 6 | имя записи репозитория в контуре, не `org/repo` |
| `branch` | трейлер `Meeseeks-Branch` шапки ТЗ | **одна ветка на срез**: у всех частей среза она одна |
| `base` | `base_branch` из `context.json` среза | базовая ветка среза; поле `null` - стоп, вопрос человеку |
| `task_id` | ID задачи | одинаков у всех вершин прогона |
| `task_ref` | `part_id` при разрезе, иначе ID среза | внешний идентификатор задания |
| `spec` | **текст файла ТЗ целиком** | не путь и не выдержка: тело едет внутрь задания |
| `tc_ids` | `tc_ids` части из `spec.json` | только свои кейсы части |
| `gate_removes` | `gate_removes` части из `spec.json` | перечень пуст - поле не кладётся |
| `depends_on` | `needs` вершины графа | `[{"local_ref": "<id>"}]`, ссылка внутри этого же вызова |

**Почему `gate_removes` обязателен.** Гейты направления `grew` (`tests`, `inventory`) считают
регрессией **исчезновение** ключа, а не только появление красного. Часть, которая
переписывает, переименовывает или удаляет существующий тест, убирает его идентификаторы - и
цикл гейтов начинает требовать вернуть то, что ТЗ удалило намеренно. Починить это цикл не
может: он выгорает по потолку итераций, каждый раз откатывая дерево. Санкция снимает вопрос.
Особо: у параметризованного теста идентификатор несёт значения параметров, поэтому правка
ожидаемого значения тоже меняет идентификатор - санкция нужна и там.

**Проверки до выдачи файла.** Не прошла хоть одна - стоп, файл не отдаётся:

1. `json.load` проходит; `version` равен 1; `nodes` непуст.
2. У каждой вершины есть все обязательные поля: `local_ref`, `repo`, `branch`, `task_id`,
   `task_ref`, `spec`, `tc_ids`.
3. `local_ref` уникальны; каждый `depends_on` ссылается на `local_ref` этого же вызова.
4. Все части одного среза несут одну `branch` и идут связанной цепочкой `depends_on`.
5. `spec` каждой вершины непуст и начинается с заголовка ТЗ, а не с пути к файлу.
6. **Скоуп разбирается непустым.** По тексту `spec` каждой вершины пройти правилом разбора
   и убедиться, что оба перечня непусты и содержат ровно те пути, что названы в ТЗ:

   > Раздел ищется по заголовку любого уровня, содержащему «изменения по слоям» либо
   > «антискоуп», и кончается **следующим заголовком любого уровня**. Элементы перечня -
   > строки, начинающиеся с `-` или `*`. Из элемента берётся текст до первого пробела,
   > двоеточия или запятой, с которого сняты обратные кавычки.

   Подзаголовок внутри раздела обрезает его до вступительной прозы, и перечень выходит
   пустым. Пустой перечень не равен отсутствующему: контур считает вне перечня **каждый**
   файл, отказ по гейтам получает класс «прогон» вместо «задача», а шаг правки находок
   остаётся без разрешённых файлов. Перечень пуст - вернуть срез на пересборку ТЗ, а не
   править текст за сабагента.

Задание в очередь скил **не подаёт**. Файл отдаётся человеку, команда подачи называется в
отчёте.

Ни одного собранного ТЗ - задания нет вовсе, файл не создаётся.

## Шаг 8 - Отчёт

`present_files` с файлом задания, всеми маленькими ТЗ и большим ТЗ каждого среза. Имена
файлов ASCII - карточка не отрисовывается для кириллицы в имени.

Сводка в чат:

```
Задача [ID] — срезов [N], репозиториев [K]

[ID среза] · [репозиторий] · [триаж ГОТОВ/НЕ ГОТОВ] · [outcome] · [оценка: сумма / по частям] → [файлы ТЗ / что закрыть]
...

Собрано ТЗ: n из N, файлов [M] (частей: [срез — k, срез — k])
Выпало из прогона: [ID — причина]
Блокеров снято основанием: n [источник по каждому] · открыто: m
Задание: [имя файла], вершин [V], рёбер [E], веток [B]
Санкции gate_removes: [срез — сколько ключей] / нет
Новые тест-кейсы вне реестра: [сколько, по каким срезам — требуют внесения в лист «Тесткейсы»]

Подать в очередь: tfc submit [имя файла]

Проставить в файле проекта вручную:
  [ID среза] → значение «ТЗ собрано»   (значения под этот исход на листе «Срезы» сегодня нет - долг человеку)
Дальше: [ответ на развилки]
```

Блок «Проставить вручную» обязателен: статусы срезов ведёт человек, и следующий прогон задачи
считает готовность по ним. Скил их не проставляет.

Строка про тест-кейсы обязательна, если ТЗ их содержит. Строка про санкции обязательна
всегда: пустые санкции там, где ТЗ правит существующие тесты, - самая дорогая ошибка задания.

Срез, разрезанный больше чем на шесть частей, называется в отчёте отдельной строкой: это
сигнал, что нарезка крупная. Прогон при этом не останавливается, перенарезка - решение
человека и отдельный вызов `meeseeks-slice`.

## Критические правила

- Состав задачи собирается скриптом до диспатча: срезы задачи могут зависеть друг от друга и
  порядок между ними выражают рёбра задания, два среза одной репы в задаче допустимы, внешние
  зависимости - на операторе.
- Один снимок файла проекта на прогон; сабагенты его не перевыгружают.
- Один срез - один сабагент - одно ТЗ. ТЗ может состоять из нескольких файлов-частей одного
  среза; срезом от этого оно быть не перестаёт. Правило поставки среза - `meeseeks-slice`.
- Потолок части живёт в `tz_budget.py --limits` и нигде больше. Оценку и разрез делает
  `meeseeks-spec`; оркестратор их не пересматривает и потолок не поднимает.
- Блокер и развилка снимаются только ссылкой на существующее основание; выбор между
  вариантами без основания - человеку.
- Срез, вставший на блокере или развилке, выпадает из прогона; остальные срезы прогона
  продолжаются.
- Большое ТЗ в задание не едет: оно рабочий документ прогона и отдаётся человеку файлом.
  Телами вершин идут маленькие ТЗ целиком.
- ТЗ, не отвечающее формату `meeseeks-spec`, в задание не кладётся.
- Имя файла ТЗ и `part_id` собирает `scripts/new_tz.py`, руками не собираются; в `--task`
  идёт ID среза, номер части - пара `--part`/`--parts`.
- Одна ветка на срез: все части среза несут одну `branch` и собираются в один PR. Ветка
  берётся из трейлера `Meeseeks-Branch` шапки ТЗ, а не сочиняется на месте.
- `base` вершины берётся полем `base_branch` из `context.json` среза. Молчаливого отката на
  ветку по умолчанию репозитория нет: `base_branch` не распознан - стоп, вопрос человеку.
  Где базовая ветка живёт в строке среза - см. `meeseeks-slice`.
- Один прогон - один граф и одно задание. Граф собирает `scripts/new_plan.py`, руками не
  пишется. Рёбра между срезами - только `depends_in_task`, зависимости от срезов других
  задач в задание не идут.
- `gate_removes` собирается по факту `pytest --collect-only`, а не по памяти. Часть правит
  существующий тест - санкция обязательна.
- Задание не отдаётся, пока разбор скоупа по тексту каждой вершины не дал непустой перечень.
- Окружение берётся из `scripts/envs.txt` и обязано совпадать с именем записи репозитория в
  контуре; неизвестное окружение - стоп, вопрос человеку. Файл заполняет человек до прогона,
  скил в него не дописывает.
- В git ничего не пушится, задание в очередь не подаётся: подаёт человек.
- Промпт реализации в этом прогоне не собирается.
- В файл проекта и в Google Drive не пишет, статусы срезов не проставляет, код не правит.
