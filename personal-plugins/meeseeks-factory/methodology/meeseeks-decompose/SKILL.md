# Meeseeks Decompose — нарезка задачи на подзадачи

## Место в методологии

`meeseeks-triage` → **`meeseeks-decompose`** → `meeseeks-testcases` → `meeseeks-slice` →
`meeseeks-spec` → Codex → `meeseeks-review`.

Подзадача — логическая единица и единица приёмки: отдельно не мержится и обязана иметь
собственный проверяемый критерий готовности (см. «Критерий готовности подзадачи»). Единица
исполнения и поставки — срез: один срез = одна ветка = один PR (граница среза —
`meeseeks-slice`, `граница-среза`). Тест-кейс выводится из критерия готовности подзадачи
скилом `meeseeks-testcases` (`вывод-тест-кейса`).

**Граница скила:** режет и заполняет строки листа «Подзадачи». Не пишет тест-кейсы, не
пишет ТЗ.

## Источники

1. **Файл проекта** — таблица проекта в Google Drive. Выгружать через
   `download_file_content` с `exportMimeType` на xlsx, разбирать `openpyxl`
   с `data_only=True`. Листы: «Задачи», «Подзадачи», «ADR», «Контракты», «Решения»,
   «Развилки», «Открытые вопросы», «Репозитории».
   <!-- example:start -->
   `fileId = "1mgoml4Kv3NPSoZYbbjTht0Fsw1Q_4xB1I9qDZ4N6zQg"`
   <!-- example:end -->
2. **Код репозитория** — через MCP того хостинга, который назван в строке листа
   «Репозитории» для этого репозитория (Шаг 3). Хостинг не выводится по умолчанию и не
   зашивается в правило. Читать ограниченно: карта репозитория, целевые модули и их прямые
   зависимости, файлы конфигурации. Цель чтения — найти швы, а не разобрать реализацию
   построчно.
   <!-- example:start -->
   Предмет разработки cnplug лежит в GitLab (`frontend/mpstatsPlugin` на gitlab.mpstats.io),
   читается через GitLab MCP; Forgejo `mpstats/mpstatsPlugin` — отстающий снимок master и
   источником актуального состояния не является.
   <!-- example:end -->
3. **project_knowledge_search** — только для документов, недоступных первыми двумя путями.
   Ни реестр репозиториев, ни ADR сюда не относятся: первый живёт на листе «Репозитории»
   (Шаг 3), второй — строкой листа «ADR» файла проекта (Шаг 2).

Не резать по памяти о прошлых задачах и не переиспользовать нарезку соседней задачи как
шаблон — швы каждый раз ищутся в коде заново.

## Шаг 1 — Получить ID задачи

Из явного указания или из контекста разговора (в том числе из отчёта `meeseeks-triage`).
Если не находится — спросить один раз, не гадать.

## Шаг 2 — Прочитать задачу и реестры

- Лист «Задачи»: строка по точному ID. Колонка «Единица бэклога» — единственный текст
  задачи; отдельного поля критериев приёмки нет, приёмка зашита в эту формулировку.
  Колонка «Зависит от» — блокирующие задачи.
- Лист «Подзадачи»: строки, где «Родитель» = ID задачи. Если строки уже есть — см. Шаг 8.
  **Шапка листа стоит в строке 3, строки 1-2 пустые, данные начинаются с 4-й.** Читать
  шапку из первой строки нельзя: там пустота.
- Лист «ADR»: строки, чья «Область связывания» покрывает затронутую область. Это рамка
  устройства задачи. Ключевая колонка — **«Что этим запрещено»**: она ограничивает
  допустимые швы. Шов, проведение которого нарушает хотя бы один пункт запрета
  действующей рамки, недопустим, и выбор между ним и альтернативой развилкой не является.
  Учитывать строки в состоянии `действует` и `принят, декомпозиция не приведена`;
  `заменён ADR-N` читать по замещающей строке.
- Лист «Контракты»: строки, чьи стороны попадают в затронутую область. Подзадача, меняющая
  сторону зарегистрированного контракта, несёт его ID (Шаг 7).
- Лист «Решения»: короткие фиксации, относящиеся к задаче или к затронутой области.
  Решение, закрывающее выбор механизма, снимает развилку и определяет шов.
- Лист «Развилки»: записи Р-N по затронутой области. Закрытая развилка определяет шов и
  снимает вопрос; статус `принято моделью` при этом легален и не блокирует нарезку.
- Лист «Открытые вопросы»: записи ОВ-N по затронутой области. Открытый или частично
  закрытый ОВ, от которого зависит проведение границы, — легальное основание не резать
  (Шаг 5).

**Корень задачи обязателен.** Если в колонке «Корень» не стоит ровно одна инициатива —
задача не режется: это разрыв прослеживаемости. Остановиться, назвать, чего не хватает, и
вернуть задачу человеку; патч не выпускать, подзадачи не выдумывать, корень за человека не
восстанавливать. Пустая «Рамка поведения» разрывом не является: это признак технической
задачи, и она режется как обычно. Операционные правила уровня задачи принадлежат
`meeseeks-backlog` — здесь они не пересказываются.

## Шаг 3 — Определить затронутые репозитории

**Реестр репозиториев** — лист «Репозитории» файла проекта: колонки `Имя`, `Путь`,
`Назначение`, `Состояние`. Другие документы проекта источником пути репозитория не
являются.

<!-- example:start -->
После переноса реестра в artifacts-service (AS-5) источником становится вид артефакта
`repository`, и читать нужно его. `OBSERVABILITY.md` §3a — реестр наблюдаемости,
источником пути не является (решение 2026-08-06); пути
`docs/observability-verification.md` §3a не существует, на него не ссылаться.
<!-- example:end -->

Путь `org/repo` берётся из реестра точным поиском по имени компонента. Два случая, и они
разные:

- **Компонент существует или заводится другой задачей.** Строки в реестре нет — развилка
  (Шаг 5). Неизвестно, к какому репозиторию относится изменение, достраивать по шаблону
  нельзя.
- **Компонент заводится этой же задачей.** Отсутствие репозитория и строки реестра
  развилкой не является. Путь выводится каноническим правилом именования проекта —
  `<аккаунт проекта>/<имя компонента>`; имя дистрибутива на pypiserver и имя образа в
  registry совпадают с именем репозитория. Служба фабрики и роль агента живут каждая в
  собственном репозитории.
  <!-- example:start -->
  Аккаунт проекта — `nikell28` (решение 2026-08-03 о переносе на личный аккаунт;
  прецеденты `correlation-contract`, `nomad-dispatch`). Отсутствие строки реестра для
  заводимого этой же задачей компонента признано не развилкой решением 2026-08-09;
  собственный репозиторий на службу фабрики и на роль агента — решения 2026-08-09 по IC-9
  и IC-8, выводится из решения 2026-08-04 о сборке артефактов в репозитории-владельце.
  <!-- example:end -->

**Строка реестра — подзадача.** Если задача заводит репозиторий, она же заводит строку
реестра, отдельной подзадачей с собственным критерием готовности.

Задача может затрагивать больше одного репозитория. Колонки репозитория на листе
«Подзадачи» нет — распределение по репозиториям не пишется в патч, но фиксируется в отчёте
(Шаг 9): срезы группируются по репозиториям (`meeseeks-slice`,
`группировка-подзадач-в-срезы`), и для этого нужно знать, какая подзадача куда ложится.

## Шаг 4 — Найти швы в коде

Шов — граница между двумя частями системы, через которую проходит фиксируемый контракт:

- файл конфигурации и его схема;
- exit code и его семантика;
- схема результата;
- сигнатура чистой функции доменного слоя;
- единица развёртывания в описании инфраструктуры;
- шаг процесса в оркестраторе и граница детерминизма вокруг него;
- сетевой контракт и его снимок.

<!-- example:start -->
Швы фабрики: конфигурация — `.meeseeks/entrypoints.yml` и `.meeseeks/project.yml`; схема
результата — `task_result.json` и подобные; единица развёртывания — таск или группа в
Nomad-джобе; шаг процесса — шаг workflow или вызов активити Temporal; сетевой контракт —
REST/MCP и его снимок.
<!-- example:end -->

Читать код нужно ровно настолько, чтобы для каждого шва ответить: существует ли он уже,
меняется ли, создаётся ли впервые, кто его потребитель. Список швов, затронутых задачей, —
это заготовка списка подзадач.

## Шаг 5 — Проверка на неустранимую развилку (обязательный чек-пойнт)

Развилка неустранима, если проведение границы требует архитектурного выбора, не выводимого
из кода и не закрытого ни записью листа «Решения», ни строкой Р-N листа «Развилки», ни
действующей рамкой листа «ADR». Строка «Развилок» со статусом `принято моделью` закрывает
развилку наравне с прочими: она достаточна, пока человек её не оспорил. Признаки:

- шов может быть проведён в 2+ равнозаконных местах (например, поле добавляется в схему
  результата либо передаётся отдельным каналом), и ни один вариант не закрыт журналом или
  рамкой;
- проведение границы зависит от записи ОВ-N в статусе `открыт` или `частично закрыт`.
  Открытый ОВ — легальное основание не резать и остановиться, а не повод выбрать самому;
- механизм задачи предполагает компонент, которого нет в коде, и способ его появления
  не определён;
- `org/repo` компонента, который существует или заводится другой задачей, не находится
  точным поиском по реестру (Шаг 3). Компонент, заводимый этой же задачей, развилкой не
  является: путь выводится правилом;
- задача продолжает цепочку, а решение по предыдущему шагу цепочки не зафиксировано;
- текст задачи и код расходятся так, что непонятно, какое поведение считается целевым.

**Если развилка найдена — СТОП.** Патч не выпускать, подзадачи не выдумывать. Результат —
список в чате:

```
Задача [ID] не готова к декомпозиции. Неустранимые развилки:

## Развилка 1: [суть — колонка «Развилка»]
Уровень: [проект / рамка / задача]
Контекст: [факты кода и реестров, которые не разрешают вопрос однозначно]
Варианты:
  А. [описание]
     + [плюсы]
     - [риски и последствия]
  Б. [описание]
     + [плюсы]
     - [риски и последствия]
Основание: [Р-N, ОВ-N, ADR-N, решение по дате, ревью кода]

## Развилка 2: ...
```

Поля формата — колонки листа «Развилки» в их порядке. После выбора человека строка Р-N
заносится на лист почти без переработки: «Принято», «Обоснование» и «Что отвергнуто и
почему» дописываются по итогу выбора, «Статус» ставит тот, кто выбрал. Дальше в этом же
вызове ничего не генерировать.

## Шаг 6 — Нарезка

**Правило разреза.** Одна подзадача = одно изменение по одному шву плюс собственный
различимый наблюдаемый исход.

**Порядок.** Пишется в колонку «Зависит от», результат — DAG. Корни — прочерк `—`,
несколько зависимостей — через запятую без пробела.
<!-- example:start -->
Несколько зависимостей: `CI-9.1,CI-9.3`.
<!-- example:end -->
Правила порядка:

- контракт раньше потребителя;
- чистая функция раньше места её вызова;
- инфраструктурная площадка раньше того, что на ней исполняется;
- регрессионный прогон — последняя подзадача, зависит от всех, чьё поведение он проверяет.

Цикл в DAG — ошибка нарезки, а не повод для суждения: перерезать.

**Полнота.** Объединение критериев готовности покрывает формулировку задачи целиком.
Фрагмент текста задачи, не покрытый ни одним критерием, — недостающая подзадача.

**Неделимость.** Не резать дальше, если у половины нет собственного различимого исхода.
«Добавить поле в схему» — не подзадача, если поле не проверяется отдельно.

**Целостность HEAD.** После каждой подзадачи существующие тесты остаются зелёными. Если
разрез оставляет репозиторий красным — половины склеиваются в одну подзадачу.

**Границы количества.**
- 1 подзадача — вердикт «декомпозиция не требуется», патч не выпускается.
- 2–6 — рабочий диапазон.
- Больше 6 — патч не выпускается, вердикт: задача крупнее подзадачного уровня, нужен
  разрез на задачи. Отдать предложенное разбиение на задачи в чат, без строк патча.

## Критерий готовности подзадачи

Критерий готовности формулируется как наблюдаемый различимый исход, пригодный для записи в
Then. Если исход не формулируется — разрез выбран неверно, резать по другому шву.
Различимость обязательна: указания на сам факт события недостаточно, нужен исход, отличимый
от соседних исходов той же области.

<!-- example:start -->
«Стадия падает» недостаточно; «падает на lint, имя упавшей стадии присутствует в
результате, отличимо от провала verify» достаточно.
<!-- example:end -->

Критерий готовности подзадачи — источник её тест-кейса; вывод кейса из критерия принадлежит
`meeseeks-testcases` (`вывод-тест-кейса`).

## Шаг 7 — Заполнение колонок

Порядок колонок листа «Подзадачи» — восемь: `ID | Родитель | Слой | Изменение | Тип |
Критерий готовности | Зависит от | Контракт`.

- **ID** — `<ID задачи>.<N>`. `N` продолжает максимум существующих подзадач этой задачи,
  не начинается с 1 при дополнении.
- **Родитель** — ID задачи как есть, включая составные ID задач ДОЛГ.
  <!-- example:start -->
  Составной ID задачи ДОЛГ: `DP-2-NM-6`.
  <!-- example:end -->
- **Слой** — словарь: `Домен`, `Orchestration`, `Infra`, `Тест`, `Cleanup`. Другие значения
  не вводить.
- **Изменение** — что именно меняется: файл/модуль, механизм, ссылка на решение из листа
  «Решения» с датой, если оно определяет форму. Конкретно, не абстрактно.
- **Тип** — функция от «Слоя»: `Домен→Домен`, `Orchestration→Интеграция`, `Infra→Infra`,
  `Тест→Тест`, `Cleanup→Cleanup`.
- **Критерий готовности** — наблюдаемый различимый исход (см. «Критерий готовности
  подзадачи»).
- **Зависит от** — по правилам порядка (Шаг 6).
- **Контракт** — ID контракта либо прочерк `—`. Подзадача, меняющая сторону контракта,
  зарегистрированного на листе «Контракты», несёт его ID; во всех остальных случаях —
  прочерк. Контракт по этой подзадаче не заводится и в реестр отсюда не пишется: граница
  контракта принадлежит `meeseeks-methodology`.

## Шаг 8 — Если подзадачи у задачи уже есть

Существующие строки не перезаписывать. Сверить существующее покрытие с текстом задачи:

- покрытие полное — вердикт «декомпозиция уже есть», патч не выпускать;
- покрытие неполное — патч содержит только недостающие подзадачи, нумерация продолжает
  максимум, в отчёте назвать, какой фрагмент задачи не был покрыт;
- существующая нарезка противоречит коду — это не повод её переписывать молча: назвать
  расхождение в чате и остановиться.

## Шаг 9 — Патч и отчёт

Патч — отдельный однолистовой xlsx, только новые строки, не копия файла проекта.

- Лист: `Подзадачи`.
- **Раскладка патча повторяет раскладку листа: шапка в строке 3, строки 1-2 пустые, данные
  с 4-й.** Патч с шапкой в первой строке ляжет со сдвигом.
- Заголовки: восемь колонок листа в том же порядке + девятая `Статус строки`.
- Значение `Статус строки` = `добавлено`, заливка строки зелёная (`PatternFill`,
  `solid`, `C6EFCE`).
- Перенос по словам и верхнее выравнивание для длинных колонок («Изменение», «Критерий
  готовности»), ширина колонок задаётся явно.
- Патчится по ID, не по номеру строки.

Сохранять в `/mnt/user-data/outputs/`. **Имя файла — ASCII**: карточка `present_files`
не отрисовывается для файлов с кириллицей в имени. Формат: `subtasks-patch-<ID>.xlsx`.

Отчёт в чат — коротко:

```
[ID] — [название]
Подзадач: N (слои: ...)
Порядок: [цепочка по «Зависит от»]
Репозитории: [org/repo — какие подзадачи; если один, одной строкой]
Не покрыто/отложено: [если есть]
Дальше: meeseeks-testcases → meeseeks-slice → meeseeks-spec
```

## Критические правила

- Подзадача — логическая единица и единица приёмки, отдельно не мержится. Единица
  исполнения и поставки — срез: один срез = одна ветка = один PR (`meeseeks-slice`). Не
  нарезать подзадачи под отдельные PR.
- Задача без корня либо с более чем одной инициативой в корне не режется: разрыв
  прослеживаемости, возврат человеку (Шаг 2). Пустая рамка поведения разрывом не является —
  это техническая задача. Правила уровня задачи — `meeseeks-backlog`.
- Тест-кейсы этот скил не генерирует. Реестр «Тесткейсы» пополняется скилом
  `meeseeks-testcases` до вызова `meeseeks-spec` — назвать это в отчёте как следующий шаг.
- Неустранимая развилка — всегда стоп, никогда не выбор за человека, даже если вариант
  кажется очевидным.
- Швы ищутся в коде через MCP того хостинга, который назван в реестре «Репозитории», и не
  выводятся из текста задачи по памяти. Допустимость шва ограничена колонкой «Что этим
  запрещено» действующих рамок листа «ADR».
- Больше 6 подзадач — сигнал, что резать надо задачу, а не подзадачи; патч не выпускается.
- Существующие строки листа «Подзадачи» не переписываются, только дополняются.
- `org/repo` существующего компонента — только точный поиск по реестру (лист
  «Репозитории», Шаг 3), никогда по шаблону. Для компонента, заводимого этой же задачей,
  путь выводится каноническим правилом именования проекта (Шаг 3), и строка реестра
  заводится подзадачей той же задачи.
