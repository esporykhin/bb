# Meeseeks Review Cycle - приёмочный цикл задачи

## Место в методологии

Обёртка над `meeseeks-review` и `meeseeks-fix-spec`. Порог находки, таксономия вердиктов,
правила сужения скоупа по циклам и правила сборки ТЗ живут в них. Здесь они не дублируются и
не смягчаются.

Единица приёмки - срез, не задача: граница среза и его отношение к ветке и PR - правило
`meeseeks-slice`, здесь оно не пересказывается. Вердикт выносится по срезу. Задача - рамка
прогона: её срезы уходят в работу и возвращаются на приёмку вместе. Вердикта у задачи нет.

Этот скил отвечает за семь вещей: один снимок реестра на прогон, поиск открытых PR по
каждому срезу, диспатч сабагентов, маршрутизацию по вердикту, закрытие развилок по уже
существующему основанию, сборку плана цикла доработки, доставку появившихся ТЗ и плана в
inbox-репозиторий.

Вход - ID задачи либо перечень ID срезов. Выход - отчёты ревью, ТЗ на доработку там, где оно
требуется, план цикла доработки, один коммит ТЗ и плана в inbox-репозиторий, и список
развилок там, где основания не нашлось.

<!-- example:start -->
Inbox-репозиторий прогона - `nikell28/meeseeks-Codex-inbox`, ветка `master`.
<!-- example:end -->

**Граница скила:** не мержит, не аппрувит, не правит код, в файл проекта и в Google Drive не
пишет, статусы срезов не проставляет. Вердикт сабагента не переоценивает. Пишет в один
репозиторий - inbox; в репозитории фабрики и в PR не пишет.

## Режим запуска

Cowork. Оркестратор и сабагенты - Opus 5. Промпты сабагентов в `agents/`.

Модель сабагента задаётся параметром `model` инструмента Agent при каждом диспатче; поле
`model` в шапке промпта сабагента дублирует то же значение. У человека модель прогона не
спрашивается. Ревью на слабой модели даёт ложный PASS, а по ложному PASS PR уходит в мерж.

Рабочая папка прогона - `run/<задача>/`:

```
run/<задача>/project.xlsx              снимок файла проекта
run/<задача>/task.json                 состав задачи и её срезов
run/<задача>/<срез>/context.json       контекст среза
run/<задача>/<срез>/prs-raw.json, prs.json
run/<задача>/<срез>/review.md, verdict.json, resolutions.md, fixspec.json
run/<задача>/decisions.md              развилки прогона строками листа «Развилки»
run/<задача>/<задача>.rework-<N>.plan.yml   план цикла доработки
run/<задача>/inbox.txt                 листинг корня inbox на момент прогона
```

Папка даёт возобновляемость: прогон, прерванный на середине, продолжается со срезов, у
которых нет `verdict.json`. Уже полученные отчёты ревью не перезапрашиваются.

## Шаг 0 - Снимок файла проекта

Выгрузить файл проекта из Google Drive по `fileId` проекта (`exportMimeType` = xlsx) и
распаковать:

<!-- example:start -->
`fileId = 1mgoml4Kv3NPSoZYbbjTht0Fsw1Q_4xB1I9qDZ4N6zQg`
<!-- example:end -->

```
python scripts/save_project.py <результат MCP> run/<задача>/project.xlsx
```

Снимок один на прогон, и сабагентам передаётся его путь. Если каждый выгружает файл сам,
ревью и ТЗ разных срезов могут увидеть три разных состояния реестра приёмки, и расхождение
всплывёт уже в ТЗ.

## Шаг 1 - Состав задачи

```
python scripts/task.py run/<задача>/project.xlsx --task <ID задачи> \
  --out run/<задача>/task.json
```

Перечень срезов вместо ID задачи - `--slices <ID среза>,<ID среза>`; ID задачи скрипт выводит
по колонке «Родитель». Срезы разных задач одним прогоном не идут: план собирается на одну
задачу.

<!-- example:start -->
`--slices CI-9-S1,AS-4-S1`
<!-- example:end -->

Оркестратору из состава нужны две вещи: `composition` (по каким срезам идёт поиск PR) и
`depends_in_task` каждого среза (из него строятся рёбра плана на Шаге 7а).

Код возврата 2 - задачи или среза с таким ID нет. Стоп: спросить ID один раз, похожий не
подбирать.

`sliced: false` при коде 0 - задача в реестре есть, срезов у неё нет. Принимать нечего:
нарезка делается `meeseeks-slice`, прогон останавливается.

## Шаг 2 - Контекст срезов

По каждому срезу задачи:

```
python scripts/slice_context.py run/<задача>/project.xlsx <срез> \
  --out run/<задача>/<срез>/context.json
```

Оркестратору отсюда нужны пять полей: `repo` - репозиторий среза, где искать PR;
`base_branch` - базовая ветка среза из той же колонки «Репозиторий», против неё сверяется
база PR; `contract` - ID контрактов среза; `status` - срез в `Done` уже принят, спросить
человека, прогонять ли повторно; `closing` - замыкающий срез, на нём проверяется полнота
реестра задачи.

`base_branch: null` при непустом `repo_raw` - базовая ветка в строке среза не распознана.
Это стоп и вопрос человеку: `master` вместо неё не подставляется. Формат колонки
«Репозиторий» - правило `meeseeks-slice`, здесь не пересказывается.

Строки листа «Контракты» по этим ID лежат в `contracts`: вид, стороны, где лежит снимок,
чем ловится расхождение. Они идут сабагенту ревью: нарушение контракта ловится прогоном
против снимка, и без строки реестра ревьюер не узнает, есть ли снимок вообще.

Остальное - реестр приёмки - собирает сабагент ревью сам, как требует Шаг 3
`meeseeks-review`.

## Шаг 3 - Поиск открытых PR по каждому срезу

**Связка PR со срезом - имя файла ТЗ в теле PR.** Воркер, разобравший inbox, кладёт его
туда; имя собрано скриптом `new_tz.py` по шаблону
`<окружение>.<id-среза>[.<пометка>][.part-NN-of-MM].tz.md`, и ID среза в нём - целый сегмент,
а не подстрока. Имя ветки источником связки не является: часть PR несёт номер задачи, а у
задачи несколько срезов, идущих разными PR подряд.

Репозиторий среза известен из строки, поэтому поиск узкий. **PR или MR читается через MCP
того хостинга, который назван для этого репозитория на листе «Репозитории»**: скил один на
аккаунт, а предмет разработки одного проекта лежит в GitLab, другого - в GitHub, третьего
снимком в Forgejo. Хостинг инбокса (Шаги 7 и 8) - отдельный и с хостингом репозитория среза
не связан.

Два запроса, результаты объединяются. **Тело PR и его база запрашиваются обязательно** -
без тела не читается связка, без базы PR в интеграционную ветку неотличим от PR в `master`:

1. Перечень открытых PR (MR) по репозиторию среза - основной путь.
2. Поиск открытых PR (MR) по ID среза в пределах владельца репозиториев проекта -
   страховка на случай, когда PR лежит не в том репозитории, который назван в строке
   среза. Такой PR - находка сама по себе: реализация ушла не туда, куда нарезано.

<!-- example:start -->
Для репозитория на GitHub это два запроса через GitHub MCP: `list_pull_requests` со
`state=open` по репозиторию среза и `search_pull_requests` с запросом
`is:open is:pr user:<владелец репозиториев проекта> <ID среза>`.
<!-- example:end -->

Собрать `run/<задача>/<срез>/prs-raw.json` - массив объектов с полями `repo`, `number`,
`title`, `branch`, `base`, `body`, `draft`, `url` - и прогнать:

```
python scripts/match_prs.py run/<задача>/<срез>/prs-raw.json <ID среза> \
  --base-branch <base_branch из context.json> \
  --out run/<задача>/<срез>/prs.json
```

Сопоставление вынесено в скрипт: ID срезов бывают префиксами друг друга, и подстрочный поиск
отдаёт на ревью PR соседнего среза.

<!-- example:start -->
Подстрочный поиск отдаёт PR по `CI-9-S10` под видом `CI-9-S1`.
<!-- example:end -->

- `matched` со `match: "tz"` - в теле PR имя файла ТЗ этого среза. Точная связка. Поле
  `cycle` посчитано из пометки `rework-N` того же имени, `tz_files` перечисляет все ТЗ
  среза, названные в PR.
- `matched` со `match: "branch"` или `"title"` - ID среза в ветке или заголовке, имени файла
  ТЗ в теле нет. Запасной путь; `cycle` в этом случае `null` и определяется сабагентом по
  телу PR и прошлым отчётам.
- `ambiguous` - ID только в теле, без имени файла ТЗ. Один вопрос человеку списком, до
  диспатча ревью. Ветка старой конвенции без ссылки на ТЗ выглядит именно так.
- `rejected` с причиной «PR по другому срезу» - в теле ТЗ соседнего среза. Это не «не
  нашли»: PR принадлежит другому срезу, в прогон не идёт и вопросом человеку не становится.
- Ни одного `matched` и ни одного подтверждённого `ambiguous` - срез в прогон не идёт. Это
  исход, а не ошибка: реализация либо не начиналась, либо уже смержена. В отчёте назвать,
  где искали и что нашлось закрытого или смерженного.

<!-- example:start -->
Старая конвенция имени ветки, дающая `ambiguous`, - `feat/s<фаза>-<id задачи>-*`.
<!-- example:end -->

Поле `note` у `matched` со значением про смешанные срезы - находка для отчёта: в одном PR
названы ТЗ разных срезов, то есть граница среза, возможно, нарушена. Вердикт по ней выносит
сабагент ревью, оркестратор только передаёт.

`base_mismatch: true` - база PR не совпадает с базовой веткой среза: PR мержится не туда,
куда нарезано. Это находка для отчёта и вход ревью, а не повод снять PR с прогона; вердикт
выносит сабагент. `base: null` (базу не запросили) - тот же порядок: строкой в отчёт.

Черновой PR помечается в отчёте и ревьюится: draft - тоже состояние кода, и ревью по нему
экономит цикл. Закрытые и смерженные PR в прогон не берутся. Два открытых PR на один срез -
оба идут в ревью, и в отчёте это помечается: по границе среза (`meeseeks-slice`) второй
открытый PR означает либо брошенную ветку, либо нарушенную границу.

## Шаг 4 - Ревью

На каждый PR - отдельный сабагент по `agents/reviewer.md` с `model` = Opus 5, не больше трёх
сразу. В промпт подставляются: ссылка на PR, `slice_id`, `base_branch` среза, `cycle` и
`tz_files` из `prs.json` (либо `null`, если связка пришла не через имя файла ТЗ), путь
снимка, путь `context.json`, `output_dir`.

`base_branch` передаётся явно, а не оставляется на вычитывание из контекста: против неё
ревьюер сверяет базу PR, и молчаливый `master` уводит ревью на чужое состояние кода.

Оркестратор в ревью не вмешивается: диff не читает, находки не добавляет и не снимает,
вердикт не пересматривает ни в одну сторону.

`verdict.json` не появился или невалиден - один повторный диспатч того же PR. Второй сбой -
PR идёт в отчёт с пометкой «сабагент не вернул результат», ТЗ по нему не собирается.

## Шаг 5 - Маршрутизация по вердикту

Маршрут считается по полю `verdict`, не по впечатлению от текста отчёта.

| `verdict` | Действие |
|---|---|
| `PASS` | Терминально. Замечания стиля переносятся в отчёт, ТЗ не собирается |
| `REWORK` | Шаг 7 |
| `FAIL` | Шаг 7 |
| `ESCALATE` | Шаг 6, и только после него - Шаг 7 |

Вердикт `ESCALATE` при том, что в отчёте есть и находки REWORK/FAIL, - обычный случай:
сначала Шаг 6 по эскалациям, потом Шаг 7 по всему скоупу.

## Шаг 6 - Закрытие развилок оркестратором

Оркестратор пробует закрыть развилку сам. **Закрыть - значит найти уже существующее
основание, а не выбрать более удачный вариант.** Допустимые основания, в порядке проверки:

1. Строка листа «Развилки» снимка (Р-N), закрывающая этот выбор: у неё есть варианты,
   принятое и «Что отвергнуто и почему». Статус `принято моделью` - легальное основание.
2. Строка листа «Решения» снимка, прямо закрывающая этот выбор.
3. Строка листа «ADR» снимка, запрещающая один из вариантов колонкой «Что этим запрещено»
   при состоянии `действует` и области связывания, накрывающей это место. ADR - строка
   листа, а не файл в папке проекта и не файл в `docs/` репозитория.
4. Однозначный факт кода: вариант описывает механизм, которого в коде нет, либо
   противоречит существующему контракту. Код репозитория среза читается через MCP того
   хостинга, который назван для него на листе «Репозитории».
5. Решение, принятое человеком внутри этого же прогона по другому срезу.

**Развилка, совпадающая с открытым вопросом листа «Открытые вопросы» (ОВ-N)**, идёт
человеку без попытки закрытия: открытый ОВ - легальное основание остановиться, а не
ненайденное основание. Строки ОВ с упоминанием среза и задачи лежат в `context.json`
полем `open_questions_mentioning_id`; реестр целиком читается из снимка.

Правдоподобие, симметрия с соседним срезом и предпочтение оркестратора основаниями не
являются. Запрет `meeseeks-review` выбирать за человека этим скилом не ослабляется:
переносится право сослаться на уже принятое решение, не право принять новое.

Каждая закрытая развилка пишется в `run/<задача>/decisions.md` **строкой листа «Развилки»**
(12 колонок: `ID | Дата | Уровень | Развилка | Контекст | Варианты | Принято | Обоснование |
Последствия | Что отвергнуто и почему | Основание | Статус`). Лист «Решения» для этого не
годится: в его четырёх колонках теряются отвергнутые варианты и уровень развилки, а именно
они объясняют, почему выбран этот вариант.

- «Варианты» и «Что отвергнуто и почему» заполняются из `escalations` отчёта ревью: там
  каждая развилка выпущена с вариантами и рисками.
- «Основание» - ссылка на источник: Р-N, строка «Решения» с датой, ID ADR, путь к файлу
  кода. Основание, которое нельзя назвать ссылкой, - не основание.
- «Статус» - `принято моделью` у развилок, закрытых оркестратором по существующему
  основанию; `принято` - у тех, где вариант назвал человек в этом прогоне.

ID строке присваивает человек при переносе в файл проекта: этот скил в файл проекта не
пишет.

Закрытая развилка меняет класс находки: находка перестаёт быть ESCALATE и получает ту
тяжесть, которую назвал сабагент ревью (REWORK или FAIL). Она записывается в
`run/<задача>/<срез>/resolutions.md` и передаётся в ТЗ вместе с отчётом. Правило
`meeseeks-fix-spec` «ESCALATE не становится пунктом ТЗ» этим не нарушается: в ТЗ идёт
находка, у которой основание найдено и названо.

**Развилка класса «критерий среза недостижим в его репозитории» оркестратором не
закрывается.** Она означает ошибку нарезки, а не невыбранный вариант, и закрывается
перенарезкой в `meeseeks-slice`. Идёт человеку всегда.

Осталась хотя бы одна незакрытая развилка - **этот срез выпадает из прогона; остальные срезы
задачи продолжаются.** ТЗ по нему не собирается даже по независимым находкам REWORK/FAIL:
ответ человека меняет скоуп соседних находок внутри того же PR. Вершин в плане у него нет.
Срезы, у которых выпавший стоит в `depends_in_task`, называются в отчёте отдельной строкой:
их ТЗ собрано против состояния кода, которого в этом плане не будет.

Формат выдачи развилок человеку - по одному срезу за раз:

```
[ID среза] · [repo]#[N] — вердикт ESCALATE

## Развилка 1: [суть]
Контекст: [факты кода и реестра, цитата находки]
Что уже проверено: [какие развилки, решения, строки ADR и файлы смотрели и почему не закрылось]

Вариант А: [описание]
  + [плюсы]
  − [риски]
Вариант Б: […]
```

«Что уже проверено» - обязательная строка: она отделяет развилку, у которой основания нет,
от развилки, основание которой оркестратор не нашёл.

Человек ответил в этом же диалоге - ответ пишется в `decisions.md` тем же форматом, и
прогон по этому срезу продолжается с Шага 7; перезапуск не нужен, `run/` сохранён. Ответ
«пропустить» - срез остаётся без ТЗ.

## Шаг 7 - ТЗ на доработку

На каждый PR со скоупом REWORK/FAIL - сабагент по `agents/fix-specer.md` с `model` = Opus 5.
В промпт: ссылка на PR, `slice_id`, `base_branch` среза, путь `review.md`, путь
`verdict.json`, путь `resolutions.md` (если есть), путь снимка, путь `context.json`,
`output_dir`, пометка цикла `note`.

На выходе шага - маленькие ТЗ по каждому срезу со скоупом доработки и отдельный план цикла
доработки, который собирается Шагом 7а.

Он же считает бюджет исполнения и режет ТЗ на части сверх потолка: правила `meeseeks-spec`,
применяемые `meeseeks-fix-spec`, здесь не пересказываются. Оркестратору из них важно одно:
части одного среза идут по одной ветке и одному PR, поэтому в inbox уходят одним коммитом.

Многорепозиторного ТЗ здесь не бывает - граница среза `meeseeks-slice`. Находка, требующая
изменения в соседнем репозитории, в ТЗ не идёт - сабагент выносит её полем
`out_of_repo_findings`, и оркестратор передаёт её человеку как ошибку нарезки.

Оркестратор части не сводит, не переименовывает и потолок не поднимает. ТЗ на доработку без
раздела «Объём» с оценкой - в inbox не идёт, срез помечается в отчёте как требующий
пересборки ТЗ.

**Имя файла - не по правилу `meeseeks-fix-spec`.** Правило Шага 8 того скила заменяется
шаблоном inbox: файлы создаёт скрипт `scripts/new_tz.py`, его вызывает сабагент, текст ТЗ
передаёт телом.

Пометка цикла считается **по каждому срезу отдельно, до диспатча сабагентов**: у срезов свои
циклы ревью, они идут разными PR и сходятся независимо. Разрез ТЗ на части номер цикла не
увеличивает: `rework-3.part-01-of-02` и `rework-3.part-02-of-02` - один цикл.

1. Прочитать корень inbox - `get_file_contents` по inbox-репозиторию, путь
   `/`, `fields: ['name']` - и сохранить имена в `run/<задача>/inbox.txt`, по одному в строке.
2. Посчитать пометку по каждому срезу:

```
python scripts/new_tz.py --task <ID среза> --rework-auto --existing run/<задача>/inbox.txt --note-only
```

Номер берётся из inbox, а не из счётчика цикла в отчёте ревью: inbox - единственное место,
где видна вся история ТЗ по срезу, и он же исключает коллизию имён. Полученный `note`
(`rework-N`) передаётся сабагенту этого среза.

Сверить его с `cycle` из `prs.json`: номер, посчитанный по inbox, должен быть на единицу
больше того, что видно в теле PR. Расхождение означает, что воркер взял из inbox не все ТЗ
по этому срезу либо не сослался на взятое. Это идёт в отчёт строкой; имя файла считается по
inbox в любом случае - перезаписи существующего ТЗ не делается.

Сабагент вызывает:

```
python3 /mnt/skills/user/meeseeks-review-cycle/scripts/new_tz.py \
  --env <окружение или org/repo> --task <ID среза> --note rework-N \
  [--part <N> --parts <M>] \
  --body <черновик ТЗ> --json
```

`--part`/`--parts` задаются вместе и только при разрезе по бюджету; вызов скрипта - на
каждый файл. Перед написанием тела части сабагент вызывает тот же скрипт с `--name-only`:
идентификатор части (`part_id`) идёт внутрь текста ТЗ трейлером `Meeseeks-Part:`, а
`prev_part_id` - в её предусловие. Части создаются по порядку, начиная с первой: скрипт
откажется создать часть N, пока нет файла части N−1.

**Порядок публикации задаёт план.** Диспетчер публикует ТЗ в очередь по графу: следующая
вершина едет, только когда предыдущая прошла успешно.

Трейлер `Meeseeks-Part` и секция «Предусловие» остаются второй линией: часть, чьё
предусловие не выполнено, останавливается сама и ничего не коммитит.

Окружения нет в списке скрипта - стоп, вопрос человеку; новое окружение заводится
человеком в README inbox, скил его не придумывает.

## Шаг 7а - План цикла доработки

Вершины плана - маленькие ТЗ этого прогона, рёбра - порядок между ними. Файл собирает
скрипт:

```
python scripts/new_plan.py --task <ID задачи> --title "<единица бэклога>" \
  --tz <имя файла ТЗ> \
  --tz <имя файла ТЗ>[:needs=<id или имя файла>[,...]] \
  --out run/<задача>/<задача в нижнем регистре>.rework-<N>.plan.yml
```

- `--tz` - по вызову на маленькое ТЗ, в порядке публикации. Имена берутся из `inbox_paths`
  каждого `fixspec.json`, порядок частей внутри среза - порядок массива.
- Части одного среза скрипт связывает линейно сам. `needs` задаётся только между срезами.
- Рёбра между срезами - `depends_in_task` из `task.json`, и только для тех срезов, по
  которым ТЗ в этом прогоне появилось. Срез с вердиктом `PASS`, выпавший на развилке или
  оставшийся без ТЗ, вершин не имеет, и ребро на него не ставится. Ссылка ставится на
  последнюю часть среза-предшественника.
- Идентификатор вершины считает скрипт, руками не собирается.
- `--title` - «Единица бэклога» задачи из `task.json`; не задан - в план идёт ID задачи.
- Номер `rework-<N>` в имени плана - тот же, что у ТЗ этого прогона. Номера цикла у срезов
  прогона разошлись - имя плана однозначно не определено: стоп, вопрос человеку.
- Имя файла скрипт сверяет с ID задачи и отказывает на чужом.

Коды возврата: `0` - план собран, `2` - вход отвергнут: цикл в зависимостях, ссылка на
несуществующий `id`, имя без суффикса `.tz.md`, повтор файла, части не по порядку, имя файла
плана не по шаблону задачи. Код 2 - стоп, вход правится; план руками не пишется.

Один прогон - один план. Существующий план не дописывается: следующий цикл доработки
выпускает свой файл со своим номером.

## Шаг 8 - Коммит ТЗ в inbox

Коммитится только то, что появилось. Прогон, где ТЗ не собрано ни по одному срезу - все
вердикты `PASS`, или всё встало на незакрытых развилках, или сабагенты не вернули
результат, - в inbox не пишет ничего: ни ТЗ, ни плана. Отчёты ревью в inbox не идут: там
лежат ТЗ и планы.

Inbox-репозиторий, ветка `master`, корень репозитория, прямой пуш без ветки и PR.

1. Проверить занятость имён по `run/<задача>/inbox.txt`. Имя занято - пересоздать файл с
   `--note rework-<N+1>`; перезаписи существующего ТЗ не делается. Номер цикла меняется у
   всех частей одного среза сразу: разъехавшийся номер внутри одного цикла читается как два
   цикла. Имя файла плана привязано к ID задачи и номеру цикла: занято - стоп, вопрос
   человеку.
2. Один коммит на прогон - `push_files` со всеми файлами ТЗ этого прогона и файлом плана
   сразу, включая все части. Части одного среза не могут доехать по одной: цепочка
   предусловий встанет на первой недостающей. План и ТЗ, на которые он ссылается, попадают в
   inbox одним коммитом: плана без своих ТЗ в истории не бывает.
3. Сообщение:

```
<ID задачи> ТЗ на доработку и план: <срез> (rework-N, <окружение>[, части 1-M])[, <срез> …]
```

<!-- example:start -->
Пример: `CI-9 ТЗ на доработку и план: CI-9-S3 (rework-3, mr_meeseeks, части 1-2), CI-9-S5 (rework-1, mr_meeseeks)`.
<!-- example:end -->

Отказ пуша (нет прав, конфликт) - стоп с текстом ошибки. Файлы в `/mnt/user-data/outputs/`
и `run/` остаются, повторный прогон не нужен: коммит повторяется отдельно.

## Шаг 9 - Отчёт

`present_files` со всеми отчётами ревью, всеми файлами ТЗ и файлом плана. Отчёты ревью
сабагенты сохраняют в `/mnt/user-data/outputs/` по правилам `meeseeks-review`, копия
остаётся в `run/`. Имена файлов ASCII - карточка `present_files` не отрисовывается для кириллицы в
имени.

Сводка в чат:

```
Задача [ID] — срезов [N]

[ID среза] · [repo]#[N] · [вердикт] · [находок по тяжести] · предмет среза двинулся: да/нет
  → [что дальше]
...

Объём ТЗ: [по каждому файлу — оценка в проходах агента; при нарезке — на сколько частей]
Решений принято: [сам: n — с указанием источников, человек: m]
Развилки человеку: [по каким срезам, сколько]
Ошибки нарезки: [находки вне репозитория среза; какой задаче нужен meeseeks-slice]
Срезов без открытых PR: [ID — где искали]
План: [имя файла], вершин [V], рёбер [E] / не собирался — ТЗ не появилось
Коммит в inbox: [sha, сообщение, имена файлов] / не делался — ТЗ не появилось
Новые тест-кейсы, требующие регистрации на листе «Тесткейсы»: [сколько, по каким срезам]

Проставить в файле проекта вручную:
  [ID среза] → значение «на ревью»   (PR открыт, вердикт REWORK/FAIL — цикл продолжается)
  [ID среза] → значение «поставлено»  (PASS, после мержа)
  (значений под эти исходы на листе «Срезы» сегодня нет — долг человеку)
Дальше: [мерж / ответ на развилки / meeseeks-slice по задаче X]
```

Блок «Проставить вручную» обязателен: статусы срезов ведёт человек, и следующий прогон
задачи считает по ним готовность. Скил их не проставляет и `Done` за мерж не выдаёт: `Done`
ставится после мержа, а мержит человек.

Строка про тест-кейсы обязательна, если ТЗ их содержит: цикл ревью не закрывается, пока
написанные тесты не попали в реестр.

## Критические правила

- Единица приёмки - срез. Задача - рамка прогона: один прогон - одна задача - один план,
  вердикта у задачи нет.
- Вердикт сабагента - данность. PASS не превращается в REWORK, REWORK не смягчается до
  PASS, находки не дописываются и не вычёркиваются оркестратором.
- Приёмка соседних срезов той же задачи в скоуп ревью не входит - это правило
  `meeseeks-review`, здесь оно не ослабляется.
- Развилка закрывается только ссылкой на существующее основание: строка «Развилки»,
  строка «Решения», строка листа «ADR», факт кода. Выбор между вариантами без основания -
  человеку. Развилка, совпадающая с открытым ОВ, - человеку без попытки закрытия.
- Закрытые развилки пишутся в `decisions.md` строками листа «Развилки»; статус
  `принято моделью` у закрытых оркестратором, `принято` - у решённых человеком.
- Незакрытая развилка - стоп по этому срезу целиком; остальные срезы задачи продолжаются.
- Находка вне репозитория среза - ошибка нарезки для `meeseeks-slice`, не пункт ТЗ и не
  повод расширить PR на второй репозиторий.
- PR сопоставляется со срезом по имени файла ТЗ в теле PR; ветка и заголовок - запасной
  путь. Сопоставление считает скрипт, а не глаз оркестратора.
- PR (MR) и код репозитория среза читаются через MCP того хостинга, который назван на листе
  «Репозитории». Хостинг инбокса - отдельный и с ним не смешивается.
- Базовая ветка среза берётся из колонки «Репозиторий» его строки, передаётся сабагентам и
  сверяется с базой PR. Не распознана - стоп и вопрос человеку; `master` не подставляется.
- PR, в теле которого лежит ТЗ другого среза, в прогон не берётся и вопросом человеку не
  становится.
- Один снимок файла проекта на прогон; сабагенты его не перевыгружают.
- Срез без открытых PR - исход прогона, а не ошибка.
- Оркестратор не ревьюит сам, даже если PR один и выглядит простым.
- Оркестратор и сабагенты работают на Opus 5; модель задаётся параметром `model` при каждом
  диспатче и у человека не спрашивается.
- Имя файла ТЗ собирает `scripts/new_tz.py`, руками не собирается; в `--task` идёт ID среза;
  окружение - из списка inbox, неизвестное окружение - стоп; номер части - пара
  `--part`/`--parts`; `part_id` и `prev_part_id` берутся из `--name-only` до написания тела.
- Порядок публикации задаёт план; трейлер `Meeseeks-Part` и «Предусловие» остаются второй
  линией проверки. Части одного среза уходят в inbox одним коммитом.
- Один прогон - один план. Файл плана собирает `scripts/new_plan.py`, руками не пишется; имя
  привязано к ID задачи и номеру цикла доработки. Существующий план не дописывается.
- Рёбра между срезами - `depends_in_task` из `task.json`, и только для срезов, по которым ТЗ
  в этом прогоне появилось; зависимости от срезов других задач в план не идут.
- Пометка `rework-N` считается по каждому срезу отдельно; разрез на части номер цикла не
  увеличивает.
- Потолок части живёт в `tz_budget.py --limits` и нигде больше. Оценку и разрез делает
  `meeseeks-fix-spec`; оркестратор их не пересматривает и потолок не поднимает.
- Поле `red_on_base` из отчёта ревьюера доезжает до раздела «База» каждого ТЗ. Отчёт с
  находками, но без `red_on_base`, возвращается сабагенту: без него исполнитель установит
  красную базу прогоном всей сюиты.
- ТЗ на доработку без раздела «Объём» с оценкой в inbox не коммитится.
- В inbox коммитятся появившиеся ТЗ и план. Нет ТЗ - нет ни коммита, ни плана; отчёты ревью
  туда не идут.
- Один прогон - один коммит в `master` inbox, сообщение начинается с ID задачи.
- Существующий файл в inbox не перезаписывается: следующий номер цикла.
- Не мержит, не аппрувит, не правит код, в файл проекта и в Drive не пишет, статусы срезов
  не проставляет.
