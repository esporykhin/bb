# Meeseeks Spec - сборка ТЗ среза

## Место в методологии

Это ручной путь того же шага, что внутри фабрики делает спека-агент: вход - срез с
его критерием готовности, задача-родитель, тест-кейсы и каталог решений, выход - ТЗ,
привязанное к конкретному состоянию репозитория. Сборка ТЗ - генеративный шаг с чтением
актуального кода, не подстановка полей бэклога в шаблон.

Единица - срез: один срез = один репозиторий = одна ветка = один PR - правило
`граница-среза`, владелец `meeseeks-slice`. Репозиторий задан строкой среза, а не выводится
из подзадач: разбор принадлежности к репозиториям принадлежит `meeseeks-slice` и на этом
шаге уже сделан.

**Большое ТЗ и маленькое ТЗ - разные единицы.** Сборка идёт в два шага. Сначала собирается
полное ТЗ среза - большое ТЗ, `run/<задача>/<срез>/tz-big.md`. Затем оно режется по бюджету
на маленькие ТЗ - упорядоченные части, каждая из которых отдельный запуск воркера по той же
ветке и тому же PR. Срез равен одному PR, но не обязан помещаться в одну сессию воркера:
сессия ограничена контекстом, и на большом ТЗ она обрывается посреди TDD-цикла. Мержа между
частями нет, и граница среза (`meeseeks-slice`) разрезом не нарушается.

Большое ТЗ в задание очереди не едет: это рабочий документ прогона, он отдаётся человеку.
Телами вершин задания идут только маленькие ТЗ.

**Граница с промптом (важно не путать):** ТЗ описывает *что* меняется - предмет среза, план
по слоям, приёмку, тесты, инварианты и out of scope. ТЗ **не описывает**, что работать нужно
по TDD, как вести себя при CI, как проверять предусловие части - это промпт реализации,
`meeseeks-tdd-implementer`. ТЗ называет предусловие и идентификатор части; механику проверки
знает промпт реализации.

**Граница с воркером.** Ветку, трейлер части, отправку, коммиты и pull request держит
`meeseeks-tdd-implementer` - по машинной шапке в начале файла ТЗ. Работа с git из тела ТЗ
ушла целиком.

## Источники (три, ни один не заменяет другой)

1. **Файл проекта** - Google Drive, по `fileId` проекта. Выгружать через
   `download_file_content` с `exportMimeType` на xlsx, разбирать `openpyxl`.
   Листы: «Срезы», «Задачи», «Тесткейсы», «Решения», «Репозитории», «ADR», «Контракты»,
   «Открытые вопросы», «Развилки». Без «ADR» в ТЗ не попадает рамка устройства, без
   «Контрактов» - снимки границ, без «Открытых вопросов» и «Развилок» - основания стопа.
2. **Код репозитория** - через MCP того хостинга, который назван в реестре «Репозитории»,

   вручную, источником не является.
3. **project_knowledge_search** - только для документов, которых нет ни в файле проекта,
   ни в репозитории напрямую доступными путями (например текст памятки, если нужно
   свериться с формулировкой правила).

## Шаг 1 - Получить ID среза

Из явного указания или из контекста разговора (в том числе из отчёта `meeseeks-triage`,
если он был только что вызван). Если не находится - спросить. Похожий ID не подбирать.

Дан ID задачи без номера среза - стоп: ТЗ на задачу целиком не пишется. Назвать её срезы и
спросить, какой из них.

## Шаг 2 - Прочитать срез и реестры из файла проекта

Контекст собирается скриптом, чтобы разбор строк не расходился между вызовами:

```
python3 /mnt/skills/user/meeseeks-spec-cycle/scripts/slice_context.py \
  <project.xlsx> <ID среза> --out context.json
```

Код возврата 2 - среза с таким ID на листе «Срезы» нет. Стоп.

Что берётся из вывода и что означает:

- **`slice`** - строка среза. `Результат` - что умеет фабрика после мержа, в терминах
  наблюдаемого поведения. `Критерий готовности` - **источник приёмочных критериев ТЗ**.
  Формулировки задачи приёмкой среза не являются: задача закрывается всеми своими срезами,
  а этот PR закрывает один. `Репозиторий` несёт репозиторий и базовую ветку среза (Шаг 3).
  `Контракт` - ID контракта или прочерк (ниже, «Колонка «Контракт» строки среза»).
- **`testcases`** - кейсы с `Источник` = ID среза. Переносятся как есть, с TC-ID и
  Given/When/Then; раскладка по фазам - раздел «Фазы тестов». Вывод и содержание
  тест-кейсов - `meeseeks-testcases`: новых кейсов на этом шаге не появляется.
- **`closing_testcases`** - непусто только у замыкающего среза: кейсы задачи, не
  привязанные ни к одному её срезу (уровень стори). Входят в его ТЗ - раздел «Фазы
  тестов».
- **`sibling_slices`** - соседние срезы задачи. Их предмет идёт в out of scope с явной
  пометкой, а не переносится в план.
- **`deps` / `blocking_deps`** - зависимости и их статусы. Непустой `blocking_deps` -
  стоп: ТЗ пишется против кода, которого ещё нет. Вернуть на закрытие зависимостей;
  готовность среза к ТЗ - `meeseeks-triage`.
- **`decisions_mentioning_id`** - **дополнение** к разделу «Архитектурные инварианты», не
  его основа: инварианты собираются с листа «ADR» (Шаг 5а). Лист «Решения» прочитать самому:
  скрипт ищет по упоминанию ID, а запись бывает сформулирована без него. Так же читается
  лист «ADR»: связывание идёт по запрету, а не по упоминанию ID.
- **`unassigned_task_testcases`** - непусто у незамыкающего среза, если у задачи есть
  кейсы вне срезов. Не находка сама по себе; в отчёт строкой, чтобы это увидел человек.

**Прослеживаемость задачи-родителя - обязательная проверка.** Срез наследует
прослеживаемость от своей задачи. Колонки «Основание» на листе «Задачи» нет; прослеживаемость
несут три колонки - «Корень», «Рамка поведения», «Рамка устройства», - а «Класс»
вычисляется. Правила уровня задачи принадлежат `meeseeks-backlog` и здесь не повторяются.

Проверяется:

- **«Корень» заполнен и это ровно одна инициатива.** Пусто, две и больше, либо значение не
  инициатива - разрыв прослеживаемости.
- **Заполнена хотя бы одна рамка** - поведения либо устройства. Обе пусты - разрыв
  прослеживаемости: задача не лежит ни в одном пересечении.
- **«Класс» сходится с вычислением**: рамка поведения заполнена - продуктовая, пуста -
  техническая. Расхождение колонки с вычислением - дефект строки задачи, а не повод
  выбрать одно из двух.

Разрыв прослеживаемости и выход за рамку - **два разных дефекта**, и проверяются они
порознь: первый - незаполненность указателя, второй - реализация, нарушающая запрет
связанной рамки (Шаг 5а, «Архитектурные инварианты»).

Разрыв прослеживаемости - **стоп**, ТЗ не пишется. Закрывается он на уровне задачи, а не
догадкой при сборке ТЗ: корень и рамку нельзя вывести из среза, кода или реестра решений.
Вернуть человеку строкой - какая задача, какого поля не хватает - и остановиться, как на
неустранимой развилке (Шаг 5).

### Колонка «Контракт» строки среза

Значение - ID записи листа «Контракты» либо прочерк. Прочерк - контрактной границы у среза
нет, дальше по контракту ничего не делается.

Непустое значение - прочитать строку «Контракты» по этому ID и взять из неё две колонки:
«Где лежит снимок» и «Чем ловится расхождение». Дальше они идут в ТЗ:

- путь снимка - отдельным пунктом раздела «Изменения по слоям», если срез меняет сторону
  контракта, и раздела «Антискоуп», если не меняет;
- способ поймать расхождение - отдельным утверждением приёмочных критериев: нарушение
  рамки ловится на ревью, нарушение контракта - прогоном против снимка, и приёмка обязана
  этот прогон называть;
- расхождение кода со снимком, обнаруженное при чтении (Шаг 4), идёт в раздел «Расхождения
  ТЗ↔код», а не правится молча.

**Контракт назван, а снимка нет** («Где лежит снимок» пусто) - развилка (Шаг 5): завести
снимок этим срезом либо принять границу без машинной проверки. Выдумывать снимок при сборке
ТЗ нельзя.

## Шаг 3 - Проверить репозиторий по реестру

Репозиторий берётся из колонки `Репозиторий` строки среза. Он ровно один.

Та же колонка несёт **базовую ветку среза**: срез есть единица поставки, и куда он
мержится - его собственное свойство. Ветка среза создаётся от базовой и мержится в неё же. Базовая
ветка идёт дальше в три места: чтение кода (Шаг 4), поле `base` задания очереди (Шаг 7) и
раздел «База» маленького ТЗ (Шаг 6). Молчаливый откат на умолчание репозитория - дефект, а
не запасной путь: при интеграционной базе вершина уедет не туда.

Проверка сводится к одному вопросу: есть ли этот путь на листе «Репозитории»
(`repo_in_registry` в контексте). Два случая:

- **Репозитория нет в реестре, и компонент заводится этим же срезом.** Не развилка: путь
  выводится правилом именования репозиториев проекта, имя дистрибутива и образа совпадает
  с именем репозитория. Заведение репозитория и строки реестра входят в план изменений
  этого ТЗ.
- **Репозитория нет в реестре, и компонент существует или заводится другим срезом.**
  Развилка (Шаг 5).

Правило именования репозиториев проекта и площадка, на которой они лежат, заданы записями
листа «Решения»; исключений из них нет. Реестр наблюдаемости источником пути не является.

## Шаг 4 - Прочитать код

Через MCP хостинга, названного в реестре «Репозитории»: только затронутые модули и их
прямые зависимости - не весь репозиторий.
Что читать - определяется критерием готовности среза и его тест-кейсами (Шаг 2). Цель -
понять текущую структуру достаточно, чтобы описать план изменений конкретно (файл, тип
изменения: создать/изменить/удалить), а не абстрактно.

Читать на **базовой ветке среза** - той, что названа в колонке `Репозиторий` строки среза
(Шаг 3). Ветка среза создаётся от неё и в неё же мержится, зависимости среза смержены
(проверено Шагом 2), поэтому базовая ветка и есть то состояние, против которого ТЗ будет
исполняться. `master` читается только тогда, когда база им и названа; подставлять его,
когда в строке стоит другая ветка, - значит писать ТЗ против чужого кода.

Отдельно - ожидания. Если приёмка среза проходит через ожидание внешнего события (сигнал,
вердикт человека, таймер, опрос, дочерний процесс, сетевой вызов), прочитать три вещи: чем
ожидание ограничено в коде, кто задаёт этот предел, и как то же ожидание снимается в уже
существующих тестах того же класса. Это факты кода того же порядка, что имена символов, и
идут они в ТЗ так же.

Значение предела читается, а не подразумевается. Умолчание, измеряемое часами, в тесте
никогда не наступит; умолчание, измеряемое секундами, наступит и без участия теста - от
этого зависит, что ТЗ требует от исполнителя.

## Шаг 5 - Проверка на неустранимую развилку (обязательный чек-пойнт)

Развилка неустранима, если выбор архитектурного уровня не выводится из **фактов кода** или
**существующего основания** - то есть несколько вариантов одинаково законны, и решение
принадлежит человеку, не агенту.

Основанием, закрывающим развилку, считается любое из четырёх: факт кода, строка листа «ADR»
(запрет из «Что этим запрещено» отсекает вариант), строка листа «Развилки» (Р-N; статус
`принято моделью` закрывает наравне с остальными), запись листа «Решения». Одного «Решения»
искать мало: рамка устройства живёт на «ADR», а закрытые развилки - на «Развилках».

**Открытый ОВ-N - самостоятельное основание остановиться.** Вопрос листа «Открытые вопросы»
в статусе `открыт` или `частично закрыт`, от ответа на который зависит предмет среза, - штатный
исход, а не ненайденное основание: назвать ОВ-N и остановиться, не выдумывая ответ.

Признаки:

- критерий готовности среза предполагает решение, для которого в коде есть 2+ равноценных
  места или подхода, и ни один не закрыт ни одним из четырёх оснований;
- код и формулировка среза расходятся так, что консервативный вариант не очевиден (это не
  то же самое, что «код не совпадает с ожиданием техническим образом» - тот случай не
  развилка, он идёт в ТЗ как есть, с пометкой расхождения для промпта);
- `org/repo` компонента, который существует или заводится другим срезом, не находится
  точным поиском по реестру (Шаг 3);
- приёмка среза проходит через ожидание внешнего события, и способ его снятия в тесте не
  установлен ни существующим тестом того же класса, ни одним из четырёх оснований. Выбор между
  средой со скачком времени, подменой предела и подменой самого источника события - решение
  человека: он задаёт цену прогона тестов на весь репозиторий, а не на один срез;
- **критерий готовности среза недостижим внутри его репозитория**: часть требуемого
  поведения живёт в соседнем репозитории, и там нет своего среза, который её закрывает.
  Это ошибка нарезки, а не повод расширить ТЗ на второй репозиторий. Развилка с двумя
  исходами: завести срез в соседнем репозитории либо сузить критерий готовности этого.
  Граница и группировка срезов - `meeseeks-slice`.
- контракт, названный в колонке `Контракт` строки среза, не имеет снимка (Шаг 2): завести
  снимок этим срезом либо принять границу без машинной проверки.

**Если развилка(и) найдена - СТОП.** Не писать ТЗ. Результат - не файл, а список в чате:

```
Срез [ID] не готов к ТЗ. Неустранимые развилки:

## Развилка 1: [суть одной строкой - колонка «Развилка»]
Уровень: [проект / рамка / задача / срез]
Контекст: [факты кода и реестров, которые не разрешают вопрос однозначно]
Варианты:
  А. [описание] - последствия: [...]
  Б. [описание] - последствия: [...]
  [В при необходимости]
Что отвергнуто и почему: [вариант - причина; заполняется вместе с выбором]
Основание: [Р-N, ОВ-N, ADR-N, решение по дате, факт кода - на что опирался разбор]
Статус: [ждёт человека; `принято моделью` ставится, только если разбор сам закрыл развилку
основанием - тогда стопа нет]

## Развилка 2: ...
```

Формат сознательно построен под строку листа **«Развилки»** (12 колонок: ID · Дата ·
Уровень · Развилка · Контекст · Варианты · Принято · Обоснование · Последствия · Что
отвергнуто и почему · Основание · Статус) - после выбора человека остаётся заполнить
«Принято», «Обоснование» и дату, и строка заносится на лист почти без переработки. Лист
«Решения» для этого не годится: у него четыре колонки, и варианты с отвергнутым в них не
помещаются.

Статус `принято моделью` легален: если разбор сам закрыл развилку основанием, строка
заводится с этим статусом и прогон не блокируется - достаточно, пока человек не оспорил.
Стоп ставится только на том, что основанием не закрыто.

Дальше в этом же вызове ничего не генерировать.

## Шаг 5а - Собрать большое ТЗ

Полное ТЗ среза собирается одним документом: план изменений по слоям, приёмка, тесты,
инварианты, out of scope. Разделы - те же, что у маленького ТЗ (Шаг 6), без секций разреза:
«Предусловие», «Скоуп части» и «Хендофф» в нём не бывает.

Файл - `run/<задача>/<срез>/tz-big.md`. Это рабочий документ прогона: он остаётся в каталоге
прогона и отдаётся человеку. Телами вершин задания идут только маленькие ТЗ, нарезанные из
него.

Дальше большое ТЗ - источник счётчиков бюджета и материал разреза. Маленькое ТЗ ничего к его
предмету не добавляет, оно берёт свою долю.

**Архитектурные инварианты собираются с листа «ADR», а не с листа «Решения».** Рамка
устройства живёт строкой «ADR»; «Решения» - короткие фиксации на четыре колонки и запретов
не несут. Порядок сборки раздела:

1. Отобрать строки «ADR», связанные со строкой работ. Критерий связывания один: **существует
   правдоподобная реализация этого среза, нарушающая хотя бы один пункт колонки «Что этим
   запрещено»**. Совпадение термина, репозитория или задачи связыванием не считается.
2. Из каждой связанной строки в раздел «Архитектурные инварианты и out of scope» идёт ADR-N
   и текст «Что этим запрещено» - запретом, а не пересказом принятого.
3. Колонка **«Требование к приёмке»** связанной строки вносится в раздел «Приёмочные
   критерии» отдельным проверяемым утверждением, а не остаётся в инвариантах.
4. Колонка **«Чем проверяется (TC)»** сверяется с фазами тестов: названные там TC-ID обязаны
   стоять в разделе «Тесты». Есть TC-ID, которого нет в фазах, - строкой в отчёт. Колонка
   пуста - кейсы под рамку ещё не заведены, это тоже строка в отчёт, а не повод придумать
   кейс здесь.
5. Строки «ADR» в состоянии `заменён ADR-N` не берутся; берётся замена.

Записи листа «Решения» остаются **дополнением** к разделу - тем, что рамкой не выражено.

Выход за рамку - реализация, нарушающая запрет связанной строки «ADR», - дефект, отдельный
от разрыва прослеживаемости (Шаг 2). Обнаружен при чтении кода (Шаг 4) - идёт в раздел
«Расхождения ТЗ↔код».

## Шаг 5б - Бюджет исполнения

Часть ТЗ исполняется одной сессией Codex в воркере. **Единица измерения - вызов
инструмента**: Bash, Read, Edit, Write. Это та же величина, что `num_turns` в отчёте прогона,
колонка `TURNS` в `mrctl ls` и лимит `--max-turns` воркера, поэтому оценка ТЗ и факт прогона
сравнимы напрямую.

Потолок и пол части числами здесь не повторяются - они живут в скрипте и берутся оттуда:

```
python3 /mnt/skills/user/meeseeks-spec/scripts/tz_budget.py --limits
```

Оценка считается тем же скриптом, не на глаз:

```
python3 /mnt/skills/user/meeseeks-spec/scripts/tz_budget.py \
  --files-new N --files-edit N --files-mech N \
  --tests-ui N --tests-e2e N \
  --migrations N --infra N --new-repos N [--ci-new] --json
```

Счётчики берутся из плана изменений большого ТЗ (Шаг 5а) и тест-кейсов среза (Шаг 2):
`files-new`/`files-edit` - файлы кода по плану; `files-mech` - однотипные правки по одному
паттерну; `tests-ui` - кейсы типа `U` и `I`, `tests-e2e` - типа `E`; `infra` - Dockerfile,
`*.nomad.hcl`, compose, workflow; `new-repos` - репозиторий или пакет, заводимый с нуля;
`--ci-new` - workflow CI заводится или меняется.

Вердикт `ok` - одна часть, одно маленькое ТЗ, секции «Предусловие» в нём нет. Раздел
«Антискоуп» есть всегда, и при разрезе, и без него: пустой антискоуп не проходит проверку
разбора (Шаг 6, «Форма разделов скоупа»). Вердикт `over` - Шаг 5в.

Вердикт `small` - не ошибка и не повод объединять срезы: группировка срезов принадлежит
`meeseeks-slice`. Назвать оценку в разделе «Объём» и продолжить.

## Шаг 5в - Разрез большого ТЗ на части

**Границу проводит вертикальный TDD-инкремент.** Часть = набор TC-ID из реестра плюс код,
который делает их зелёными. Не «сначала все тесты, потом вся реализация»: часть, оставившая
ветку с красными тестами, съест лимит попыток CI у следующей части.

Инвариант части: после неё тесты части зелёные и работа закоммичена. Ветку заводит воркер по
шапке ТЗ, поэтому части одинаковы: первая ничем не отличается от остальных, и «создать ветку»
в план не входит.

Порядок шагов:

1. Разложить план изменений большого ТЗ на части снизу вверх по слоям, по одной вертикали
   за раз.
   Файл целиком принадлежит одной части: две части, правящие один файл, дают конфликт
   границ и ломают антискоуп.
2. Проверить раскладку `--plan`:

```
python3 /mnt/skills/user/meeseeks-spec/scripts/tz_budget.py --plan plan.json --json
```

   Формат `plan.json` - массив частей в порядке исполнения, со счётчиками и полем `name`.
   Часть с вердиктом `over` - шов выбран не там, переложить. Часть с вердиктом `small` -
   слить с соседней.
3. Неделимая часть сверх потолка (скаффолд репозитория, одна миграция, один e2e-кейс с
   тяжёлой обвязкой) помечается `"atomic": true` и остаётся как есть. Превышение
   называется в её разделе «Объём» строкой - это факт, который нужен человеку при разборе
   упавшего прогона, а не оправдание.

Разрез больше чем на шесть частей - строка в отчёт: срез, скорее всего, нарезан слишком
крупно. Прогон при этом продолжается, ТЗ пишутся; перенарезка принадлежит `meeseeks-slice`
и делается отдельным вызовом по решению человека.

## Шаг 5г - Имена и сцепка частей

Имя файла и идентификатор части считает скрипт, руками они не собираются:

```
python3 /mnt/skills/user/meeseeks-spec-cycle/scripts/new_tz.py \
  --env <окружение или org/repo> --task <ID среза> \
  --part <N> --parts <M> --name-only --json
```

Скрипт возвращает `part_id` (имя файла без `.tz.md`, вида
`<repo>.<id среза>.part-<N>-of-<M>`) и `prev_part_id`. Оба идут внутрь текста ТЗ: `part_id`
- в трейлер коммитов, `prev_part_id` - в предусловие. Поэтому имя считается **до** написания
тела, а не после.

Порядок исполнения частей выражает план, а не сортировка имён: следующее маленькое ТЗ
публикуется, только когда предыдущее прошло. Трейлер `Meeseeks-Part` и секция «Предусловие»
остаются второй линией - если ТЗ опубликовано раньше времени, агент останавливается сам.
Номер части дополнен нулём слева, поэтому десятая часть не встаёт перед второй в перечнях.

## Шаг 6 - Собрать маленькие ТЗ

Одна часть - один файл. Шапка, предусловие и хендофф повторяются в каждом файле; **полный
текст ТЗ в части не дублируется** - иначе постоянные издержки умножатся на число частей, а
выигрыш от разреза исчезнет.

**Каждая часть полна по своему предмету.** Агент, который её исполняет, читает только её: ни
большого ТЗ, ни соседних частей он не видит. Значит всё, что нужно знать о предмете этой
части, в ней есть - контекст, план изменений, приёмка, тесты, границы. Общий контекст,
нужный для понимания предмета части, повторяется в каждой части, которой он нужен. Не
дублируется план других частей, а не контекст.

### Машинная шапка

Первые строки файла - поля `Ключ: значение`, которые читает воркер. По ним он заводит ветку,
сверяет репозиторий, ставит трейлер части и делает pull request. Без `Meeseeks-Branch` воркер
работает по-старому: ветку и отправку берёт на себя агент, и всё, что описано ниже про
границу ответственности, не действует.

Формат жёсткий, потому что разбор машинный:

- шапка идёт **до** заголовка `# ТЗ:` и до любого текста;
- пустых строк внутри шапки нет - первая пустая строка её закрывает;
- строка, начинающаяся с `#`, разбор прекращает;
- значение - одной строкой, без переносов.

Обязателен только `Meeseeks-Branch`. Имя ветки выводится из ID среза правилом
`feat/<id в нижнем регистре>`. Слаг и номер части в имя ветки не входят - ветка одна на
срез, части идут по ней же.

<!-- example:start -->
`CI-9-S1` → `feat/ci-9-s1`; `part_id` третьей части из трёх -
`mr_meeseeks.ci-9-s1.part-03-of-03`.
<!-- example:end -->

`Meeseeks-Repo` сверяется с `origin` дерева задачи: несовпадение останавливает прогон до
запуска агента. `Meeseeks-Part` воркер проставляет трейлером в последний коммит части сам -
агенту об этом писать не нужно.

### Граница ответственности

Ветку, трейлер части, отправку и pull request держит исполнение -
`meeseeks-tdd-implementer`.

Поэтому в тело ТЗ **не входят**: указания создать или продолжить ветку, создать PR,
запушить, проставить трейлер, не переписывать историю. Приёмка части описывает состояние
кода, а не состояние origin.

```markdown
Meeseeks-Repo: [org/repo]
Meeseeks-Branch: feat/[ID среза в нижнем регистре]
[Meeseeks-Part: [part_id] - только при разрезе]
Meeseeks-PR-Title: [ID среза]: [результат среза одной строкой]

# ТЗ: [ID среза] - [результат среза одной строкой]
[· часть N из M - [короткое имя части], если ТЗ разрезано]

Зависимости среза смержены: [ID - статус].

## Предусловие
[только при разрезе]
[часть N > 1: к началу части в ветке существуют - файлы: [перечень]; зелёные TC-ID:
[перечень]]
Предусловие не выполнено - работа не начинается, коммитов нет.

## Объём
Оценка: [N] вызовов инструментов (потолок части - из `tz_budget.py --limits`).
[счётчики: файлов новых/изменяемых/однотипных, тест-кейсов U/I и E, миграций,
инфраструктурных файлов]
[при разрезе: суммарная оценка ТЗ - K, частей - M]
[если часть неделима и сверх потолка - сказать это строкой и назвать, что именно неделимо]

## Срез
[ID среза] · задача [ID задачи] - [единица бэклога]
Результат: [колонка «Результат» - что умеет фабрика после мержа]
[замыкающий срез задачи: да/нет]

## База
Базовая ветка: [ветка из колонки `Репозиторий` строки среза] - от неё заведена ветка среза,
в неё же уходит PR.
[красные до начала части тесты - поимённо, с указанием, чем они красны;
либо строка «база зелёная»]
Это состояние ветки на входе, не работа части. Устанавливать его прогоном не нужно,
чинить - тоже: если пункт не назван в приёмочных критериях, он вне скоупа.

## Скоуп части
[только при разрезе]
TC-ID: [только свои]
Файлы: [только свои]
Локальные проверки: [конкретные аргументы - пути для pytest, каталоги для линтера;
полная сюита остаётся за CI]

## Изменения по слоям

- `[путь]` - [слой], [что сделать]. Критерий готовности: [...]. Зависимость: [...]
- `[путь]` - [слой], [что сделать]. Критерий готовности: [...]
... (в порядке снизу вверх: контракт и домен, хранилище и адаптеры, оркестрация,
инфраструктура и сборка)

## Антискоуп

- `[путь]` - [почему не трогать: предмет части N, предмет другого среза]
- `[путь]` - ...

## Санкции на удаление ключей гейта
[ключи, которые часть удаляет, переименовывает или переписывает так, что идентификатор
меняется - по каждому гейту отдельной строкой]
gate tests: [nodeid], [nodeid], ...
gate inventory: [ключ], ...
[если часть ничего не удаляет - строка «Срез ключей гейтов не удаляет»]

## Приёмочные критерии
[при разрезе: приёмка этой части - её тесты зелёные, изменения закоммичены;
приёмка среза целиком закрывается частью M]
[без разреза: колонка «Критерий готовности» среза, разложенная на проверяемые утверждения]
[«Требование к приёмке» каждой связанной строки «ADR» - отдельным утверждением]
[контракт среза непуст: прогон против снимка - чем ловится расхождение]

## Тесты
### Фаза A (инварианты слоёв, снизу вверх)
[TC-ID - Given/When/Then, тип U/I]
### Фаза B (приёмка, сверху)
[TC-ID - Given/When/Then, тип E]
[для замыкающего среза: кейсы уровня стори из closing_testcases - реестр задачи
прогоняется целиком после мержа этого среза]

Если срез требует теста вне реестра - пометить явно:
`[новый TC-<ID среза>-D<N> - требует внесения в лист «Тесткейсы»]`, не придумывать его
молча внутри плана.

Кейс проходит через ожидание внешнего события - назвать отдельной строкой под ним:
`[ожидание: <что ждётся> - снимается <чем в тесте> - предел <какой и кем задан>]`

Ожидание, снимаемое только течением реального времени, в тест не ставится. Предел ожидания
теста задаёт воркер, и такой кейс будет красным, а не зелёным. Умолчание продуктового кода
здесь ничего не решает: измеряется часами - тест обязан задать своё значение либо идти в
среде со скачком времени, и ТЗ называет, какое из двух.

## Хендофф
[только при разрезе, кроме последней части]
Следующая часть ([часть N+1]) вправе считать существующим:
[дословно тот же текст, что стоит в её секции «Предусловие»]

## Архитектурные инварианты и out of scope
[связанные строки листа «ADR»: ADR-N - что этим запрещено, дословно запретом]
[дополнением - релевантные записи листа «Решения», с датой и сутью]
[контракт среза: K-N - где лежит снимок, чем ловится расхождение]
[соседние срезы задачи: ID - что делает - «не в этом ТЗ»]
[что явно не трогать]

## Расхождения ТЗ↔код, если есть
[технические - не архитектурные - несовпадения кода с ожиданием среза;
консервативный вариант, который сохраняет инварианты]
```

«Хендофф» части N и «Предусловие» части N+1 совпадают текстуально. Расхождение между ними -
ошибка сборки, а не разница формулировок: по этому тексту исполнитель решает, продолжать
работу или остановиться.

Раздела «Межрепозиторные зависимости» в ТЗ среза нет: репозиторий один. Стыковка с соседним
репозиторием, если она нужна, выражена порядком срезов в колонке `Зависит от` и попадает в
строку «Зависимости среза смержены».

### Форма разделов скоупа

«Изменения по слоям» и «Антискоуп» разбираются машинно: из них контур строит множество
файлов, которые ТЗ разрешило менять, и множество файлов, которые оно запретило. Разборщик -
`parse_scope` в `src/claude_worker/intake/scope_spec.py` репозитория `nikell28/taskforge`.
Его правило, дословно:

> Раздел ищется по заголовку markdown любого уровня, в тексте которого встречается
> «изменения по слоям» либо «антискоуп» (регистр и нумерация не важны); раздел кончается
> следующим заголовком любого уровня либо концом текста. Элементы перечня - строки,
> начинающиеся с `-` или `*` (после необязательных пробелов). Из элемента берётся первый
> образец пути - текст до первого пробела, двоеточия или запятой, с которого сняты обратные
> кавычки; пустой результат - элемент пропускается. Раздела нет - `None`; раздел без
> образцов - пустой кортеж.

Отсюда форма, и она обязательна:

- **Плоский перечень, без подзаголовков внутри раздела.** Любой заголовок внутри раздела
  обрезает раздел до вступительной прозы, и перечень оказывается пустым.
- **Путь первым в строке, в обратных кавычках.** Всё, что стоит после первого пробела,
  двоеточия или запятой, разборщику невидимо: там место роли слоя, того, что сделать,
  критерия готовности и зависимости.
- **Критерий готовности и зависимость - внутри того же пункта**, продолжением строки либо
  вложенными пунктами. Вложенные пункты разборщик читает как обычные элементы, поэтому во
  вложенном пункте путь первым **не** ставить: он попадёт в скоуп.

```markdown
## Изменения по слоям

- `src/claude_worker/gate_cycle/budget.py` - пишет B6. Правило и форма возврата.
- `tests/gate_cycle/test_budget.py` - пишет B4. Кейсы TC-..., красные до логики.
```

```markdown
## Антискоуп

- `src/claude_worker/runner/sessions.py` - предмет другого среза, не трогать.
```

**Почему форма важна.** Пустой перечень не равен отсутствующему. При пустом скоупе
`scope_verdict` считает вне перечня **каждый** файл, отказ `gate-regression` получает класс
«прогон» вместо «задача», а шаг правки находок C3 остаётся без разрешённых файлов
[код: `src/claude_worker/gate_cycle/analysis.py`, `scope_verdict`, `regression_scope_of`].
На этом сгорел прогон r41: три итерации цикла гейтов, около $37 по таблице тарифов, 2 часа
37 минут.

### Проверка разбора перед выдачей (обязательная)

По тексту **каждого** маленького ТЗ прогнать правило разборщика вручную и убедиться, что:

- оба перечня непусты - и «Изменения по слоям», и «Антискоуп»;
- образцы совпадают ровно с теми путями, которые ТЗ называет в этих разделах: ни лишнего
  (вложенный пункт, начатый с пути), ни потерянного (пункт, у которого перед путём стоит
  слово).

Не сошлось - **ТЗ правится, а не отдаётся**. Проверка идёт до Шага 7 и до сборки задания:
файл с пустым перечнем в очередь уходить не должен.

### Санкции на удаление ключей гейта

Гейты направления `grew` (`tests`, `inventory`) считают регрессией **исчезновение** ключа, а
не только появление красного [код: `src/claude_worker/gates/compare.py`, функция `compare`].
Срез, который переписывает, переименовывает или удаляет существующий тест, убирает его
идентификаторы - и цикл гейтов требует вернуть то, что ТЗ удалило намеренно. Починить это
цикл не может и выгорает по потолку итераций.

Санкция - поле `gate_removes` задания: по гейту перечень ключей, чьё исчезновение регрессией
не считается. Совпадение точное, без образцов и звёздочек.

Правила сборки раздела:

- Идентификаторы снимаются фактом, а не по памяти: `pytest --collect-only -q` по затронутым
  файлам на текущем HEAD ветки. Выписанный из головы nodeid не совпадёт с ключом гейта.
- Особый случай - параметризованный тест: его идентификатор несёт значения параметров
  (`...[0.2-0.2-attempt]`), поэтому правка ожидаемого значения тоже меняет идентификатор.
  Санкция нужна и там, хотя «тест не удаляли».
- Часть ничего не удаляет - раздел всё равно есть, строкой «Срез ключей гейтов не удаляет».

### Фазы тестов

Кейсы среза раскладываются по фазам колонкой «Тип»: `U` и `I` - Фаза A, инварианты слоёв
снизу вверх; `E` - Фаза B, приёмка сверху. Фазы не перемешиваются: Фаза B проверяет то, что
Фаза A уже держит.

У замыкающего среза в Фазу B добавляются кейсы задачи, не привязанные ни к одному её срезу:
после его мержа реестр задачи прогоняется целиком.

При разрезе фазы раскладываются внутри части: часть - вертикальный инкремент, а не «сначала
все тесты, потом вся реализация».

## Шаг 7 - Сохранить и отдать

Файлы маленьких ТЗ создаёт `new_tz.py`, по вызову на часть - с теми же `--part`/`--parts`,
что на Шаге 5г, и с `--body`:

```
python3 /mnt/skills/user/meeseeks-spec-cycle/scripts/new_tz.py \
  --env <окружение или org/repo> --task <ID среза> \
  [--part <N> --parts <M>] --body <черновик части> --json
```

Части создаются по порядку, начиная с первой: скрипт отказывается создать часть N, пока нет
файла части N-1. Пропуск ломает цепочку предусловий и обнаруживается только сгоревшим слотом
воркера.

Выход шага - три вещи: маленькие ТЗ файлами, большое ТЗ файлом и JSON задания для очереди
контура. Файлов для коммита в git-inbox скил больше не готовит.

### Машинная сводка `spec.json`

По каждой части вызов возвращает `spec.json`. Обязательные поля части:

- `part` - номер части, `part_id` - идентификатор от `new_tz.py`, `file` - имя файла ТЗ;
- `tc_ids` - идентификаторы тест-кейсов **этой** части, те же, что стоят в разделе «Скоуп
  части» её текста. Чужие кейсы в перечень не попадают;
- `gate_removes` - перечень объектов `{"gate": "<имя>", "keys": [...]}` по разделу «Санкции
  на удаление ключей гейта». Ничего не удаляется - пустой массив.

`spec.json` обязателен всегда, в том числе когда скил вызван сабагентом внутри
`meeseeks-spec-cycle`.

### Файл задания `<id среза в нижнем регистре>.task.json`

Формат - `schemas/intake/task.schema.json` репозитория `nikell28/taskforge`; это же тело
`POST /intake` и тот же вход у команды `tfc submit`.

Каркас: `{"version": 1, "nodes": [ ... ]}`. Одна вершина - одна часть ТЗ.

| Поле | Откуда | Правило |
|---|---|---|
| `local_ref` | `p1`, `p2`, ... по номеру части | уникален в вызове; только `A-Za-z0-9_.-` |
| `repo` | имя окружения, оно же первый сегмент имени файла ТЗ | имя записи репозитория в контуре, не `org/repo` |
| `branch` | трейлер `Meeseeks-Branch` шапки ТЗ | одна ветка на срез: у всех частей она одна |
| `base` | базовая ветка из колонки `Репозиторий` строки среза | у всех частей она одна; не задаётся только когда база совпадает с умолчанием репозитория |
| `task_id` | ID задачи-родителя среза | |
| `task_ref` | `part_id` при разрезе, иначе ID среза | |
| `spec` | **текст файла ТЗ целиком** | не путь и не выдержка |
| `tc_ids` | `tc_ids` части | только свои кейсы |
| `gate_removes` | `gate_removes` части | перечень пуст - поле не кладётся |
| `depends_on` | предыдущая часть | `[{"local_ref": "p<N-1>"}]`; у первой части поля нет |

**Почему `base` проставляется.** Умолчание репозитория в контуре - `master`. Базовая ветка
среза живёт в колонке `Репозиторий` его строки и совпадать с умолчанием не обязана: срез
бывает нарезан на интеграционную ветку. Не проставили `base` - контур возьмёт умолчание, и
вершина уедет ветвиться и мержиться не туда, молча. Оставить поле незаданным можно ровно в
одном случае: базовая ветка строки среза и есть умолчание репозитория.

Проверки перед выдачей файла. Не прошла хоть одна - стоп, файл не отдаётся:

- JSON разбирается;
- `version` равен 1;
- `nodes` непуст;
- у каждой вершины есть `local_ref`, `repo`, `branch`, `task_id`, `task_ref`, `spec`,
  `tc_ids`;
- `local_ref` уникальны;
- `depends_on` ссылается на `local_ref` этого же вызова;
- все части несут одну `branch` и связаны цепочкой;
- базовая ветка строки среза отлична от умолчания репозитория - `base` стоит у каждой
  вершины и равен ей; совпадает с умолчанием - поля нет ни у одной;
- `spec` непуст и начинается с заголовка ТЗ;
- **разбор скоупа по каждому `spec` даёт непустые оба перечня** (раздел «Проверка разбора
  перед выдачей»).

Скил задание **в очередь не подаёт**: файл отдаётся человеку, команда подачи -
`tfc submit <файл>` - называется в сводке.

Когда скил вызван сабагентом внутри `meeseeks-spec-cycle`, задание собирает оркестратор из
всех срезов сразу - тогда этот шаг пропускается, файл `.task.json` не собирается, а
`spec.json` с полями `tc_ids` и `gate_removes` остаётся обязательным.

## Критические правила

- Единица ТЗ - срез. ТЗ на задачу целиком не пишется.
- Сборка идёт в два шага: сначала большое ТЗ среза (`run/<задача>/<срез>/tz-big.md`), потом
  разрез на маленькие. Большое ТЗ - рабочий документ прогона: отдаётся человеку, в задание
  не едет; телами вершин задания идут только маленькие ТЗ.
- Каждая часть полна по своему предмету: агент читает только её, ни большого ТЗ, ни соседних
  частей он не видит. Общий контекст, нужный для понимания предмета части, в ней
  повторяется; план других частей - нет.
- Репозиторий берётся из строки среза, не выводится заново. Граница среза - репозиторий,
  ветка, PR - `meeseeks-slice`.
- Приёмка ТЗ - колонка `Критерий готовности` среза, не формулировка задачи.
- Код читается на базовой ветке среза из колонки `Репозиторий` его строки, не на `master`:
  `master` читается, только когда база им и названа.
- Задача-родитель среза без «Корня» или без обеих рамок - стоп: ТЗ не пишется, разрыв
  прослеживаемости возвращается человеку. Колонки «Основание» на листе нет, «Класс»
  вычисляется из заполненности рамки поведения. Правила уровня задачи - `meeseeks-backlog`.
- Разрыв прослеживаемости и выход за рамку - два разных дефекта, проверяются порознь:
  первый на Шаге 2, второй против запретов связанных строк «ADR».
- Архитектурные инварианты берутся с листа «ADR» - колонка «Что этим запрещено»; критерий
  связывания - существует правдоподобная реализация среза, нарушающая хотя бы один её пункт.
  «Требование к приёмке» идёт в приёмочные критерии, «Чем проверяется (TC)» сверяется с
  фазами тестов. Лист «Решения» - дополнение, не основа.
- Колонка `Контракт` строки среза непуста - снимок из «Где лежит снимок» идёт в «Изменения
  по слоям» либо в «Антискоуп», «Чем ловится расхождение» - в приёмочные критерии. Контракт
  без снимка - развилка.
- Развилка закрывается фактом кода, строкой «ADR», строкой «Развилки» (Р-N, в том числе со
  статусом `принято моделью`) или записью «Решения». Открытый ОВ-N - самостоятельное
  основание остановиться. Формат стопа - под 12 колонок листа «Развилки».
- Хостинг репозитория берётся из листа «Репозитории»; конкретный MCP в теле правил не
  зашивается.
- Незакрытая зависимость среза - стоп: ТЗ читало бы не то состояние кода.
- Единица бюджета - вызов инструмента, та же, что `TURNS` в `mrctl ls`. Потолок и пол
  берутся из `tz_budget.py --limits`, числом в тексте не повторяются. Оценка считается
  скриптом, не на глаз, и пишется в раздел «Объём» каждой части.
- Раздел «База» называет красные на входе тесты поимённо. Без него исполнитель устанавливает
  их сам - прогоном всей сюиты, и это десятки вызовов из бюджета части.
- «Локальные проверки» в скоупе называют пути. Не названы - исполнитель выбирает сам и
  выбирает широко.
- «Изменения по слоям» и «Антискоуп» - плоские перечни: путь первым в строке, в обратных
  кавычках, дальше роль слоя и что сделать. Подзаголовков внутри этих разделов нет -
  заголовок любого уровня обрезает раздел, и перечень становится пустым.
- «Антискоуп» есть в каждом маленьком ТЗ, и при разрезе, и без него: пустой антискоуп
  проверку разбора не проходит.
- Перед выдачей по каждому маленькому ТЗ прогоняется правило разборщика: оба перечня
  непусты и совпадают с путями, названными в ТЗ. Не сошлось - ТЗ правится, а не отдаётся.
- Пустой перечень скоупа не равен отсутствующему: вне перечня оказывается каждый файл, отказ
  `gate-regression` получает класс «прогон» вместо «задача», а шаг правки находок остаётся
  без разрешённых файлов. Новый тестовый файл под маской тестов объявления не требует,
  правка существующего - требует, иначе чужой тест можно переписать молча.
- Часть, удаляющая, переименовывающая или переписывающая существующие ключи гейта, несёт
  раздел «Санкции на удаление ключей гейта» и поле `gate_removes`: гейты направления `grew`
  считают регрессией исчезновение ключа, и без санкции цикл выгорает по потолку итераций.
  Идентификаторы снимаются `pytest --collect-only -q` на текущем HEAD ветки, не по памяти;
  у параметризованного теста правка ожидаемого значения тоже меняет идентификатор.
- `spec.json` по каждой части несёт `tc_ids` (только свои кейсы) и `gate_removes` (пусто -
  пустой массив). Обязателен всегда, в том числе при вызове сабагентом.
- Выход шага выдачи - маленькие ТЗ, большое ТЗ и `<id среза в нижнем регистре>.task.json`.
  Файлы для коммита в git-inbox скил не готовит.
- Одна ветка на срез: у всех вершин задания одна `branch`. `base` проставляется базовой
  веткой строки среза; не задаётся только когда она совпадает с умолчанием репозитория.
  Умолчание контура - `master`, и при интеграционной базе молчаливый откат на него уводит
  вершину не туда.
- Задание скил в очередь не подаёт: файл отдаётся человеку, `tfc submit <файл>` называется
  в сводке. Внутри `meeseeks-spec-cycle` задание собирает оркестратор, и этот шаг
  пропускается.
- Сверх потолка - разрез на части по той же ветке и тому же PR, а не возврат в
  `meeseeks-slice` и не ТЗ «как есть». Мержа между частями нет.
- Часть - вертикальный TDD-инкремент: после неё CI зелёный. Файл целиком принадлежит одной
  части.
- «Хендофф» части N и «Предусловие» части N+1 совпадают текстуально.
- Порядок исполнения частей держит план; трейлер `Meeseeks-Part` и секция «Предусловие»
  остаются второй линией и из маленьких ТЗ не убираются.
- Имя файла и `part_id` считает `new_tz.py`; имя считается до написания тела, потому что
  идентификаторы идут внутрь текста.
- Файл ТЗ начинается машинной шапкой `Meeseeks-Branch` / `Meeseeks-Repo` /
  `Meeseeks-Part` / `Meeseeks-PR-Title` - до заголовка, без пустых строк внутри. Без
  `Meeseeks-Branch` воркер работает по-старому.
- Имя ветки - `feat/<ID среза в нижнем регистре>`, одно на срез. В теле ТЗ оно не
  повторяется: один факт живёт в шапке.
- Ветка, трейлер части, отправка и pull request - `meeseeks-tdd-implementer`. Указаний о
  них в теле ТЗ нет, приёмка описывает состояние кода, а не origin.
- Неделимая часть сверх потолка допустима, если превышение названо в её «Объёме» строкой.
- Тест-кейсы только из реестра, по колонке `Источник` = ID среза; кейсы уровня стори - у
  замыкающего среза. Вывод и содержание кейсов - `meeseeks-testcases`.
- Кейс, проходящий через ожидание внешнего события, несёт строку «ожидание»: что ждётся, чем
  снимается в тесте, каким пределом ограничено. Не названо - исполнитель напишет ожидание
  без предела, и прогон закончится временем, а не результатом.
- Предмет соседних срезов задачи - out of scope, с явной пометкой.
- Неустранимая развилка - всегда стоп, никогда не выбор за человека, даже если вариант
  кажется очевидным.
- Технические расхождения (не архитектурные) - не блокируют ТЗ, идут отдельным разделом.
- ТЗ = описание *что*, не *как работать процессом*: TDD, ветка, PR, механика проверки
  предусловия - `meeseeks-tdd-implementer`.
- В файл проекта и в Google Drive не пишет, статусы срезов не проставляет.
