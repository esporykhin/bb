# Meeseeks Review - ревью PR среза напрямую

Выполняется здесь, в Codex Desktop/чате, а не передаётся в чистую сессию Codex.
Ревью опровергает, а не любуется: ищет, где не работает, где инвариант протекает, где тест
врёт - не оценивает «выглядит ли хорошо».

## Единица ревью

Единица - срез: граница среза - правило `граница-среза`, владелец `meeseeks-slice`. Поэтому
предмет ревью равен предмету одного среза, а не задачи. Задача закрывается всеми своими
срезами; её замыкающий срез прогоняет реестр кейсов задачи целиком, остальные - только свои.

Отсюда следствие, которого не было в задачном ревью: **критерий готовности соседнего среза
той же задачи - out of scope.** «Реестр задачи покрыт не полностью» находкой не является,
если непокрытое принадлежит срезу, который ещё не мержился. Проверять полноту реестра
задачи можно только на замыкающем срезе.

## Порог находки

Находка - то, что ломается на существующем коде или на существующем сценарии
эксплуатации. Обход, для которого нужно, чтобы кто-то сначала дописал новую цель, новый
тест или новый файл, - гипотеза, а не находка. Такие наблюдения в отчёт не идут, даже
если воспроизводятся мутацией.

Проверка: воспроизведение находки требует правки репозитория, которой в нём нет? Тогда это
гипотеза. «Гейт держится на списке имён и пропустит цель, которую могут добавить»,
«фикстура опубликует, если новый тест забудут пометить» - гипотезы, не находки.

Границы механизма называются один раз, в цикле, где механизм появился, и только если
граница уже пройдена кем-то в этом же репозитории. Во втором и последующих циклах те же
границы не переоткрываются.

## Сужение скоупа по циклам

Первый цикл ревью PR смотрит весь предмет среза. Каждый следующий смотрит уже:

1. закрыты ли находки предыдущего цикла;
2. не появилось ли регрессии в том, что раньше работало;
3. изменилось ли что-то в коде, чего в прошлом цикле не было.

Неизменившийся с прошлого цикла код повторно не ревьюится и новых классов проверок не
получает. Если в цикле N код прошёл проверку, а в цикле N+1 к нему нашёлся новый угол
зрения - этот угол не открывается, потому что предыдущий вердикт был вынесен без него.

Если PR не менялся с прошлого цикла (тот же HEAD) - не ревьюить заново. Сослаться на
прошлый отчёт одной строкой и назвать действие, которое ждёт исполнения.

## Стоимость циклов

Перед выдачей вердикта проверить: достигнут ли результат, ради которого срез заведён -
колонка `Результат` строки среза? Если нет, а находки цикла касаются обвязки - тестов,
документации, сообщений об ошибках, - назвать это в отчёте прямо: предмет среза не
двинулся, цикл потрачен на периметр. Это часть вердикта, не замечание в конце.

Находки тяжести «стиль/качество» не превращаются в вопросы «требует решения человека».
Их место - короткий список в конце отчёта, без развилок и без вариантов. Если находка
стиля кажется настолько важной, что просится в решение, значит она либо ломает что-то
существующее (тогда это REWORK), либо не просится.

## Источники

1. **Файл проекта** - листы «Срезы», «Тесткейсы», «Задачи», «ADR», «Контракты», «Принципы
   построения», «Решения», «Развилки», «Открытые вопросы», «Репозитории»: тот же реестр
   приёмки, что использовался при написании ТЗ, не то, что утверждает сам PR. ADR ведутся
   строками листа «ADR», а не файлами в папке проекта и не в `docs/` репозитория; искать их

   «Репозитории»: заголовок, тело и база PR, список изменённых файлов, содержимое файлов на
   ветке PR.

## Шаг 1 - Получить ссылку на PR

Распарсить org/repo/номер PR из ссылки.

## Шаг 2 - Понять, какой срез выполнялся

Через MCP хостинга, названного на листе «Репозитории», получить заголовок, ветку, базу и
тело PR, список изменённых файлов. Извлечь ID среза - из имени ветки или из текста PR.

ID среза имеет вид `<ID задачи>-S<N>` и опознаётся по границе токена, чтобы номер среза не
склеился с номером, начинающимся с тех же цифр. Имя ветки даёт ID среза только если оно
собрано по действующей конвенции; иначе из имени выводится одна задача, ID среза берётся из
тела PR, а если его нет и там - вопрос человеку, какой из срезов задачи выполнялся. Гадать
по diff не нужно: срезы одной задачи различаются репозиторием и предметом, но не всегда
очевидно.

<!-- example:start -->
`CI-9-S1` не совпадает с `CI-9-S10`. Рекомендуемая форма ветки -
`feat/<id среза в нижнем регистре>-<краткое>`, например `feat/ci-9-s1-verify-job`. Старая
конвенция `feat/s<N>-<id задачи>-*` несёт номер фазы («СРЕЗ 1» колонки `Фаза` листа
«Задачи»), а не номер среза.
<!-- example:end -->

Расхождение между срезом, названным вызывающим, и тем, что видно в PR, - находка, а не
повод молча переключиться на другой срез.

## Шаг 2а - Определить номер цикла и что уже проверено

По телу PR и предыдущим отчётам ревью определить, какой это цикл и какие находки уже
закрывались. Сверить HEAD PR с коммитом, проверенным в прошлом цикле. Дальше работать в
скоупе из раздела «Сужение скоупа по циклам».

## Шаг 3 - Собрать реестр приёмки среза заново из файла проекта

Не доверять описанию PR как источнику критериев - оно может утверждать, что сделано, реестр
остаётся источником истины. Контекст собирается скриптом:

```
python3 /mnt/skills/user/meeseeks-spec-cycle/scripts/slice_context.py \
  <project.xlsx> <ID среза> --out context.json
```

Что чем является в ревью:

- **`slice.Критерий готовности`** - перечень прослеживаемости: полный и единственный
  перечень того, что этот PR обязан закрыть. Выход за рамку он не покрывает - разрыв
  прослеживаемости и выход за рамку два разных дефекта, и проверяются они порознь. Выход за
  рамку проверяется отдельно, по колонке «Что этим запрещено» строк листа «ADR», названных
  в колонке «Рамка устройства» задачи этого среза (вопрос 4 Шага 5).
- **`slice.Результат`** - что должно стать наблюдаемым после мержа. Проверяется вопросом
  «Стоимость циклов».
- **`slice.Репозиторий`** - репозиторий среза и его базовая ветка. База PR сверяется с этой
  базовой веткой; расхождение базы - находка. Молчаливый откат на дефолтную ветку
  репозитория - дефект, а не запасной путь.
- **`slice.Контракт`** - заполнен, значит у среза есть двусторонняя граница. Тогда по строке
  листа «Контракты» взять колонки «Где лежит снимок» и «Чем ловится расхождение» и проверить
  прогон против файла-снимка; расхождение со снимком - FAIL. Нарушение контракта ловится
  прогоном, а не чтением диффа. Границы внутри одного репозитория контрактом не считаются -
  их держат рамки ADR.
- **`testcases`** - кейсы с `Источник` = ID среза. Каждый обязан быть покрыт реальным
  тестом.
- **`closing_testcases`** - непусто только у замыкающего среза. На нём же проверяется, что
  реестр задачи прогоняется целиком.
- **`sibling_slices`** - соседние срезы задачи. **Их критерии и их кейсы в приёмку этого PR
  не входят.** Непокрытый кейс, чей `Источник` указывает на другой срез, - не находка.
- **`decisions_mentioning_id`** - черновик списка инвариантов. Лист «Решения» прочитать
  самому: инвариант бывает сформулирован без упоминания ID.

## Шаг 4 - Получить код на закоммиченном состоянии PR

Содержимое читать на HEAD ветки PR через MCP хостинга, названного на листе «Репозитории»,
не полагаясь на описание изменений из тела PR. Если нужно прогнать тесты - `bash_tool`: клонировать репозиторий, получить ref
PR (`git fetch origin pull/<n>/head` или аналог для используемого хостинга), checkout ровно
на commit PR - не работать с рабочим деревом и не доверять отчёту PR о зелёном сьюте на
слово.

**Ограничение окружения.** Внешняя инфраструктура, от которой зависит полный тест-сьют, в
этой песочнице не поднимается. Реально прогнать здесь можно только тесты, не требующие
внешней инфраструктуры (изолированные unit). Интеграционные/e2e-тесты, завязанные на
инфраструктуру, проверяются статическим чтением кода теста, не исполнением. В отчёте всегда
явно указывать, какие тесты реально прогнаны, а какие только прочитаны - не выдавать
прочитанное за исполненное.

## Шаг 5 - Четыре вопроса ревью (не смешивать)

1. **То ли построили? (приёмка)** - критерий готовности среза и его реестр тест-кейсов из
   Шага 3: каждый пункт покрыт реальным тестом, тест про то, что заявлено, не про соседнее.
   Непокрытый хвост критерия вида «и соседнее продолжает работать» - находка только если
   соседнее реально затронуто изменением. Формулировки в реестре пишет тот же контур, что
   проводит ревью; страховочная приписка, ничего не проверяющая по существу, не должна
   возвращаться находкой на следующем цикле. В таком случае - назвать хвост избыточным и
   предложить снять его из реестра, а не требовать теста под него; сам реестр правит
   `meeseeks-testcases`.
2. **Правильно ли построили? (инварианты)** - сквозные законы трёх листов: «Принципы
   построения», «Решения» и «Развилки». Два последних не путать: «Решения» - короткие
   фиксации, «Развилки» - журнал развилок Р-N с вариантами и отвергнутым. Тесты могут быть
   зелёными, а инвариант - обойдён стороной.
3. **Не сломали ли соседнее? (регрессия + границы)** - out of scope среза не тронут, чужие
   тесты не изменены. Предмет соседних срезов задачи - тоже граница: PR, реализовавший
   заодно кусок соседнего среза, нарушил границу, даже если код работает.
4. **Не вышли ли за рамку? (рамка устройства)** - по каждому ADR, связанному с этим срезом,
   проверить колонки «Что этим запрещено» и «Требование к приёмке» строки листа «ADR».
   Кандидаты берутся из колонки «Рамка устройства» задачи среза. Связанным ADR считается
   тот, для которого существует правдоподобная реализация строки, нарушающая хотя бы один
   запрет; совпадение термина, репозитория или задачи связыванием не считается.
   Прослеживаемость этого вопроса не закрывает: критерий готовности бывает покрыт целиком,
   а запрет - нарушен.

## Шаг 6 - Проверка честности тестов

На закоммиченном состоянии (HEAD PR). Искать: `assert True`, безусловный `skip`/`xfail`,
тесты без реального assert, over-mocking - мок, скрывающий уровень регистрации или
инфраструктуры. Если находка касается «X не зарегистрирован» - проверять регистрацию именно
в закоммиченном коде, не в описании PR.

<!-- example:start -->
Частый случай: замоканный `execute_activity` не ловит, что функция вообще не зарегистрирована
как activity/handler.
<!-- example:end -->

Повторяющийся паттерн одной и той же находки в нескольких файлах - не одна находка, а
паттерн: не множить точечные замечания по каждому файлу, а явно указать в отчёте, что нужен
`git grep` по всему репозиторию для критерия готовности фикса, не список конкретных файлов.

## Шаг 7 - Классификация находок → вердикт

Вердикт детерминированный, из фиксированного множества, равен худшей находке:

| Тяжесть находки | Что это | → Вердикт |
|---|---|---|
| Нарушен инвариант | HITL обойдён, determinism boundary сломан, идентификатор шага не пробрасывается, нет идемпотентности, изменение существует только в рабочем дереве, а не в коммите | **FAIL** |
| Приёмка не покрыта | критерий готовности среза без реального теста, тест-заглушка | **REWORK** |
| Расхождение с контрактом | прогон против файла-снимка контракта строки среза расходится со снимком | **FAIL** |
| Выход за рамку устройства | реализация нарушает запрет из «Что этим запрещено» связанного ADR либо не держит его «Требование к приёмке» | **REWORK** (FAIL, если нарушен инвариант) |
| База PR не та | база PR не совпадает с базовой веткой из колонки «Репозиторий» строки среза | **REWORK** |
| Границы нарушены | out of scope тронут, чужой тест изменён, реализован предмет соседнего среза | **REWORK** (FAIL, если тронут инвариант в чужом коде) |
| Стиль/качество | дублирование, нейминг, отклонение от принятых паттернов | **PASS с замечаниями** |
| Противоречие PR ↔ репозиторий (техническое) | явно описанное расхождение | **ESCALATE** |
| Критерий среза недостижим в его репозитории | приёмка требует изменения в соседнем репозитории, где среза под это нет | **ESCALATE** (ошибка нарезки, чинится в meeseeks-slice) |
| Неустранимая развилка выбрана молча | PR выбрал вариант за человека там, где выбора не было | **FAIL** (если выбор уже сделан) или **ESCALATE** (если развилка ещё не разрешена) |
| Приёмка упирается в открытый ОВ | закрыть находку нельзя, пока открыт вопрос листа «Открытые вопросы» | **ESCALATE** со ссылкой на ОВ-N |

## Шаг 8 - Границы полномочий (жёстко, не нарушать)

- Не мержит PR и не аппрувит в гите. Выход - только отчёт с вердиктом.
- Не решает противоречия сам - ESCALATE с описанием; не выбирает за человека на неустранимой
  развилке, даже если выбор кажется очевидным.
- Не правит код и не коммитит ничего.
- В файл проекта не пишет, статус среза не проставляет.

```markdown

**Репозиторий:** [org/repo] · **Ветка:** [ветка] · **Проверено на коммите:** [sha]
**Задача:** [ID задачи] · **Замыкающий срез:** да/нет

## Предмет среза
Результат: [колонка «Результат»] — достигнут / не достигнут
База PR: [база PR] vs [базовая ветка колонки «Репозиторий»] — совпадает / расходится
Соседние срезы задачи (out of scope): [ID — статус]

## Рамка и контракт
Рамка устройства: [ADR-N — запрет не нарушен / нарушен: чем]
Контракт: [K-N — снимок сверен прогоном / расхождение: чем | прочерк]

## Прогнано / прочитано
- Реально исполнено: [список тестов, которые запускались в этой сессии]
- Только прочитано (инфраструктурная зависимость): [список]

## Находки
1. [тяжесть] · [файл:строка] · [описание] · [как воспроизвести]
```

## Критические правила

- Единица ревью - срез. Приёмка соседних срезов той же задачи в скоуп не входит; полнота
  реестра задачи проверяется только на замыкающем срезе.
- Опровергать, а не любоваться - искать, где ломается, не оценивать «выглядит хорошо».
- Находка - то, что ломается сейчас. Обход, требующий дописать в репозиторий цель, тест
  или файл, которых там нет, - гипотеза; в отчёт не идёт.
- Каждый следующий цикл ревью уже предыдущего: находки прошлого цикла, регрессия, новый
  код. Новые классы проверок по неизменившемуся коду не открываются.
- PR с неизменившимся HEAD не ревьюится повторно - ссылка на прошлый отчёт и название
  ожидающего действия.
- Находки «стиль/качество» не превращаются в развилки для человека.
- Если предмет среза не двинулся, а цикл ушёл на периметр - сказать это в вердикте.
- Реализованный заодно предмет соседнего среза - нарушение границы, а не бонус.
- Реестр приёмки берётся из файла проекта, не из описания PR.
- Критерий готовности - перечень прослеживаемости; выход за рамку проверяется отдельно, по
  колонке «Что этим запрещено» связанных ADR. Это два разных дефекта.
- Контракт проверяется прогоном против файла-снимка, а не чтением диффа; расхождение со
  снимком - FAIL.
- База PR сверяется с базовой веткой из колонки «Репозиторий» строки среза.
- Тесты - на закоммиченном состоянии; в этой песочнице реально исполняются только тесты без
  внешних зависимостей, остальное - чтением, с явной пометкой в отчёте.
- Вердикт - из фиксированного множества (PASS/REWORK/FAIL/ESCALATE), не «в целом нормально».
- Не мержит, не правит код, не решает неустранимую развилку за человека.
