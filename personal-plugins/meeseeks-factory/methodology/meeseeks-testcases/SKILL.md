# Meeseeks Testcases — реестр тест-кейсов

## Место в методологии

`meeseeks-triage` → `meeseeks-decompose` → **`meeseeks-testcases`** → `meeseeks-spec` →
Codex → `meeseeks-review`.

Реестр тест-кейсов принадлежит целиком этому скилу — включая кейсы, рождённые находками
ревью. `meeseeks-fix-spec` пишет ТЗ на доработку и реестр не трогает: два артефакта, два
скила.

<!-- example:start -->
Это решение заменяет правило от 2026-08-03 о едином артефакте.
<!-- example:end -->

`meeseeks-spec` берёт кейсы из реестра как есть и раскладывает их по фазам — см.
`meeseeks-spec`. Поэтому колонка «Тип» — не разметка, а управление порядком реализации.

## Источник

Файл проекта — таблица в облачном хранилище. Выгружать через `download_file_content`
с `exportMimeType` на xlsx, разбирать `openpyxl` с `data_only=True`. Листы: «Задачи»,
«Подзадачи», «Тесткейсы», «ADR», «Контракты», «Открытые вопросы», «Решения», «Развилки»,
«User Flow».

Шапка листа «Подзадачи» стоит в третьей строке, строки 1-2 пустые; то же у «User Flow».
Шапку искать сканом первых строк. Скрипт, берущий шапку из первой строки жёстко, на этих
листах прочитает пустоту.

<!-- example:start -->
Google Drive, `fileId = "1mgoml4Kv3NPSoZYbbjTht0Fsw1Q_4xB1I9qDZ4N6zQg"`.
<!-- example:end -->

**Код не читается.** Вся конкретика — имена функций, ключи схем, коды возврата, пути
файлов — уже лежит в колонке «Изменение» подзадачи: её туда положил `meeseeks-decompose`,
который код читал. Если подзадача контракта не называет, кейс писать не по чему — см.
стоп-правило (Шаг 6).

## Методология: откуда берутся кейсы

**Каркас покрытия — критерий готовности подзадачи.** Критерий раскладывается на
различимые утверждения; каждое утверждение даёт один кейс.

<!-- example:start -->
Критерий CI-9.3 содержит два утверждения (упорядоченный список стадий;
`MissingVerifyCommandError` не сломан) — кейсы `-a` и `-b`. Критерий CI-9.1 содержит
одно — кейс `-a`.
<!-- example:end -->

**Дополнительный класс — регрессия инварианта.** Инвариант живёт в колонке «Что этим
запрещено» действующей рамки листа «ADR». Если подзадача трогает код, на который такой
запрет распространяется, добавляется кейс на то, что инвариант не сломан. Только для
инвариантов, которые подзадача реально может задеть.

**Техники тест-дизайна** (классы эквивалентности, границы, таблицы решений) применяются
внутри уже выведенного кейса — для формулировки Given. Источником объёма они не являются:
кейс, не выводимый ни из критерия, ни из инварианта, не выпускается.

## Шаг 1 — Определить вход

Режим А (по задаче или цепочке): ID задачи из явного указания или контекста разговора.
Режим Б (по находке): отчёт `meeseeks-review` с находками REWORK/FAIL.

Если ID не находится — спросить один раз, не гадать.

## Шаг 2 — Собрать цепочку

- Лист «Задачи»: строка по ID. Колонка **«Корень»** даёт ID инициативы; корень всегда
  инициатива и ровно одна. По корню собираются все задачи той же инициативы — это цепочка.
  Замыкающая задача цепочки — последняя по «Зависит от».
- Лист «Подзадачи»: все строки, где «Родитель» ∈ задачи цепочки.
- Лист «Тесткейсы»: все строки, где «Единица бэклога» ∈ задачи цепочки.
- Стори берётся из колонки **«Рамка поведения»** листа «Задачи» и опознаётся своей записью,
  а не позицией на листе: формулировку (роль, желание, польза) даёт рамка стори, роль
  стори — строка ролевой модели. Реестр ролевой модели — источник, откуда берётся роль.
- Проверка: роль стори существует в ролевой модели. Роли нет — это разрыв
  прослеживаемости: назвать его в аудите покрытия (Шаг 3) и вернуть человеку.
- Лист «User Flow»: представление последовательности шагов пути. Источником идентификаторов
  и формулировок стори не является.
- Лист «ADR»: рамки устройства, названные в колонке «Рамка устройства» задач цепочки.
  Колонка «Что этим запрещено» действующей рамки — источник кейсов-регрессий, колонка
  «Требование к приёмке» — вход для Шага 8.
- Листы «Решения» и «Развилки» — журнал: читаются для контекста, источником объёма кейсов
  не являются.
- Лист «Открытые вопросы»: записи, адресованные задачам цепочки.

Колонка «Рамка поведения» у задачи пуста — задача техническая. Приёмочного кейса стори у неё
нет, и это норма, а не разрыв: работать по критериям готовности её подзадач.

## Шаг 3 — Аудит покрытия (первым, до генерации)

Проверить и перечислить:

- подзадачи цепочки без единого кейса;
- утверждения критериев готовности, не покрытые ни одним Then;
- кейсы-сироты: «Источник» указывает на подзадачу, которой нет на листе «Подзадачи»;
- расхождение «Единица бэклога» кейса с родителем его подзадачи;
- стори, роль которой не найдена в ролевой модели, — разрыв прослеживаемости;
- стори без приёмочного `E`-кейса на замыкающей задаче;
- рамки устройства цепочки, чьё «Требование к приёмке» не покрыто ни одним кейсом;
- кейсы, чей Then не различает исходы там, где критерий требует различия;
- кейсы, чей Then сформулирован через факт вызова мока, а не через наблюдаемый исход.

Аудит идёт всегда, в обоих режимах. Если пробелов нет — сказать это прямо и не выпускать
патч.

## Шаг 4 — Генерация кейсов (режим А)

Один кейс на утверждение критерия. Правила:

**Свёртка.** Несколько входов сворачиваются в один кейс только когда проверяют один
инвариант разными данными — класс эквивалентности. Разные инварианты не сворачиваются.

**Различимость.** Если критерий требует отличать исходы, Then формулирует различие явно:
не «стадия падает», а «падает на lint, имя упавшей стадии в результате, отличимо от
провала verify».

**Честность.** Then описывает наблюдаемый исход системы, не факт вызова мока и не порядок
внутренних вызовов. Кейс, зелёный без изменения кода, не выпускается — кроме кейсов,
помеченных как регрессия существующего поведения, где это и есть цель.

**Негативная ветка.** Обязательна там, где критерий содержит гейт, классификацию или код
возврата. Положительный путь без отрицательного такой критерий не закрывает.

**Привязка.** Then называет контракты шва: публичную функцию, ключ схемы результата, код
возврата, путь файла-артефакта — то, что зафиксировано в колонке «Изменение» подзадачи.
Не называет приватные хелперы, порядок вызовов и структуру ветвлений: кейс, краснеющий от
рефакторинга без изменения поведения, приёмкой не является.

**Объём.** 1–4 кейса на подзадачу. Больше четырёх — признак, что подзадача крупнее
подзадачного уровня; вернуть в `meeseeks-decompose`, а не дробить кейсы.

### Приёмочный кейс стори

Один `E`-кейс на стори, «Единица бэклога» = замыкающая задача,
«Источник» = `<ID стори> (стори)`. Given/When/Then описывают сквозной путь стори целиком,
не поведение отдельного механизма.

## Шаг 5 — Генерация кейсов (режим Б, по находке ревью)

Находки REWORK/FAIL из отчёта разбираются по исходу:

- находка вида «тест нечестный», «кейс не покрывает то, что заявляет», «Then не различает» →
  **правка существующего кейса**: строка переиздаётся с изменённым Then (или Given/When),
  TC-ID сохраняется, «Статус строки» = `изменено`;
- находка вида «поведение не покрыто вовсе» → **новый кейс** с ID
  `TC-<ID источника>-D<N>`, где источник совпадает с колонкой «Источник», `N` продолжает
  максимум D-кейсов этого источника;
- находка ESCALATE в реестр не превращается: решение принадлежит человеку, кейс на
  неразрешённую развилку не пишется.

## Шаг 6 — Стоп-правила

- Критерий готовности подзадачи не отвечает форме, заданной `meeseeks-decompose`, или
  подзадача не называет ни одного контракта → кейс не придумывать. Вернуть подзадачу в
  `meeseeks-decompose` с указанием, чего в ней не хватает.
- На задаче цепочки висит открытый или частично закрытый вопрос листа «Открытые вопросы»,
  от исхода которого зависит формулировка кейса → кейс не выдумывать: назвать ОВ по ID и
  остановиться на нём. Это штатный исход, а не пробел покрытия.
- Задача не найдена по ID → сказать прямо, похожий ID не подставлять.
- Пробелов покрытия нет → патч не выпускать, отдать результат аудита.

## Шаг 7 — Заполнение колонок

Порядок колонок листа «Тесткейсы»: `TC-ID | Уровень | Тип | Единица бэклога | Источник |
Given | When | Then | Контракт`.

- **TC-ID** — `TC-<ID источника>-<буква>`, буквы по порядку (`a`, `b`, `c`, `d`), продолжая
  существующие для этого источника. Кейсы по находкам — `TC-<ID источника>-D<N>`.
- **Единица бэклога** — ID задачи. **Источник** — ID подзадачи либо `<ID стори> (стори)`;
  позже «Источник» переставляется с подзадачи на срез — см. `meeseeks-slice`.
- **Уровень и Тип** выводятся из колонки «Слой» подзадачи:

  | Слой подзадачи | Уровень | Тип |
  |---|---|---|
  | Домен | Домен | U |
  | Orchestration | Интеграция | I |
  | Infra | Инфраструктура | I |
  | Тест — сквозной сценарий через границы компонентов или задач | Тест | E |
  | Тест — прогон одного механизма или регрессия одного сьюта | Интеграция | I |
  | Cleanup | Интеграция | I |

  Кейс уровня стори — всегда (Тест, E). Значения вне этих словарей не вводить.
- **Given** — предусловие: состояние системы и входные данные, названные конкретно.
- **When** — наблюдаемое действие или запуск.
- **Then** — исход по правилам Шага 4.
- **Контракт** — ID контракта из колонки «Контракт» родительской подзадачи; она пуста —
  из колонки «Контракт» задачи; нет ни там, ни там — прочерк. Правило заведения контрактов
  принадлежит `meeseeks-methodology`.

## Шаг 8 — Покрытие рамки кейсами

Колонку «Чем проверяется (TC)» листа «ADR» заполняет этот скил — после генерации кейсов,
не раньше. «Требование к приёмке» формулируется до заведения кейсов и TC-ID не содержит:
это норма, а не пробел.

Порядок работы:

- Взять рамки цепочки: строки листа «ADR» с состоянием `действует`, названные в колонке
  «Рамка устройства» задач цепочки.
- Сопоставить «Требование к приёмке» рамки с Then кейсов цепочки — и выпущенных сейчас, и
  уже лежащих в реестре. Требование покрыто, когда Then утверждает ровно то, что требование
  требует наблюдать; совпадение термина покрытием не считается.
- Покрытое требование даёт правку: в «Чем проверяется (TC)» перечисляются TC-ID покрывающих
  кейсов через запятую, уже стоящие там TC-ID сохраняются.
- Рамка, чьё требование к приёмке не покрыто ни одним кейсом, правки не получает — она
  называется пунктом аудита покрытия (Шаг 3) и возвращается человеку.
- Кейс под текст требования не выдумывается: объём кейсов даёт критерий готовности
  подзадачи, а не формулировка рамки.

Правки выпускаются вторым листом патча — см. Шаг 9.

## Шаг 9 — Патч и отчёт

Патч — отдельный xlsx, не копия файла проекта.

- Лист: `Тесткейсы`. Заголовки: девять колонок листа в том же порядке + `Статус строки`.
- `добавлено` — заливка зелёная (`solid`, `C6EFCE`); `изменено` — жёлтая (`solid`,
  `FFEB9C`). Изменённые строки выпускаются целиком, не только изменённой ячейкой.
- Патчится по TC-ID, не по номеру строки.
- Перенос по словам и верхнее выравнивание для Given/When/Then, ширина колонок задаётся
  явно.
- Второй лист: `ADR` — только если есть правки по Шагу 8. Заголовки: `ID` |
  `Требование к приёмке` | `Чем проверяется (TC)` | `Статус строки`; строки выпускаются со
  статусом `изменено` и жёлтой заливкой, патчатся по ID рамки. Остальные колонки рамки
  не выпускаются: правится одна колонка, «Требование к приёмке» идёт только для опознания.
- Имя файла ASCII: `testcases-patch-<ID>.xlsx` — карточка `present_files` не отрисовывается
  для файлов с кириллицей в имени. Сохранять в `/mnt/user-data/outputs/`.

Отчёт в чат:

```
[ID] — [название] · корень [ID инициативы] · рамка поведения [ID стори или «пуста — техническая задача»]
Аудит: подзадач без кейсов N, непокрытых утверждений M, сирот K
Добавлено: N кейсов (U/I/E: ...)
Изменено: M кейсов (по находкам ревью)
Рамки: требований покрыто P, не покрыто Q
Возвращено в декомпозицию: [подзадачи с непроверяемым критерием, если есть]
Открытые вопросы: [ОВ на задачах цепочки, если есть]
Дальше: meeseeks-spec
```

## Критические правила

- Кейс выводится из критерия готовности подзадачи или из инварианта действующей рамки
  листа «ADR» (колонка «Что этим запрещено»). Ниоткуда больше.
- Код не читается. Недостаток конкретики — дефект подзадачи, а не повод открыть репозиторий.
- Then про наблюдаемый исход, не про моки и не про порядок вызовов.
- Существующие строки реестра не переписываются молча: правка выпускается как `изменено`
  с сохранением TC-ID и только по находке ревью.
- Находка ESCALATE в кейс не превращается.
- Больше четырёх кейсов на подзадачу — сигнал вернуть подзадачу в декомпозицию.
- Колонка «Чем проверяется (TC)» листа «ADR» заполняется только по факту выпущенных кейсов;
  под непокрытое требование рамки кейс не сочиняется.
- Аудит покрытия выполняется всегда, даже когда пользователь просит просто «добавить кейсы».
