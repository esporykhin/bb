# Meeseeks Slice — группировка подзадач в срезы

## Место в методологии

`meeseeks-triage` → `meeseeks-decompose` → `meeseeks-testcases` → **`meeseeks-slice`** →
`meeseeks-spec` → Codex → `meeseeks-review`.

Срез — единица планирования и реализации (см. «Граница среза»). Подзадача осталась
разметкой швов системы и единицей вывода тест-кейсов; отдельным видом артефакта она
упразднена, новые подзадачи не заводятся.

Скил работает поверх готовой декомпозиции: подзадачи уже нарезаны по швам
(`meeseeks-decompose`), кейсы уже выведены из их критериев (`meeseeks-testcases`). Для
задач, декомпозируемых после переноса листа «Подзадачи» в «Срезы», шаг вливается в
`meeseeks-decompose`, и этот скил на них не вызывается.

**Режим запуска.** Кроме прямого вызова человеком по ID задачи, скил вызывается сабагентом
внутри `meeseeks-spec-cycle`: `sliced: false` в `task.json` означает, что срезов у задачи
нет, и нарезка делается до диспатча по срезам. Выход тот же - патч листов «Срезы» и
«Тесткейсы», строки вносит человек. Развилки вместо срезов останавливают и прогон цикла.

**Граница скила:** заполняет строки листа «Срезы» и переставляет колонку «Источник» листа
«Тесткейсы». Не пишет тест-кейсы, не пишет ТЗ, не правит подзадачи, не трогает статус
задачи.

## Граница среза

Срез — минимальный атомарный кусок задачи, доводимый до мержа; один срез = один
репозиторий = одно ТЗ = одна ветка = один PR.

Подзадача и срез режут по разным основаниям: подзадача — по логике и приёмке, срез — по
исполнимости и мержабельности. Сторона подзадачи принадлежит `meeseeks-decompose`.

## Источники

1. **Файл проекта** — Google Drive. Выгружать через `download_file_content` с
   `exportMimeType` на xlsx, разбирать `openpyxl` с `data_only=True`. Листы: «Задачи»,
   «Подзадачи», «Тесткейсы», «Срезы», «Решения», «Репозитории», «ADR», «Развилки»,
   «Открытые вопросы». Файл выгружается заново каждый вызов, не берётся из памяти.
2. **Код репозитория** — ограниченно и только для двух вопросов: в каком репозитории лежит
   изменение подзадачи и остаётся ли HEAD зелёным после предполагаемого среза. Разбирать
   реализацию построчно не нужно. Хостинг берётся из листа «Репозитории»; читать код через
   MCP того хостинга, который назван в реестре.

## Шаг 1 — Получить ID задачи

Из явного указания или из контекста разговора. Если не находится — спросить один раз,
не гадать.

## Шаг 2 — Собрать вход

- Лист «Задачи»: строка по точному ID. «Единица бэклога» — текст задачи, приёмка зашита
  в эту формулировку.
- Лист «Подзадачи»: строки, где «Родитель» = ID задачи. Шапка этого листа стоит в третьей
  строке, строки 1-2 пустые: чтение шапки из первой строки даёт пустоту, искать её сканом
  первых строк. Колонка «Изменение» несёт конкретику контрактов — её туда положил
  `meeseeks-decompose`, который читал код.
- Лист «Тесткейсы»: строки, где «Единица бэклога» = ID задачи. Колонка «Источник» даёт
  привязку кейса к подзадаче.
- Листы оснований — «Решения», «ADR», «Развилки», «Открытые вопросы»: записи, относящиеся
  к задаче или к затронутой области. Решение или развилка (Р-N), фиксирующие порядок
  поставки или границу репозитория, снимают развилку нарезки; строка «ADR» запрещает
  часть группировок колонкой «Что этим запрещено»; открытый ОВ — основание не резать.
- Лист «Срезы»: строки, где «Родитель» = ID задачи. Если они есть — см. Шаг 8.

**Стоп до группировки.** Подзадач у задачи нет — вернуть в `meeseeks-decompose`. Кейсов у
задачи нет — вернуть в `meeseeks-testcases`. Группировать нечего, патч не выпускать.

## Шаг 3 — Разложить подзадачи по репозиториям

Репозиторий подзадачи в листе «Подзадачи» не хранится: `meeseeks-decompose` называл
распределение только в отчёте. Восстанавливать по колонке «Изменение» — имя компонента,
путь файла, имя пакета или образа — и сверять с листом «Репозитории» точным поиском по
имени.

Компонент, заводимый этой же задачей, в реестре отсутствовать может: канонический путь
выводится правилом `<организация проекта>/<имя компонента>`. Компонент, который
существует или заводится другой задачей и не находится точным поиском по реестру, —
развилка (Шаг 5).

**Один срез — один репозиторий.** Подзадачи разных репозиториев в один срез не сводятся

## Шаг 4 — Группировка

**Правило границы.** Срез мержабелен: после его мержа HEAD репозитория зелёный, а
изменение наблюдаемо снаружи среза. Граница проходит там, где выполняются оба условия, а
не там, где кончается слой системы.

**Вертикаль.** Подзадача, не дающая собственного наблюдаемого поведения — поле в схеме
без потребителя, чистая функция без вызывающего, миграция без ручки, — склеивается с той,
которая это поведение даёт. Срез из одних подзадач-заготовок не выпускается.

Инфраструктурный срез без прикладного кода допустим, когда сама инфраструктура
наблюдаема и проверяема: compose-сервис в состоянии healthy, образ в registry, пакет на
pypiserver.

**Порядок.** Колонка «Зависит от» среза — транзитивное замыкание зависимостей подзадач,
в него входящих, за вычетом зависимостей внутри самого среза. Зависимости внутри среза
исчезают: они разрешаются одним PR. Цикл между срезами означает, что зависимые подзадачи
разведены по разным срезам, — перегруппировать, а не разрывать зависимость.

**Замыкающий срез.** Ровно один на задачу: тот, после которого прогоняется реестр
тесткейсов задачи целиком. Если терминальных срезов несколько, замыкающим назначается
последний по порядку мержа, и остальные терминальные попадают в его «Зависит от» —
реестр задачи прогоняется, когда весь её код на месте.

**Объём.** Оценка среза в вызовах инструментов считается и называется в отчёте; в лист не
пишется, колонки под неё нет. Потолок среза — 400 вызовов; это мера обозримости PR, а не
границы одной сессии агента. Потолок сессии живёт в `tz_budget.py --limits`, и ТЗ сверх него
режется на части по той же ветке и тому же PR (`meeseeks-spec`, Шаг 5б) — перегруппировкой
срезов это не решается и решаться не должно.

Срез сверх 100 проходов — перегруппировать: такой PR не обозрим на ревью. Если срез не
режется без потери мержабельности, это развилка (Шаг 5), а не повод выпустить его как
есть.

**Границы количества.**
- 1 срез — рабочий исход, а не отказ: задача целиком мержится одним PR, строка
  выпускается.
- 2–5 — рабочий диапазон.
- Больше 5 — патч не выпускается, вердикт: задача крупнее задачного уровня. Отдать
  предложенное разбиение на задачи в чат, без строк патча.

## Шаг 5 — Проверка на неустранимую развилку (обязательный чек-пойнт)

Развилка неустранима, если группировка требует выбора, не выводимого из кода и не
закрытого ни одним основанием: записью листа «Решения», строкой листа «Развилки» (Р-N,
в том числе со статусом `принято моделью`) или строкой листа «ADR». Признаки:

- две группировки равнозаконны и различаются последствиями поставки — контракт мержится
  отдельным срезом и оставляет потребителя на прежнем поведении либо мержится вместе с
  потребителем одним PR, — и ни один вариант не закрыт решением;
- мержабельного среза меньше целой задачи не существует, а задача сверх потолка в 100
  проходов: мержабельность и потолок противоречат друг другу, и способ разрешения (флаг
  функциональности, временная ветка интеграции, один крупный PR) не зафиксирован;
- `org/repo` компонента, который существует или заводится другой задачей, не находится
  точным поиском по реестру;
- подзадача относится к двум репозиториям сразу, и её невозможно отнести к одному без
  повторного разреза — разрез подзадачи принадлежит `meeseeks-decompose`;
- кейс-сирота: «Источник» указывает на подзадачу, которой нет на листе «Подзадачи», —
  распределить его по срезам не по чему;
- существующие срезы задачи противоречат текущей декомпозиции (Шаг 8).

**Если развилка найдена — СТОП.** Патч не выпускать, срезы не выдумывать. Результат —
список в чате:

```
Задача [ID] не готова к нарезке на срезы. Неустранимые развилки:

## Развилка 1: [суть]
Контекст: [факты кода / реестров, которые не разрешают вопрос однозначно]

Вариант А: [описание]
  + [плюсы]
  − [риски]
Вариант Б: [описание]
  + [плюсы]
  − [риски]

## Развилка 2: ...
```

Формат близок к строке листа «Решения» — после выбора заносится в лист почти без
переработки. Дальше в этом же вызове ничего не генерировать.

Развилка, закрываемая существующей записью листа «Решения», строкой листа «Развилки»
(Р-N), строкой листа «ADR» или фактом кода, развилкой не является: сослаться на основание
и продолжить. Открытый вопрос на листе «Открытые вопросы», задевающий нарезку, работает в
обратную сторону — это легальное основание остановиться и не резать, штатный исход, а не
ненайденное основание. Выбор за человека не делать, даже когда вариант выглядит
единственным разумным.

## Шаг 6 — Заполнение колонок листа «Срезы»

Порядок колонок: `ID | Родитель | Репозиторий | Результат | Критерий готовности |
Зависит от | Замыкающий | Статус | Контракт`.

- **ID** — `<ID задачи>-S<N>`, нумерация с 1 в порядке мержа. Формат `<ID задачи>.<N>`
  не использовать: он занят подзадачами той же задачи, и «Источник» тесткейса стал бы
  неоднозначным.
- **Родитель** — ID задачи как есть, включая составные ID задач.
- **Репозиторий** — `org/repo`, ровно один, и базовая ветка среза: куда он мержится.
  Срез есть единица поставки, и базовая ветка — его собственное свойство: ветка среза
  создаётся от базовой и мержится в неё. Базовая ветка указывается всегда и явно, включая
  `master`; молчаливый откат на дефолтную ветку репозитория — дефект, а не запасной путь.
  Без явной базовой ветки `meeseeks-spec` строит ТЗ против `master`, и цепочка ветка - PR -
  ревью ломается.
- **Результат** — что умеет фабрика после мержа этого среза, в терминах наблюдаемого
  поведения. Не перечень файлов и не перечень подзадач.
- **Критерий готовности** — условие приёмки среза: объединение критериев вошедших
  подзадач, сведённое к проверяемым утверждениям. Утверждение, потерянное при сведении, —
  ошибка группировки.
- **Зависит от** — ID срезов через запятую без пробела, корни — прочерк `—`. Зависимости
  на срезы других задач допустимы.
- **Замыкающий** — `да` у одного среза задачи, `—` у остальных.
- **Статус** — `NeedSpec` для всех выпускаемых строк. Значения дальнейшего жизненного
  цикла этот скил не проставляет: их набор ведёт человек на листе «Срезы».
- **Контракт** — ID контракта, который срез затрагивает; не затрагивает ни одного —
  прочерк `—`. Несколько ID — через запятую без пробела. Значение берётся из колонки
  «Контракт» подзадач, вошедших в срез. Новых записей в реестр контрактов этот скил
  не заводит.

## Шаг 7 — Перестановка «Источника» тест-кейсов

Каждый кейс задачи переезжает с подзадачи на срез, в который эта подзадача вошла.

- **TC-ID сохраняется.** Он назван в именах тестовых модулей и в отчётах ревью;
  переименование обнулило бы эти ссылки. Расхождение между TC-ID, построенным по ID
  подзадачи, и новым значением «Источник» — принятое следствие.
- Меняется единственная колонка «Источник»: ID подзадачи → ID среза. «Единица бэклога»,
  «Уровень», «Тип», Given, When, Then не трогаются.
- Строка выпускается целиком со статусом `изменено`.
- Кейс уровня стори (`Источник` = `<ID стори> (стори)`) не трогается — см.
  `meeseeks-testcases`.
- Кейс-сирота не переставляется — см. Шаг 5.

Разбиение полное по построению: каждый кейс задачи попадает ровно в один срез, объединение
по срезам равно реестру тесткейсов задачи.

## Шаг 8 — Если срезы у задачи уже есть

Существующие строки не перезаписывать.

- Все подзадачи и кейсы уже распределены — вердикт «нарезка уже есть», патч не выпускать.
- Распределены частично — патч содержит только недостающие срезы, нумерация `S<N>`
  продолжает максимум, в отчёте назвать, что не было покрыто.
- Существующая нарезка противоречит текущей декомпозиции — развилка (Шаг 5), молча не
  переписывать.

## Шаг 9 — Патч и отчёт

Патч — отдельный двухлистовой xlsx, не копия файла проекта.

- Лист `Срезы`: девять колонок в порядке Шага 6 + десятая `Статус строки` = `добавлено`,
  заливка зелёная (`PatternFill`, `solid`, `C6EFCE`).
- Лист `Тесткейсы`: девять колонок листа в его порядке — `TC-ID | Уровень | Тип | Единица
  бэклога | Источник | Given | When | Then | Контракт` — + `Статус строки` = `изменено`,
  заливка жёлтая (`solid`, `FFEB9C`).
- Патчится по ID и TC-ID, не по номеру строки.
- Перенос по словам и верхнее выравнивание для «Результат», «Критерий готовности»,
  Given/When/Then; ширина колонок задаётся явно.
- Имя файла ASCII — карточка `present_files` не отрисовывается для файлов с кириллицей
  в имени: `slices-patch-<ID>.xlsx`. Сохранять в `/mnt/user-data/outputs/`.

Отчёт в чат:

```
[ID] — [название]
Срезов: N
  [ID среза] · [org/repo] · [результат одной строкой] · оценка ~K проходов
  ...
Порядок мержа: [цепочка по «Зависит от»]
```

## Критические правила

- Срез — единица PR. Граница проводится по мержабельности, не по слою и не по шву.
- Один срез — один репозиторий. Подзадачи разных репозиториев не сводятся.
- Срез из подзадач-заготовок без наблюдаемого поведения не выпускается.
- Ровно один замыкающий срез на задачу.
- TC-ID при перестановке «Источника» сохраняется всегда.
- Тест-кейсы этот скил не пишет и не правит по существу: меняется одна колонка привязки.
- Оценка сверх 400 вызовов — перегруппировать; выпустить срез сверх потолка нельзя.
  Потолок среза — обозримость PR. Помещается ли срез в одну сессию агента, этот скил не
  решает: сверх потолка из `tz_budget.py --limits` ТЗ режется на части внутри того же PR
  (`meeseeks-spec`).
- Больше 5 срезов — сигнал резать задачу, а не срезы; патч не выпускается.
- Неустранимая развилка — всегда стоп, никогда не выбор за человека.
- Существующие строки листов «Срезы» и «Подзадачи» не переписываются.
